# Worklog — 2026-09-04: IBD peer-floor regression (77 KB/s), found by benchmark, fixed, re-measured

## Symptom
Fresh-install IBD on a dedicated 1.8 TB SSD (/mnt/2tbssd) downloaded at
**77 KB/s aggregate** across 16 chunk-claiming workers — ~3 days projected
for the ~965k-block span, against the hours the engine had previously been
measured at (commit 017a83b recorded 218 KB/s -> 1.6 MB/s from aggressive
eviction; the current build could not clear 0.1 MB/s). Per-peer medians over
20 minutes: **22 of 22 workers under the 32 KB/s dead-weight floor, zero
evictions**. Every peer looked "slow" and none was replaceable.

## Root cause
`93fab72` (2026-09-02, "dead weight needs a low block rate too") rewired
dl_catchup's eviction rule to

    dead = byte_rate < dead_weight_bps AND blocks_this_tick < 10

to stop the byte floor from banning honest peers serving tiny early blocks
(85 of 121 peers banned in 8 minutes on a fresh sync — a real bug, correctly
identified). But the AND made the **byte floor unreachable for the first
~150k blocks**: a peer trickling 6–9 blocks/s of few-hundred-byte blocks
clears the block check while sitting far under 32 KB/s, so it is never
evicted — and early-chain, that is most of a fresh pool. The eviction
feature that 017a83b had measured at 7x was, in the exact population a
fresh install meets, switched off.

## Discovery
Not found by any test. The user observed "too many slow peers" on the live
console; the benchmark harness (peer_speed_audit.py: per-worker medians,
floor coverage, kill counts) quantified it: 22/22 under floor, 0 kills, 3-day
ETA. `git log -L` on the eviction function named 93fab72 as the change; its
own commit message documented the false positive it fixed and, inadvertently,
the false negative it created.

## The rule, restated (Rule C, this commit's parent)
- byte_rate under the floor -> dead at **any** chain depth (a slow peer is a
  slow peer wherever it lives; early-chain "healthy" tiny-block peers sit
  ABOVE the byte floor by their block rate — 50 tiny blocks at ~500 B = 25
  KB/s, right at it, and 3 consecutive 10 s ticks of judgment still stands)
- at/above the floor -> dead only if blocks/tick < 10 AND bytes < 2x floor
  (catches a peer that stalled between ticks; spares 1.5 MB/s serving one
  fat block near tip)
- no reading yet -> alive (unchanged)

test_dialhelper now pins seven corners, including both original incidents:
the 09-02 false positive (2 KB/s, 50 tiny blocks... early-chain healthy peers
sit above the byte floor; the corner documents what does and does not die)
and the near-tip big-block server.

## Measurements (same datadir, same peer pool, /mnt/2tbssd)
| configuration | result |
|---|---|
| fresh sync, AND-rule (93fab72) | **77 KB/s**, 0 kills in 20 min, 3-day ETA |
| fresh sync, Rule C | **7.2 -> 11.0 MB/s**, 31 evictions over 9 h, ETA ~8 h total |
| 30k-hole A/B: byte-floor-only | 160k blocks / 240 s (1.4 MB/s) |
| 30k-hole A/B: block-floor-only | 178k blocks / 240 s (2.0 MB/s) |
| 30k-hole A/B: AND-rule on the SAME deep datadir | 4.5 MB/s, 0 kills — the
  exemption is only pathological where blocks are small AND the pool is
  fresh-proven; near tip the byte floor would bind anyway |

The last row is the honest footnote: 93fab72 did not slow a *caught-up*
node; it specifically crippled **fresh installs** — the population the
fresh_install_ibd acceptance test exists to serve, and where it crawled
(2026-09-02 run: same symptom, misdiagnosed then as peer-pool quality).

## Fix commit
`fix/dlc-peer-floor-depth` @ 2b36678 (with full attribution in the commit
message). Benchmark, logs, scripts, and this write-up live at
`benchmarks/2026-09-04-ssd-bmc-vs-core/` on the same branch.

## Lessons
- A guard added against a false positive must be measured against the
  false-negative it creates on the population that motivated the ORIGINAL
  feature (here: eviction tuned by 218->1600 KB/s measurement in 017a83b;
  93fab72 regressed exactly that win without re-measuring).
- Eviction rules deserve a pinned test per corner (now: test_dialhelper x7),
  not just a prose comment.
- The benchmark harness (per-peer medians + floor coverage + kill counts,
  scripts in the benchmark dir) is the detector; promote peer_speed_audit
  into the gate-adjacent validation/ set.
