    format matches my 8-byte int64 LE exactly).

  - **sendheaders (BIP130)**: new dispatch records a peer's `sendheaders`
    negotiation into `s_shdr`. New exported `node_announce_tip(fd,st,idx,
    use_headers)` advertises the current tip block as either an `inv`(MSG_BLOCK)
    37B or, when sendheaders is negotiated, a `headers` message (count=1, 80B
    header, tx-count 0 = 82B). The serve-loop tip-watch (each `.next`) calls it
    with `s_shdr`, so a peer that requested `sendheaders` gets a single 80-byte
    header announcement instead of a 36-byte inv entry — exactly Core's
    behavior. VERIFIED byte-structure-identical to real Core: after mining a
    new regtest block Core announced it to our sendheaders-negotiated peer as
    `headers`(82) (capture printed count=1 + header + tx-count 0x00), not an

## HTTP JSON-RPC server endpoint card t_0ca5d72e COMPLETE (server half of RPC-transport OPEN item) [DONE]
- Server side of the RPC wire-up, complementing the bitcoin-cli client card
  t_8e5be37f. Together they close the RPC-transport OPEN item (PLAN.md:500/503).
  The server dispatches through the SAME `rpc_dispatch()` as the client, so the
  two ends can never diverge.
- `asm/rpc_server.c/.h`: reusable HTTP JSON-RPC 2.0 server endpoint. Owns the
  loopback listen socket + accept thread, and reproduces bitcoin-cli/bitcoind
  behavior bit-exact (modeled directly on Core src/httprpc.cpp):
  - non-POST -> 405 "JSONRPC server handles only POST requests"
  - missing/bad auth -> 401 + `WWW-Authenticate: Basic realm="jsonrpc"`
  - non-parseable body -> -32700 "Parse error" (HTTP 500, V1 envelope)
  - parseable-but-not-object -> -32700 "Top-level object parse error" (500)
  - JSON-RPC 2.0 -> errors caught and returned as HTTP 200 with the V2 envelope
    (`{"jsonrpc":"2.0",<result|error>,"id":...}`, null member omitted)
  - V1/no-version -> both result+error fields, no jsonrpc field; -32600->400,
    -32601->404, else 500
  - V2 notification (no id) -> executed but HTTP 204, no body
  - id preserved verbatim (type + value)
- `asm/daemon/bitcoin_rpcd.c`: production HTTP server daemon — loads rpcport /
  rpcuser / rpcpassword from config/bitcoin.conf, builds a deterministic
  in-memory rpc_wallet, serves until SIGINT/SIGTERM. `TEST_RPC_PORT` env lets a
  harness pin/zero the port for integration tests.
- `asm/tests/test_rpc_server.c`: END-TO-END proof over the PRODUCTION path —
  forks+execs the REAL daemon/bitcoin_rpcd on an ephemeral port and drives it
  (a) with the REAL daemon/bitcoin_cli (getnewaddress/getbalance/listunspent
  output bit-exact; method-not-found stderr bit-exact) and (b) over raw sockets
  asserting the exact HTTP status lines, WWW-Authenticate header, and V2/V1
  JSON-RPC envelopes. 23 checks, all green.
- config/bitcoin.conf: added rpcuser=bitcoin / rpcpassword=bitcoin (Core auth).
- Makefile: rpc_server.o + daemon/bitcoin_rpcd + tests/test_rpc_server targets,
  wired into `test` + `clean`; .gitignore updated. Full `make test` green
  (56 binaries, 0 failures).
- Notable bug fixed during development: the read loop stopped at the first
  Content-Length mismatch because `find_header` was called with `namelen=15`
  for "Content-Length" (which is 14 chars) — off-by-one made strncasecmp catch
  the `:` at index 14 and return non-zero, so the server read only the headers
  and parsed a truncated body (-32700) on TCP-split requests. Fixed to 14 and
