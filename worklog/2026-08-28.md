## block-filter backfill: unstuck, then made fast

The mainnet filter index had been stuck at height **425,211** since 08-27.

- [x] **Root cause** (`aadbc68`): a fixed 64-entry array for prevout scripts
      too large for the inline arena. Height 425,211 is 2016-era, when large
      bare-multisig was common, and a block with more than 64 such outputs
      aborted the whole backfill. Nothing in consensus caps this at 64, so
      neither does the builder now.
- [x] Same commit: stop reading whole parent blocks. Resolving one prevout
      needs ~250 bytes, and `store_read_at` was copying up to 4 MB to get
      them — tens of megabytes per block filtered.
- [x] `f703493` — opt-in `MADV_RANDOM` on the archive mappings
      (`store_map_random`), used by the backfill: the workload reads one
      transaction from a block picked at random, so kernel readahead was
      measured pulling ~45 KB per 250 bytes used.
- [x] `fb78732` — resolve prevouts on 8 threads. **3.1x, byte-identical**
      output, which is how it was verified.
- [x] `d42bc18` — direct-mapped parent cache instead of a linearly scanned
      LRU. perf put ~10% of backfill CPU in that scan; a txid is already a
      uniform hash, so its low bits index the cache directly. 128 → 4096
      entries at the same time.
- [x] `9dcd74f` — `serve_cfilters` opened the filter files once per *filter*
      rather than once per request.
- [x] `508f0bf` / `878efb6` — the adopt gate judged the **connected height**
      rather than the tip, so it could adopt an index that was actually behind.
- [x] `29d3a02` — `validation/bfi_closing_pass.sh`: the long backfill runs to a
      FIXED target, so on completion it sits short of a moving tip and the
      144-block adopt gate correctly declines — the whole multi-hour run would
      sit on disk unused. The closing pass runs a short second build **with the
      daemon stopped**, because the builder and the daemon's tail both append
      to `bfilters.dat` with no lock between them.

### the pre-deploy review that found seven defects

Worth recording as the day's main lesson. The merged, pushed, fully-green
anon-networks code had **seven** defects, two of which meant **zero outbound
peers on the next restart**:

- The dial pool's entries became `"host:port"` and three consumers still
  `inet_pton`'d a bare host — boot parallel dial, feeler picker, `dlc_probe_round`.
  A reviewer proved it by compiling a harness against the real `peers.dat`:
  **64/64 entries failing**.
- `poll_idx` stayed at 1 after the IPv6 listener took `pfds[1]`, so every leg
  read the **previous leg's** `revents`.
- 64-byte pool slots truncated onion addresses; `listen=0` did not gate the v6
  listener; `-proxy` skipped IPv6/CJDNS; `proxyrandomize` never defaulted (Tor
  stream isolation silently OFF) and used a counter that **resets per fork**;
  self-announce leaked our clearnet IPv4 to onion and i2p legs; `.onion` names
  could reach the system resolver.

**Lesson:** changing a shared representation — what a "pool entry" *is* —
breaks consumers no test covers. A green 208-suite gate said nothing about any
of them.

## environment (authorized)

- [x] `tor` 0.4.9 (SOCKS 9050, ControlPort 9051 + cookie auth), `i2pd`, and
      `cjdns` built from source.
- [x] **i2pd: use the source build.** The Ubuntu package (2.49.0) segfaulted 66
      times in 45 minutes and never built tunnels; 2.61.0 from source has had
      zero crashes. The packaged unit is `Type=forking` and `--daemon` takes no
      argument — hence the drop-in override.
- [x] This box is "Firewalled - Symmetric NAT": it cannot publish its own
      leaseset, so an I2P **self-connect always fails** with `CANT_REACH_PEER`.
      Do not use a self-connect as the I2P proof; connect to a real remote.
- [x] IPv6 was disabled system-wide and enabled **at runtime only** — see
      2026-08-29, where that was finally made persistent.
