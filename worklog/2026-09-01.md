- [x] INCIDENT 00:31 (deploy 20260901b, the diverse pool): worker wedged --
      heartbeat silent, 0 outbound peers, SIGTERM unanswered, backtrace
      `tcp_connect_ip <- outbound_connect <- serve_download_worker`. Rolled
      back to 20260901a within minutes. ROOT CAUSE (pre-existing; the 21:20
      wedge yesterday had the same shape): both TCP connect paths set only
      SO_RCVTIMEO, so a blackholed address holds the blocking connect() for
      the kernel's ~127 s SYN schedule at every dial site outside the SIGALRM
      budget. Proven on this kernel with a scratch probe (no timeout: >10 s
      and counting; SO_SNDTIMEO=3: EINPROGRESS after 3.1 s). Fix: SO_SNDTIMEO
      10 s before connect() in bitcoin_net.asm and net6.c. The diverse pool
      only exposed it faster (more unreachable targets).
- [x] ROOT CAUSE, deeper: the SO_RCVTIMEO added 2026-08-15 NEVER took effect.
      bitcoin_net.asm loaded the timeval pointer into RCX; the kernel takes a
      syscall's 4th argument in R10 (SYSCALL clobbers RCX), so every
      setsockopt returned EFAULT into an ignored result -- strace:
      `setsockopt(3, SOL_SOCKET, SO_RCVTIMEO_OLD, NULL, 16) = -1 EFAULT`.
      Reads on outbound sockets have had NO timeout since that date; connect()
      never had one. Fixed (R10) + SO_SNDTIMEO; probe: connect to a blackhole
      returns EINPROGRESS after 10.3 s. tests/test_net_timeouts pins it (a
      silent server; the read must give up in ~10 s). Only the two sites in
      the asm issue setsockopt; the listeners are C.

- [x] THE COMMON TRIGGER: the worker's tx-submission follow loop
