## Session 2 — peer throughput, durable config, script verification Stage A

### THE HEADLINE: the block archive was destroyed and is being re-downloaded

`store_truncate_to` assumes blocks were appended in increasing height order. It
was called to "repair" an archive whose diagnosed defect **was** out-of-order
blocks (height 479,658 held block 43's data at `blk00000.dat` offset ~9,597).
It cut file 0 there and unlinked ~4,855 files — roughly 600GB, and the chain
had been at 962,831 blocks.

Re-sync is in progress and healthy: **510,926/962,831 (53.06%)**, 11 MB/s
sustained, 16 workers, 17 processes. Headers were never lost.

Guards added so this cannot recur:
- `store_layout_monotonic()` — read-only index walk (`bitcoin_store.asm`).
- `store_truncate_to` calls it ITSELF and returns -1 unchanged if the archive
  is non-monotonic (`a7e2d26`). A caller-only guard was the first fix
  (`1535468`) and was not sufficient — `reorg_execute` also truncates.
- The destructive test that reported seven green PASSes while deleting the
  archive symlinked live production `blk*.dat` into a scratch dir
  (`ftruncate` follows symlinks) and asserted only on `index.dat` counts.
  Destructive tests now build their own fixtures and assert the data survived.

### Bugs found while verifying the config work

- **`listen=0` killed the node.** `lsock()` correctly skipped the bind and
  returned -1; the caller treated that as fatal and exited. Outbound-only mode
  never worked, and neither did `connect=`, which implies `listen=0`. It had
  been reported verified earlier in the day on the strength of the log line
  appearing — the process printed it and died. Fixed in `5809942`.
- **`archive_check` read every block at the wrong offset.** `index.dat`'s
  `data_pos` points at the 8-byte frame (`[u32 len][u32 magic]`), not the
  payload. Its unit test passed because the FIXTURE wrote bare payloads at
  `data_pos` — same wrong assumption as the code. Only a live run exposed it.
  The frame is now validated explicitly. `e22699b`.
- **prune ran after the catch-up**, so a disk budget was only applied after a
  full header sync and archive fill — backwards. Moved ahead of the catch-up.
- **`dlc_span` had no notion of `prune_height`**, so pruning would have looped
  forever: delete, see holes, re-download, prune again. Span is now floored.
- **Two test files had never been compiled.** `test_node_config.c` and
  `test_addr_ingest.c` had no Makefile rule and were not in the test target;
  the suite had been reporting green without them. Both wired in.

### Script verification — the node does not verify block signatures

Established by reading the code, not assumption: `cons_verify` checks PoW, tx
parsing, coinbase shape and merkle root. `txval_modern` — the real script and
signature validator — is reached from exactly one place, `tx_accept.c:189`, the
MEMPOOL path. **Nothing script-verifies a block.** A block with valid PoW and a
correct merkle root is accepted regardless of its signatures.

- [x] Scoped in `PLAN_SCRIPT_VERIFY.md` with a MEASURED cost basis, not a
      guess: new `tests/bench_ecdsa` reports 8,731 verifications/s/core, so
      ~1e9 signatures is ~32 core-hours, about 2 h on 16 of this box's 32
      cores. That demotes `assumevalid` from prerequisite to optimisation.
      `cb675de`.
- [x] Decisions taken: **the asm interpreter is authoritative**, `assumevalid`
      defaults OFF, verification runs inline in `apply_block_inner`. `16e5d08`.
- [x] Stage B sizing CORRECTED: legacy `SignatureHash` is SIGHASH_ALL only
      (`sighash_all` hardcodes hashtype=1) and there is no `FindAndDelete`
      anywhere. Stage B now carries a full legacy SignatureHash before any
      dispatch work. `16e5d08`.
- [x] Stage A: the asm interpreter now emits Core's own ScriptError values,
      GENERATED from Core's header by `validation/gen_script_error_defines.py`
      (21 of 24 were wrong). Shared `asm/script_error_codes.h` so the C side
      cannot drift. `9f3c04b`.
- [x] Stage A: `bitcoin_scriptverify.c` — VerifyScript driven by `script_eval`,
      plus `tests/test_scriptverify_parity.c` comparing it against the C
      reference on the Core-validated P2SH vectors. `d3fb55d`.

**A REAL CONSENSUS BUG, found by that parity test on its first run:**
`interp_checkmultisig` did not enforce BIP147 NULLDUMMY — **the interpreter
accepted a spend Core rejects.** Its comment said the caller enforces it, which
is not implementable: the function pops the dummy during operand cleanup, so
nothing survives for a caller to inspect. Now checked at the opcode. Two more
from the same function: too-few operands returned EVAL_FALSE where Core reports
INVALID_STACK_OPERATION, and the operand-count errors were RAW NUMBERS (20 and
12, matching no scheme; Core uses 10 and 9) that survived the generated
renumbering untouched.
