## Round 0 addendum 7 — secp256k1_fe C twin (40/40) + a debugging war story

- [x] fe_twin.c: add/sub/mul/sqr/inv. The x86 ADcx/ADox/MULX carry schedule
      has no AArch64 equivalent; reimplemented the algorithm (schoolbook
      4x4, fold by 2^256==C, one conditional subtract) as constant-time C.
- [x] Gates: upstream test_fe 40/40 (vectors + sqr==mul + a*inv(a)==1 per
      vector), test_fe_sqrt via crypto_fe_sqrt.c ALL PASS.
- [x] The gate caught two real bugs in my first reduce512 (both invisible
      to per-round static checks, found by differential testing against
      python big-int on random 512-bit inputs):
      (1) acc[5] weight typo: `<< 32` instead of `<< 64`;
      (2) the oh*C fold added lo at v[0]/hi at v[1] — correct weights are
      v[1]/v[2] (oh carries weight 2^64).
- [x] Also found and fixed the REAL inv bug: the exponent loop iterated
      bits LSB-first with the MSB-first square-and-multiply recurrence
      (result^2 * a^bit), computing a^(bit-reversed p-2). Fixed to iterate
      MSB-first. Symptom: inv correct for special inputs (1, p-1) but
      garbage for random ones.
- [~] test_fe_repr/test_fe_inline require the x86-only fe_ref/_inl
      differential objects; superseded by test_fe's vectors + the python
      big-int differential (5000-case) used during bring-up.
