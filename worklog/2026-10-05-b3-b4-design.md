# 2026-10-05 — Design: the memtable flush and the index writers off the applier (plan B3, B4)

Written while run 35 ran (box quiet), from the code, so the work can start
the moment the box is free. Numbers are run 34's applier columns
(`docs/reports/2026-10-05-logged-ibd-pair.md`).

## What the applier pays that is not apply

| column | s | what it is (verified in code) | movable |
|---|---|---|---|
| flush | 1,350 | `mac_flush` inside a put/del: sort the memtable + tombstones, write a run, publish the manifest, reset | yes (B3) |

So B3 is worth ~1.35k s and B4 ~1.16k s of applier time, against a 17.2k s
applier (run 34) that run 35 should already have cut by the put change.

## B3 — the flush off the critical path

Today (`bitcoin_utxo_lsm.asm`): one memtable (`bitcoin_utxo.asm`'s open-
addressing table) with one WAL generation (`bitcoin_utxo_store.asm`); when
`op_count` or the live count crosses its threshold, the put/del that crossed
it runs `mac_flush` inline: radix-sort the live entries and this
generation's tombstones into descriptors, write `utxo_run_%06u.dat` with its
Bloom filter, append the manifest entry (temp + fsync + rename), reset the
memtable, WAL and tombstone list. 113 flushes × ~12 s in run 34. Compaction
already runs in the background through the flush hook
(`utxo_live.c` "compaction in the background": immutable runs in, one run
out), so the publish-by-manifest-rename discipline exists.

Design: **two memtables, one frozen at a time.**
1. `mac_flush` becomes `mac_freeze`: swap in the spare memtable + a fresh
   WAL generation + an empty tombstone list; the full one becomes the
   *frozen* set (memtable, WAL file, tombstones). O(1) for the applier.
2. A flush thread (pthread in the fold process; the compaction runner is the
   model) sorts and writes the frozen set to a run exactly as today, then
   publishes the manifest entry, then releases the frozen memtable as the
   next spare. One frozen set at a time: if the live memtable fills while the
   thread is still writing, the applier **waits** (the old inline cost, only
   under sustained pressure) — never two frozen sets, so recovery stays
   two-generation.
3. Reads: `utxo_lsm_get` consults live memtable → frozen memtable (+ its
   tombstones) → runs. `utxo_lsm_del` of a key in the frozen set writes a
   tombstone in the LIVE generation (the frozen set is immutable); the
   flush's run then carries the PUSH and the live generation's tombstone
   shadows it, which is the existing multi-run rule.
4. Crash: the frozen WAL generation is kept on disk until its run's manifest
   entry is published; on reload, a WAL generation with no run is replayed
   into the memtable as today (two generations instead of one — the loader
   replays the older first). The manifest rename is the commit point, as now.
5. Counters: `total_live` and the flush line (`[bench] flush at block …`)
   are updated by the thread; `csi` (coinstats) folds are per put/del and
   unaffected.

Tests: `test_utxo_catchup_crash_resume` with a kill while a frozen set is
being written (expect: the run is absent, both WAL generations replay,
counts match); `test_lsm_count_drift` across the two memtables;
`test_utxo_lsm` get-through-frozen (a key in the frozen set, a key deleted
after the freeze, a key put after the freeze); a revert-check that pins
"the applier's put returned before the run file existed". The asm follows
the scratch-copy + assemble rule.

Risk: medium. Memory: one more memtable of the configured size (steady
state 64 MB; bulk mode 6 GB blob + 2^25 slots — allocate the spare lazily
and only in bulk mode where the flushes are).

## B4 — the index writers off the applier

Today `dl_new_block_choke` (main.c) runs in the process that applies, after
each connected block: reads the block from the archive once, then
`txit_on_block` (txindex tail), `tsp_on_block` (txospender), the bfilter
adopt/append, the address tail, ZMQ. The coinstats handoff (`csi`, inside
the block line) hands coins to the coinstats worker. Core runs the
equivalents on the validation-interface callback threads; its validation
thread spends 5 s on "index writing" for the whole chain.

Design: **a choke-point ring and one index worker.**
1. The applier publishes (height, archive offset, length) to a shared ring
   (MAP_SHARED, like the coinstats fold ring, `test_coinstats_fold_ring`)
   after the block is committed to the archive; it does NOT read the block.
2. An index worker (forked at catch-up start, same lifetime rules as the
   coinstats worker; `csi_worker_pid` is the model) consumes in height order:
   reads the block once, runs `txit_on_block`, `tsp_on_block`, the bfilter
   append, the address tail. The bfilter needs the spent prevouts' scripts:
   they are in the block's undo run (`undo_log.c`, written with the END
   marker before the choke point), so the worker reads undo for that height
   rather than asking the UTXO set.
3. ZMQ stays with the applier (ordering with `sequence` events; it is
   cheap). The coinstats handoff stays as is.
4. Readiness: `[ready]` already requires `txit_covered()` and `bfi_count()`
   at the tip, so the finish line is unchanged; `getindexinfo` reports the
   worker's covered height (Core's indexes trail the same way).
5. Backpressure: the ring is bounded (1,024 blocks); a full ring blocks the
   applier, which is the inline behaviour and only happens if the worker is
   slower than apply — it is not (1.16k s of work against 17k s).

Tests: `test_index_trail` extended with the worker; a 1,000-block regtest
chain where the worker's txindex/bfilter equal the inline build's
byte-for-byte; a kill of the worker mid-stream and its restart resuming at
the covered height (the existing idempotent-by-height rule); the
revert-check that pins "the applier's choke point no longer reads the
block".

Risk: medium-low; the pieces (fold ring, worker lifetime, idempotent
writers) all exist.

## Order
B4 first (smaller blast radius, all C), then B3 (asm, two-generation
recovery). Each on its own branch, each gated, each measured on the
loopback replay before a mainnet run.

## 2026-10-06 — B3 revisited against the memtable's real shape

Two facts the design above did not have:
- the memtable is a **shared file mapping** (`utxo_lsm_blob.map` 6 GB +
  `table.map` 1.6 GB in bulk mode; the B8 diagnosis found the serve process
  faulting them in after IBD end), so a forked child sees the parent's live
  writes, not a snapshot;
- `utxo_del` is **backward-shift** deletion (no tombstone slots): a delete
  moves later entries of the probe chain into the gap, so any per-slot
  "frozen" marking is invalidated by a concurrent delete.

So neither "fork and let the child flush its snapshot" nor "a flush thread
over a frozen second memtable" fits as written. The shape that does:

1. **Generation in the slot.** The slot's unused pad word (+44, written
   together with the index at +40 as ONE qword store, so a reader never
   sees an index without its generation) carries the generation the entry
   was put in. A freeze increments the live generation: O(1), no scan.
2. **Freeze = fork + WAL rotation.** `mac_flush` becomes: rotate the WAL
   to a new generation file, bump the generation, fork. The child runs
   today's flush walk over the shared table but writes only entries with
   generation ≤ frozen (and this generation's tombstones), publishes the
   run through the existing defer-publish/adopt path the compaction child
   uses, and exits. One child at a time; a freeze while one lives waits
   for it (the inline cost, only under sustained pressure).
3. **While a child lives, the parent never moves a slot.** Puts go to
   empty slots as before (new generation). Dels mark the slot dead (a flag
   in the same pad word) instead of shifting; a del of a FROZEN entry also
   appends a tombstone to the live generation, because the child's run
   will carry that coin and the tombstone must shadow it (the multi-run
   rule). `utxo_get` skips dead slots and keeps probing; `utxo_put` of a
   key whose slot is dead keeps probing to an empty slot (BIP30's two
   duplicate coinbases are the only case).
4. **After the child exits: the sweep.** The parent rebuilds the table
   from the entries of the live generation that are not dead (a few
   hundred thousand re-inserts), compacts their blob records to the start
   of the blob, resets fill, drops the frozen generation's tombstones and
   WAL file, and adopts the child's manifest. Reads between the child's
   publish and the adopt still see the frozen entries in the memtable, so
   nothing is missing at any instant.
5. **Recovery.** Two WAL generations may exist; the loader replays the
   older first and drops it if its run is already in the manifest -- the
   same two-generation rule the first design needed.

Cost model: the fork of an 8 GB mapping is page-table work (~2M PTEs, tens
of ms, ~109 times a sync); the parent's COW is nil (shared mapping). Gain:
the ~1,360 s of inline flush (run 38) leaves the applier's wall; the
applier would sit at ~12,000 thread-seconds against Core's 13,909.
Where it lives: `bitcoin_utxo.asm` (put/get/del + the generation and dead
bits), `bitcoin_utxo_lsm.asm` (mac_flush's walk filtered by generation,
the freeze), `bitcoin_utxo_store.asm` (WAL generations), `utxo_live.c`
(fork/reap/sweep/adopt, the hook). Tests as listed above, plus: a del of a
frozen key during a child's flush is a tombstone in the live generation; a
put during a flush lands in the new generation and survives the sweep; a
kill of the child mid-write leaves both WAL generations replayable.
Order: after run 39 and the Core rerun with the sampler (both pure box
time); write the asm against the scratch-copy rule while they run.

## 2026-10-06 — B3 as built (branch perf/2026-10-06-b3-async-flush)

The 10-06 addendum above was over-built. Both of its facts hold (shared
mapping, backward-shift deletes), but neither forces per-slot generations
once the frozen set is a **copy** that nobody writes:

1. **Freeze = copy + swap, in the applier** (`utxo_lsm_freeze`, asm): the
   live table (header + slots, 1.6 GB at 2^25) and the blob's used prefix
   are `rep movsb`'d into a private anonymous copy sized like the live one
   (`lst+168`); this generation's tombstone list and hash set swap with a
   spare pair; `next_gen`/`next_run_no` are reserved into `fz_gen`/
   `fz_run_no`; `fz_wal_end = log_len` (after a WAL drain); `fz_active=1`;
   the live table is cleared. Sub-second. The compaction gate runs first,
   as in `mac_flush`.
2. **The writer is a forked child** (`utxo_live.c` `fz_hook`): it runs
   `utxo_lsm_build_run` -- the middle of the old `mac_flush`, extracted and
   parametrized by (memtable, tombstone list, gen, run_no) -- on the copy
   and exits 0 / 3 (nothing) / 2. The parent's reads consult the copy
   between the live generation and the runs (`utxo_lsm_get`: live hit →
   live tombstone → frozen hit (script copied to the per-thread scratch,
   the run-hit contract) → frozen tombstone → runs). A del of a frozen key
   is a live-generation tombstone, which already shadows the run the
   child writes (the multi-run rule). One writer at a time: the next
   threshold crossing waits for it.
3. **The WAL is never truncated on this path.** The adopt appends
   `{fz_gen, fz_run_no}` to the manifest, publishes with the persisted
   runs-only count moved by the frozen generation's net (`total_live -
   persisted` at the freeze), then retires the generation's bytes: a
   `utxo.idx` checkpoint `{log_off = fz_wal_end, n = 0}` (tmp + fsync +
   rename; `utxo_store_reload` already replays from it) and a punched hole
   over `[previous log_off, fz_wal_end)` (`fallocate`; ext4 on both
   volumes). The live generation's bytes above `fz_wal_end` stay put. The
   file's logical size grows for the life of the store (sparse).
4. **Recovery** needs no new reader: a crash before the adopt leaves the
   generation in the WAL from `log_off` (replayed as today) and its run an
   orphan (the boot sweep); between the publish and the idx write the
   generation replays over its run (duplicate puts; the reload's recount
   corrects the count). The combined replay of a frozen + live generation
   fits the bulk memtable (the live one is seconds of blocks when the
   writer is alive).
5. **Two reload defects found on the way**, both fixed in the asm: the
   reload's tombstone-rebuild pass scanned the WAL from byte 0 regardless
   of the checkpoint offset (zeros in a retired range would have ended it
   and dropped every tombstone); and `mac_flush`'s reset truncated the WAL
   without emptying `utxo.idx` (a stale `log_off` would have skipped the
   records appended below it). The sync path (`bmc.asyncflush=0`,
   build_utxo, the tools) keeps `mac_flush`, now a hook/drain/cap-check +
   `mac_build_run` + publish + reset.
6. Failures: a writer that dies is replaced by an inline build from the
   same copy; a failed publish/adopt sets a fatal flag the next threshold
   crossing returns as -1 (the apply halts, as a flush error always did)
   while reads stay right through the copy. Shutdown waits up to 30 s for
   the writer, then kills it (the generation replays).

Cost model as built: the applier pays the copy (~2-3 GB at memcpy speed,
plus the 1 GB tombstone-hash reset it already paid) ≈ 0.3-0.6 s per flush
instead of ~12 s; memory +1.6 GB (the copy's table, resident after the
first freeze) + the blob prefix + a second tombstone list (touched as
used). Tests: `tests/test_utxo_async_flush` (freeze keeps reads right;
reload pass from the checkpoint; crash before the adopt; the hook at the
crossing; a second freeze refused), each revert-checked against a variant
of the module; the catch-up tests with tiny thresholds (`test_lsm_count_
drift`, `test_utxo_catchup_*`) now exercise the forked writer.
