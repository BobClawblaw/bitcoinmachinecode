# 2026-09-29 — the A/B's network settings, matched to Core

The Core v31.1 rerun on the repaired link was still in IBD at 01:00Z
(892,181 after 8 h 55 m); the run 30 report took its 850,000 row (#343)
and waits for the end. Then the operator asked whether we download with
16 peers where Core uses 8, and then that the two nodes' default network
connection settings match so the pair is a fair A/B.

## What the comparison found

Neither number was right. Run 30 downloaded from 8 peers
(`bmc.catchupworkers=8`, the harness default since run 27) beside 4 idle
legs; the 16 was run 19. Core's download set is not 8 either: during IBD
it fetches from every outbound peer that can serve blocks — the 8
full-relay **and** the 2 block-relay-only (`fPreferredDownload`) — 16 in
flight each inside a 1,024-block window. The 2026-09-10 note and the
divergences register had read `MAX_OUTBOUND_FULL_RELAY_CONNECTIONS` and
stopped.

The connection budget itself already matched (200, 8 + 2 + 1, inbound by
subtraction, the timeouts, the feeler interval). Three download settings
did not, each in Core's favour: 8 download peers against 10, a 4,096-block
window against 1,024, and idle legs held beside the workers where Core's
download peers are its whole outbound set.

## What run 30's own lines say

The `[dlc] ==` status lines settle the report's open question. The lag
between blocks stored and the applied tip sat at 3,500–4,100 from minute
eleven to the end: the download waited at the 4,096 window's edge on the
apply for the whole sync. On the repaired link both nodes are apply-bound,
and the flat 55–59% margin at every height is the apply rate — the
download-strategy candidate in the first draft is withdrawn, and the
report says so.

## What landed (PR #344, `deploy-20260929a`)

- `bmc.catchupworkers` derived as `bmc.maxoutbound + bmc.blockrelayonly`
  (10) unless set; the window is Core's 1,024; while the tip is older than
  `maxtipage` the idle legs are closed, named, before the parallel download
  and re-dialled after. Revert-checked on both rule tests; the leg rule's
  proof is run 31's log.
- The harness no longer writes the worker key; the sample config, the
  register, the compat rows, the fairness table and the old note carry
  the correction.

## The Core rerun did not finish

At 01:40:53Z Core's log says `cannot create directories: Read-only file
system [/mnt/nvme8tb/bench/core31/blocks]`, fatal, `Shutdown done` at
01:41:34Z, height 924,616 after 9 h 38 m 24 s. The NVMe was never
read-only: the journal shows a ClusterMan VM-test session (another session
on this box) running `mount -o ro /dev/loop16p1 /mnt` and `umount /mnt` in
that same second. A mount on `/mnt` shadows everything under it, so for
that second Core's datadir path resolved into a read-only VM image. The
900,000 row (Core 9:05:13, bmc 4:11:32, 53% ahead) is in; the end row
never will be from this run. The report says so, the finisher is still
waiting for a line that will not come, and the Core unit stays down
(`Restart=no`; its `ExecStartPre` refuses a non-empty datadir, so a rerun
is the operator's: move `core31` aside first). Rule for the box: nothing
mounts on `/mnt` while a datadir lives under it.

## The even comparison, line by line (PR #347)

The operator's standard for the next pair: bmc's defaults equal Core's,
the bench configs differ only in ports, peer selection stays bmc's. Every
sync-relevant setting was read from Core v31.1's source against
`node_config.c`; the table is in `docs/devlog/BENCHMARKS.md`, "The even
comparison". Three more moved: the `dbcache` default 1024 → 450 MiB (no
Core release defaults to 1024); tx announcements are ignored while the
daemon is in IBD, as Core's are (run 30 fetched and rejected every one on
its idle legs); and the script-thread count is said at boot — it was
already Core's 16 (the 15-worker cap has been in `par_script_threads`
since 09-06; the morning's note that bmc used 32 was wrong). The harness
defaults are now the even ones: `NICE=0`, `/srv/nvme8tb`, and `PARITY=1`
writing the three indexes, `maxconnections=48` and Core's four ZMQ topics.
Not matched, and said so: Core's block-file XOR, its 16-thread cap, bmc's
40-block `getdata`. The end row is defined as time to the same height from
both logs, because Core's IBD-exit line fires up to a day of blocks early.
