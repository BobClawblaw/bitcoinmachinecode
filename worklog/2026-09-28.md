## Three things worth more than their rows

**A benchmark row is a claim about two loops.** The first MuHash finalize
number said "1.18× ahead of Core". Splitting both sides showed the inverse
level (23.0 µs in Core's own library, 22.8–24.0 here — the same C algorithm)
and the whole margin in the row's shape: Core's iteration also divides the
digest back in. The same look found the posted "7.7× faster multiply"
comparing one multiply of ours with Core's `*=`, which runs two. Both are
corrected in the docs and the 09-27 report carries a dated correction. The
rule since: read Core's loop down to the primitives before pairing a row,
and decompose both sides before claiming a margin.

**The ElligatorSwift encoder was biased.** It tried the eight branches of
the reverse map in a fixed order and returned the first family's `t`
whenever that family had one — so the 64 bytes on the wire were not uniform
over the valid encodings, which is the property ElligatorSwift exists for.
libsecp256k1 draws the branch from a hash pool per attempt; ours now does
the same. Found because the fixed order was also slow (12.3 branch attempts
per key; the header's "each u succeeds with probability close to 1" was
wrong — 45% do).

**"Convert it to asm" is the wrong question for most of the table.** Where
the C was glue over asm primitives (the ElligatorSwift map, the Jacobi
test), rewriting it would buy under a microsecond; the wins came from
shape (a comb instead of a ladder, a Jacobi symbol instead of a discarded
root). Where the primitive itself was C (ChaCha20) or slow asm (SHA-1's
per-round branch to four f-functions, SHA-512's spills, Base58's byte-wise
`div`), asm — or the right instruction set — was the whole answer.

## Harness lessons, the expensive kind

- A test that computed its reference with one call and its candidate with
  random pieces "failed" correct code: a ChaCha20 call consumes whole
  blocks, so the split changes the stream. Replay the same pieces on both.
- A "passing" test after a `-Werror` failure ran the previous binary
  (twice today). Delete the binary before the rebuild when the outcome
  matters.
- Three mutations were invisible by construction (a sigma word the AVX2
  routine never reads from the state; a group count whose leftover block
  is recomputed correctly; a NEGINV table entry that only costs rounds).
  A revert-check that passes is a claim to investigate, not a test gap to
  assume.
- The Makefile's link check reads prerequisites, not recipes; adding an
  object to 30 rules by script took four passes (a compile-only recipe, two
  doubled lists, the header/recipe split). `make -n` every target and count.

## Left on the table

- ECDH: the w=4 window (33 µs) against libsecp256k1's GLV-split
  `ecmult_const`; `sc_split_lambda` has five conditional branches, so a
  constant-time split is its own piece of work.
- Single-block ChaCha20 (64-byte packets): 0.94 vs Core's 0.77 ns/B — a
  dependent chain either way; a scalar asm block would reach ~0.83.
- The other k·G callers of the 52 µs ladder (bip340_sign, wallet_core,
  bip32_ckdpub, bitcoin_keys.asm) can take the 9 µs comb, each with its own
  gate.
- SHA-256 over a megabyte, 1.25× behind Core's SHA-NI path; the merkle
  root 1.2×; GCS construct 4.1× (a row whose two sides do different work).

Not landed: a two-lane SHA-NI block (exact on 100,000 pairs) ran no faster
than two one-way calls — the out-of-order core already overlaps independent
`sha256_block` calls — so the SHA-256d and merkle rows keep their ~10%.
Not written: a register-resident squaring chain for `fe_pow_sqrt` (the
compressed-pubkey square root that is most of the script rows' 1.1×): the
chain is latency-bound at 7.5 ns a squaring, and keeping the value in
registers would not shorten it.

Defects the tests caught in this batch: the GLV routine's CPU probe (`cpuid`)
clobbered rdx — the scalar pointer — before `sc_split_lambda` read it, and the
variants test had never taken the probe path because it forced the scan body
first (it now goes through the probe once); a `vmovdqa` on a constant in a
16-aligned `.rodata` faulted in one binary and not another; the SHA-256 test's
vectors were all one block, so a multi-block defect (the byte-swap mask reused
as scratch) passed until two-block and million-`a` vectors and a
scalar-vs-SHA-NI differential were added.
