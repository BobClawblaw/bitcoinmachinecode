## Session (continuous from 08-23): the C→asm conversion campaign — fourteen differential-proven twins, and the three bug classes the differentials caught

### Why this campaign exists

The project's claim is 100% AI-generated **machine code**, and `daemon/` plus
the script-verification layer were ~16,100 lines of C — a third of the
codebase. The honest description was "all consensus *primitives* in assembly,
orchestration in C". Every slice below closes part of that gap.

**The method, unchanged for every slice:** extract a testable seam in the C if
one is needed → write the asm twin → drive both over identical inputs and
compare *everything written*, not just return codes → benchmark → optimise to
parity → merge. **The C stays in the tree as the differential oracle and the
daemon keeps running it**; nothing here is deployed yet. The swap happens after
a replay soak, as its own change.

### 02:53 — slice 11, and the bug that justifies the whole method

- [x] `b70356a` `bitcoin_checksig.asm`. It assembled, passed
      `callee-saved-check` (406 functions), and **matched the C on every
      rejection case**. It failed only the *accept* cases, and only in the
      final stack bytes — `sv_run_v`'s ok/err and the stack depth matched,
      because `OP_CHECKSIG` pushes false rather than failing the script.
- [x] Root cause: **`qy[4]` at `-0xf8` overlapped `zl[4]` at `-0xf0` by 24 of
      32 bytes**, so `pubkey_parse` clobbered the message hash and
      `ecdsa_verify` **rejected every valid signature**. Same class as incident
      #31, and again invisible to both static auditors: they check save-area
      aliasing and push/pop balance, not whether two of a function's *own*
      locals overlap.
- [x] Two rules recorded: **an accept case is not optional in a crypto
      differential** (every reject-only comparison is weaker than it looks),
      and **overlapping locals is a third question nothing in the tree asks
      statically** — filed as a candidate check, mechanically decidable from
      the frame-map comments this codebase already writes.

      costumes — a layout or ABI detail typed from memory instead of
      measured:**
      1. `tapctx_t` field **order** (hash_type sits after `n_in`, not later);
      2. `txview_t` **layout** — not the same as the other file's `swtx_t`
         despite looking similar (`int version`, no `inputs` field). The twin
         segfaulted; then the same wrong struct **in the test** drove the C
         oracle through garbage, so the second crash was in the *oracle*;
      3. the **SysV register/stack boundary** — `h_seq` is the 6th argument, so
         it arrives in `r9`; the twin read `[rbp+16]`, which is the 7th.
- [x] Diagnostic worth keeping: **ASAN clean + systematic wrong values + a
      segfault = a marshaling bug, not a memory bug** — count the argument
      list first. Final: **1,684 cases, 0 mismatches**, comparing aggregates,
      the located spk-at-n_in, the length, the entire preimage buffer, and the
      digest, across 13 hash_types (including the six invalid ones the
      2026-08-22 consensus fix must keep rejecting).
- [x] **Standing rule, applied without exception from here:** no struct
      offset, no field order, no argument position enters assembly until an
      `offsetof` probe has printed it or it has been counted against the SysV
      tables. Three for three today, all caught before the daemon linked
      anything.

### 12:20–14:23 — incident #33: the node was never actually following the chain

- [x] Noticed the tip frozen at 963,775 for **14h26m** while Core moved 80
      blocks ahead, with `peers=8/8` the whole time. Every advance the night
      before had come from a restart's catch-up path; I restarted constantly
      to deploy, so "8/8 + advancing tip" read as keep-up. It was the
      restarts. And `do_outbound_sync` returned SILENTLY on both "exchange
      failed" and "peer had nothing" — the one condition that mattered logged
      nothing.
- [x] `b36c567` root cause: `node_sync_multi` passed `cap=64` to
      `cons_verify`, whose 4th arg is the txid-scratch capacity IN
      TRANSACTIONS. Any block over 64 txs failed validation; tip blocks carry
      thousands. Isolated by driving node_sync_multi against the oracle:
      **ok=0 with cnt=51,727** — it downloaded, validated and STORED 51,727
      blocks, then returned failure, and the caller threw the work away.
      Core's net log named the boundary: a run of ~216-byte blocks, then one
      of 97,994 bytes, then nothing.
- [x] `9fea9ad` RESOLVED: fixed (scratch to .bss, cap 80,000), and verified
      on live data — followed two consecutive blocks with no restart,
      `sync ok=1 new=1`, including one with **tx=3923**. Added `sync_fail_code`
      (1–9) naming which `.fail` exit was taken. It looked unfixed for half an
      hour only because no block was mined in that window; waiting for a real
      block instead of concluding from a quiet interval is what settled it.

### 14:35 — incident #34: the same units error, three more times, two of them stack smashes

- [x] `5c2860f`: auditing every `cons_verify` call site found three more.
      `node_drain` reserved 1024 bytes and declared 256 txids (8192): any
      block >32 txs writes ~7 KB past it over saved regs and the return
      address, on peer-supplied data. `node_ibd_blocks` similar. `node_serve_
      loop` passed `(2000*81+8)` — a headers-page BYTE size — into the COUNT
      parameter, and its scratch was `hp_buf`, the live headers page. All
      three now use dedicated .bss scratches. Generalisation recorded: a
      parameter that is a COUNT while the caller owns the BUFFER is a units
      trap; the C callers all get it right structurally with
      `sizeof scratch / 32`, every asm caller wrote a literal.
