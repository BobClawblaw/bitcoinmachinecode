## Session 2: real production incident #1 -- LSM compaction inverted its manifest scan order

The live daemon (`bmc-bitcoind.service`), replaying the real archive with
the fixes above deployed, hit a genuine rejection at real mainnet height
184390:
```
REJECT h=184390 tx=1: legacy script verification failed
FATAL: apply_block failed at height 184390 -- stopping catch-up
[dl] utxo_live_catchup FAILED at height 184389 -- attempting in-place recovery
recover: compact manifest_n=2 -> 1 (result=1)
```
User instruction: "Investigate it now -- find the actual script and scope a
fix", then "Root-cause the flush/compact bug now" once the auto-recovery
compaction was found to be a blind, undiagnosed response
(`daemon/main.c` calls `utxo_live_recover()` unconditionally on ANY
`utxo_live_catchup` failure -- it cannot distinguish "manifest full" from
"genuine consensus rejection"; still true after this fix, worth treating any
future FATAL+recovery pair with suspicion over).

- [x] Root-caused by reading `bitcoin_utxo_lsm.asm` directly (not guessing):
      `utxo_lsm_get`'s disk-run scan walks the manifest array HIGHEST index
      down to 0 (highest = newest). `mac_flush` always appends correctly at
      the true array end. `utxo_lsm_compact` inverted this for the
      merged/oldest run after a partial compaction -- shifted survivors down
      to `[0,K)` FIRST, then appended the merged (oldest) entry AFTER them
      at the highest index, exactly backwards from the scan order. A stale,
      already-deleted key could resolve as live again post-compaction.
- [x] Fix (`e12dcbb`, `asm/bitcoin_utxo_lsm.asm`): write the merged entry
      first at index 0, shift survivors starting at `dst=1` instead of
      `dst=0`.
- [x] New regression test `tests/test_compact_manifest_order.c`: forces a
      partial compaction with a deleted key's tombstone landing in the
      merged (oldest) batch alongside a genuinely-live survivor. Caught a
      bug in the TEST ITSELF first (the initial `del` didn't trigger its own
      flush, so the tombstone never reached the buggy disk-run-scan code
      path at all -- fixed by adding a "trigger" dummy PUT to force the
      flush). Verified via `git stash` that the corrected test FAILS against
      the pre-fix code with the exact predicted symptom (key resolves live
      with its old value) and PASSES with the fix.
- [x] Full `make -k test` green; worktree -> merge `--ff-only` -> rebuild +
      retest on `main` -> push, standard workflow.
- [x] User approved (`AskUserQuestion`) a clean `archive_drop_utxo_state()`
      rebuild before redeploying, since the bug could have left latent
      corruption in the on-disk manifest from earlier compactions -- the
      block archive itself was untouched. Redeployed on the fresh state.

## Session 3: real production incident #2 -- dangling pointer into the byte pool

Redeployed daemon hit the SAME height-184390 rejection again on a
completely fresh, post-fix UTXO state -- proving incident #1, while real,
was not the sole cause of this symptom. Investigated on my own initiative
(no new explicit user request), consistent with the standing root-cause
mandate above -- stopped the daemon and moved to isolated reproduction.

- [x] Built a read-only reproduction: symlinked the real `blk*.dat`/
      `index.dat` files (read-only) into a throwaway scratchpad directory,
      ran the SAME `utxo_live_init`/`utxo_live_catchup` the real daemon
      uses against a fresh UTXO state there -- never touching the live
      daemon's own data.
- [x] Three rounds of targeted debug instrumentation (temporary, on `main`,
      reverted after use -- never committed) localized the bug precisely: a
      `[DEBUG-RESOLVE]`/`[DEBUG-RESOLVE2]` double-read at Phase 1 resolve
      time proved the prevout scriptPubKey was resolved CORRECTLY and
      stably; a `[DEBUG]` print at verify time (`txvb_verify_one`) proved
      the SAME input's script bytes were CORRUPTED by the time verification
      ran -- divergence isolated to inside/around `bytepool_alloc`.
- [x] Root cause: `bytepool_alloc` (introduced hours earlier, see Session 1
      above) returned a RAW POINTER into its own `realloc()`-backed buffer.
      A later input's allocation in the SAME block's Phase 1 resolve loop
      could trigger a `realloc()` that relocated the buffer, silently
      dangling every pointer already handed to EARLIER inputs in that loop.
      Non-deterministic across process runs (whether `realloc` relocates
      depends on that process's own heap layout), matching why it reproduced
      inconsistently between attempts.
- [x] Fix (`4ec089c`, `daemon/tx_verify.c`): `txvb_in_t.spk` -> `spk_off`, a
      stable byte OFFSET into `g_spk_pool` (now file-scope so both
      `txvb_verify_one` and the taproot pass can resolve it), converted to
      an address only after Phase 1 has finished growing the pool for that
      block. An offset survives relocation; a raw pointer captured
      mid-growth does not.
- [x] New regression test `tests/test_tx_verify_bytepool_realloc.c`: mines
      10 blocks each with a single ~9000-byte legacy coinbase output script
      (via chained data-pushes ending in OP_1, staying under both
      `TXV_SPK_CAP`=10000 and the interpreter's 520-byte-per-push /
      201-non-push-op limits), then spends all 10 in one block -- ~90000
      bytes total, comfortably past the pool's 65536-byte initial capacity,
      forcing `bytepool_alloc`'s `realloc()` to fire mid-loop after several
      earlier inputs are already resolved. Verified via `git stash` that it
      reproduces the EXACT production failure signature
      (`REJECT h=130 tx=1: legacy script verification failed`) against the
      pre-fix code and passes cleanly with the fix.
- [x] Full `make -k test`: 87/87 test binaries green on both the fix
      worktree and `main` after merge (`--ff-only`); pushed.
- [x] Before redeploying, found the on-disk UTXO state in an inconsistent
      condition unrelated to either bug: `utxo_applied_height.dat` was
      missing (an earlier SIGKILL during debugging) while undo logs past
      height ~203000 remained on disk -- resuming as-is risked silently
      double-applying blocks against a UTXO set that already reflected
      them. User approved (`AskUserQuestion`) another clean
      `archive_drop_utxo_state()` rebuild; confirmed with the user
      (`AskUserQuestion`) before the actual restart.
- [x] Redeployed `bmc-bitcoind.service` on the fresh state. Confirmed live
      past height 184390 (reached ~200000 cleanly within minutes, no
      rejections) during a full from-scratch archive replay that continues
      unattended overnight, per explicit user instruction ("reindexing from
      the start is fine as we're still in active development" -- fix and
      redeploy autonomously if anything comes up).
