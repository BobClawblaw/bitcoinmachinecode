## incident: production mempool froze at exactly 4096 (00:00–01:00)

- [x] **Root cause:** `tx_accept`'s shared policy state (`mempool_cfg.c`) was
      sized to a fixed 4096 entries — the pool stopped accepting at exactly
      4096 with ~1.2 MB of a 300 MB blob used. `unsigned long pn = slots`
      (was `4096`) sizes it to the pool's real slot capacity (~216 MB for 1M
      slots). Hotfix `70a754a`, deployed immediately as
      `bitcoind.deploy-20260827o-hotfix`.

## Core-style mempool management (01:00–01:30)

- [x] The freeze exposed a design gap: the pool **rejected** new txs when full
      instead of **evicting** cheap ones. Rebuilt it Core's way
      (`c4e908c` → `be85835`, deploy **`p`**):
- [x] **TrimToSize eviction** (`bitcoin_mempool_policy.c`): on a full pool,
      evict lowest-feerate LEAF txs (leaf = `desc_cnt==1`, Core's
      self-inclusive convention) until the incoming tx fits, never evicting
      one paying ≥ incoming. Divergence stated: individual-leaf, not
      descendant-package, eviction.
- [x] **blob compaction** (`daemon/mempool_compact.c`): the pool's
      bump-allocator never reclaimed freed bytes, so eviction freed a slot but
      no space — compaction slides live regions down (O(n log n)) before each
      store retry.
- [x] **dynamic `mempoolminfee`** = last evicted feerate + incrementalrelayfee;
      txs below it rejected up front; `getmempoolinfo` reports max(relay,
      floor). (Floor moved off the accepted-bytes accumulator offset — a
      collision found in test.)
- [x] **config-wired** (defaults == Core): `minrelaytxfee`,
      `incrementalrelayfee`, `limitancestorcount`/`size`,
      `limitdescendantcount`/`size`, `mempoolfullrbf`. Boot logs `[config] mpol`.
- [x] tests/test_mempool_evict + full suite green (186). Live on deploy `p`:
      `getmempoolinfo` reports the dynamic floor; `[config] mpol` confirmed.
