# 2026-09-03

## 00:20-01:40 UTC -- our own transactions now announce the way Core's do

Asked whether disabling private broadcast left the node "broadcasting like
Core does on clearnet", the honest answer turned out to be no, and worse
than Core rather than equal to it. Two things gave the origin away.

Transactions this node originated went out as an unsolicited `tx` message.
That is not what a relaying node sends: anything merely passing one along
announces the txid and waits for `getdata`, so a peer handed the bytes
unprompted can tell it is talking to the source. And they went to every leg
in the same instant, which is the other half of the same tell -- a relayer's
announcements have already been smeared by the hop that reached it, so
simultaneous fan-out says the transaction started here. Core spreads its
announcements over an independent Poisson timer per peer for exactly this
reason.

The comment in tx_submit.c justified the push by saying the worker runs no
serve loop to answer a follow-up getdata. That had quietly stopped being
true: tx_relay.c's drain has answered getdata(MSG_TX/MSG_WITNESS_TX) from
the shared mempool since 2026-08-26, which is how relay-received
transactions already propagate. Own transactions were the only ones still
working around it, and the gap had never been written down.

They now go through the same announce queue, which gained a per-leg timer to
match Core: each leg draws its own next-send time from an exponential with
mean 2 s (m_next_inv_send_time, OUTBOUND_INVENTORY_BROADCAST_INTERVAL),
armed the moment the leg appears so the first announcement of a session is
staggered too. Nothing in this build links libm, so the deviate is computed
from the bit pattern instead: for uniform 64-bit r, -ln(r/2^64) is
(clz+1)*ln2 minus the log of the normalised mantissa, taken from a 65-entry
table with linear interpolation. The test holds it to the distribution
rather than the mean alone -- 200,000 draws gave mean 1998.3 ms against
2000, P(>m) 0.3678 against 1/e, P(>2m) 0.1352 against 1/e^2, and the gate
reproduced it on a fresh seed at 1999.3 / 0.3682 / 0.1352.

One defect surfaced only because the test went looking for it. A descriptor
is recycled the instant a leg closes, so a re-dialled leg was picking up the
previous peer's slot -- including a timer already due. It would have been
announced to immediately, defeating the stagger precisely when legs churn
most, and it would have inherited txids queued for someone else.
txrelay_leg_reset is called from all three sites that hand a leg a fresh
descriptor, and txrelay_announce independently re-arms any descriptor absent
on the previous call, so a dial site added later and left unwired cannot
degrade the stagger silently.

Gate: 321 test invocations, 0 failures, in the worktree and again on main
after the ff-only merge. test_tx_submit now asserts the peer socket stays
SILENT on accept, which is the whole point; test_tx_relay grew case 8b for
the timer. Deployed as `ar` 01:38; the node is at the oracle's height and
relaying 200 transactions a minute through the new announce path with no
FATAL lines.

GATE FLAKE worth knowing: the first run failed at `link-check` with "81
rule(s) link a file whose symbols nothing in the rule defines". Nothing was
wrong. The link audit compiles all ~644 files in parallel to read their
symbols, cached by mtime, and in a COLD worktree the largest ones
(daemon/main.c, rpc_node.c, rpc_chain.c) hit its per-file compile timeout;
their symbols then look missing everywhere. It passes on a second run once
the cache is warm. Because link-check gates the `test` target, the whole
suite silently did not run -- the log had zero test output and it would be
easy to read that as "nothing failed".

NOT proven live: the own-transaction branch specifically. Exercising it end
to end means broadcasting a real mainnet transaction with real funds, which
is the user's call, not a thing to do unasked. The staggered announce path
itself IS under continuous real load, since every relayed transaction now
takes it.

## 01:50-02:20 UTC -- TRUC sibling eviction (task 1 of the queued three)

A second TRUC child was refused outright. It spends a different output of the
parent, so it double-spends nothing and ordinary RBF cannot reach it; only the
TRUC descendant rule saw it at all, and that rule said no. Core does not simply
refuse: SingleTRUCChecks hands the existing child back alongside the error and
MemPoolAccept adds it to the to-be-replaced set, letting the ordinary
replacement arithmetic decide. That is the whole point of the topology. A
parent's fee is meant to be raisable through its one child, so if that child
sits at a low feerate, without sibling eviction the only party who can rescue
the parent is whoever owns the child -- the pin TRUC exists to abolish.

Implemented to Core's shape, which is deliberately narrow: the parent must have
exactly itself and one child, and that child exactly itself and the parent,
because anything wider needs a rule for choosing WHICH descendant dies and Core
has none. Reorgs leave wider shapes and those are still refused, as are package
contexts. removed_fees was hoisted out of the conflict block so an eviction
landing on top of existing conflicts is priced over the whole to-be-replaced
set, as Core prices it. BIP125 signalling is not asked of the sibling; Core
skips it and says why.

The test checks both outcomes, because having only the refusal proves nothing.
An equal-paying challenger is refused ON FEE rather than on topology -- a
TRUC-violation there would mean the eviction path never ran -- one clearing the
sibling's fee plus its own incremental relay cost is accepted and the sibling
leaves the pool, and a third child must then beat the new incumbent.

STATED SHORTFALL: no regtest differential against real Core. These rules are
read from Core's source, not observed from its running behaviour, which is
below the bar the surrounding package/TRUC work was held to. Recorded in
FEATURE_GAPS.md rather than glossed.

## The gate could not run in a fresh worktree, and said so badly

Setting this up exposed a real build bug. link-check reads symbols from every
.c AND every .o a rule names, so it needs a BUILT tree -- but it sat first in
the test target's prerequisite list, before anything was compiled. In a fresh
worktree version_gen.h does not exist yet (generated, gitignored), so
daemon/main.c, rpc_node.c, rpc_chain.c and the tests including them would not
compile and were silently skipped; a skipped file's symbols are unknown, so
~100 rules looked as though nothing defined what they use. Generating the
header cut it to 5, all of them rules naming .o files not yet built.

link-check now depends on version_gen.h and runs LAST. What made it worth
fixing rather than re-running: link-check gates `test`, so when it failed
make -k built everything and ran NO tests at all, and the log -- no test
output, no failures, no summary -- read exactly like a clean build. 0 test
invocations on the failing pass against 321 on the re-run.

Worth recording that my first diagnosis of this was wrong. I blamed a parallel
compile timing out on a cold cache, on the evidence that it passed the second
time. It did pass the second time, for a different reason. Compiling the file
by hand gave the actual error in one line.

Gate 321/0 in the worktree and again on main. Deployed as `as` 02:17; node at
the oracle's height, no FATAL lines.
