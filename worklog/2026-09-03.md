## 00:20-01:40 UTC -- our own transactions now announce the way Core's do

Asked whether disabling private broadcast left the node "broadcasting like
Core does on clearnet", the honest answer turned out to be no, and worse
than Core rather than equal to it. Two things gave the origin away.

Transactions this node originated went out as an unsolicited `tx` message.
That is not what a relaying node sends: anything merely passing one along
announces the txid and waits for `getdata`, so a peer handed the bytes
unprompted can tell it is talking to the source. And they went to every leg
in the same instant, which is the other half of the same tell -- a relayer's
announcements have already been smeared by the hop that reached it, so
simultaneous fan-out says the transaction started here. Core spreads its
announcements over an independent Poisson timer per peer for exactly this
reason.

The comment in tx_submit.c justified the push by saying the worker runs no
serve loop to answer a follow-up getdata. That had quietly stopped being
true: tx_relay.c's drain has answered getdata(MSG_TX/MSG_WITNESS_TX) from
the shared mempool since 2026-08-26, which is how relay-received
transactions already propagate. Own transactions were the only ones still
working around it, and the gap had never been written down.

They now go through the same announce queue, which gained a per-leg timer to
match Core: each leg draws its own next-send time from an exponential with
mean 2 s (m_next_inv_send_time, OUTBOUND_INVENTORY_BROADCAST_INTERVAL),
armed the moment the leg appears so the first announcement of a session is
staggered too. Nothing in this build links libm, so the deviate is computed
from the bit pattern instead: for uniform 64-bit r, -ln(r/2^64) is
(clz+1)*ln2 minus the log of the normalised mantissa, taken from a 65-entry
table with linear interpolation. The test holds it to the distribution
rather than the mean alone -- 200,000 draws gave mean 1998.3 ms against
2000, P(>m) 0.3678 against 1/e, P(>2m) 0.1352 against 1/e^2, and the gate
reproduced it on a fresh seed at 1999.3 / 0.3682 / 0.1352.

One defect surfaced only because the test went looking for it. A descriptor
is recycled the instant a leg closes, so a re-dialled leg was picking up the
previous peer's slot -- including a timer already due. It would have been
announced to immediately, defeating the stagger precisely when legs churn
most, and it would have inherited txids queued for someone else.
txrelay_leg_reset is called from all three sites that hand a leg a fresh
descriptor, and txrelay_announce independently re-arms any descriptor absent
on the previous call, so a dial site added later and left unwired cannot
degrade the stagger silently.

Gate: 321 test invocations, 0 failures, in the worktree and again on main
after the ff-only merge. test_tx_submit now asserts the peer socket stays
SILENT on accept, which is the whole point; test_tx_relay grew case 8b for
the timer. Deployed as `ar` 01:38; the node is at the oracle's height and
relaying 200 transactions a minute through the new announce path with no
FATAL lines.

GATE FLAKE worth knowing: the first run failed at `link-check` with "81
rule(s) link a file whose symbols nothing in the rule defines". Nothing was
wrong. The link audit compiles all ~644 files in parallel to read their
symbols, cached by mtime, and in a COLD worktree the largest ones
(daemon/main.c, rpc_node.c, rpc_chain.c) hit its per-file compile timeout;
their symbols then look missing everywhere. It passes on a second run once
the cache is warm. Because link-check gates the `test` target, the whole
suite silently did not run -- the log had zero test output and it would be
easy to read that as "nothing failed".

NOT proven live: the own-transaction branch specifically. Exercising it end
to end means broadcasting a real mainnet transaction with real funds, which
is the user's call, not a thing to do unasked. The staggered announce path
itself IS under continuous real load, since every relayed transaction now
takes it.

## 01:50-02:20 UTC -- TRUC sibling eviction (task 1 of the queued three)

A second TRUC child was refused outright. It spends a different output of the
parent, so it double-spends nothing and ordinary RBF cannot reach it; only the
TRUC descendant rule saw it at all, and that rule said no. Core does not simply
refuse: SingleTRUCChecks hands the existing child back alongside the error and
MemPoolAccept adds it to the to-be-replaced set, letting the ordinary
replacement arithmetic decide. That is the whole point of the topology. A
parent's fee is meant to be raisable through its one child, so if that child
sits at a low feerate, without sibling eviction the only party who can rescue
the parent is whoever owns the child -- the pin TRUC exists to abolish.

Implemented to Core's shape, which is deliberately narrow: the parent must have
exactly itself and one child, and that child exactly itself and the parent,
because anything wider needs a rule for choosing WHICH descendant dies and Core
has none. Reorgs leave wider shapes and those are still refused, as are package
contexts. removed_fees was hoisted out of the conflict block so an eviction
landing on top of existing conflicts is priced over the whole to-be-replaced
set, as Core prices it. BIP125 signalling is not asked of the sibling; Core
skips it and says why.

The test checks both outcomes, because having only the refusal proves nothing.
An equal-paying challenger is refused ON FEE rather than on topology -- a
TRUC-violation there would mean the eviction path never ran -- one clearing the
sibling's fee plus its own incremental relay cost is accepted and the sibling
leaves the pool, and a third child must then beat the new incumbent.

STATED SHORTFALL: no regtest differential against real Core. These rules are
read from Core's source, not observed from its running behaviour, which is
below the bar the surrounding package/TRUC work was held to. Recorded in
FEATURE_GAPS.md rather than glossed.

## 06:40-07:30 UTC -- bytespersigop (task 2 of the queued three)

FEATURE_GAPS.md called this deliberately not done: vsize came from weight
alone, the sigop cost was recorded after acceptance, and "a half-wired fee
policy is worse than an absent option". Half of that had already stopped being
true. A pending-sigops hook existed, tx_accept.c's prechecks set it from where
the UTXO view is already open, and the two entry fee floors used it. The option
was in exactly the half-wired state the paragraph warned about.

Three things were wrong. The adjustment reached only the fee floors, but Core's
GetTxSize() IS the adjusted figure, so the replacement arithmetic, the ancestor
and descendant byte budgets, the TRUC size caps, eviction, mining and
getmempoolentry all see it -- a sigop-dense transaction paid Core's price to
get in and then occupied a smaller footprint than Core in every limit after.
It is now computed once at the top of mpol_accept and IS the entry's size.

The rounding was Core's formula rearranged. Core takes the max on the weight
scale and rounds once at the end; taking it after dividing rounds the sigop
term down and undercharges a byte whenever sigops*bytespersigop is not a
multiple of 4. That is invisible at the default 20, itself a multiple of 4, so
the test uses a value that is not.

And a rejected transaction left its sigop count parked for the next one. The
count arrives in a global set before the call and was cleared at the fee gate,
with eight rejection paths in between. A sigop-dense transaction rejected on
any of them left its count behind and the next transaction -- a different one,
possibly with no sigops at all -- was priced as though it carried them. Read
and cleared as the function's first act now. The test proves the bug rather
than the fix: against the previous code the follow-up transaction is refused
with "min relay fee not met", which is how it was confirmed.

Worth recording how this first looked green. test_mempool_policy's okv macro
evaluated its condition twice, once for the label and once for the counter, so
a check whose condition had a side effect ran it twice. My
okv(mpool_policy_add(...) == 1) submitted the transaction again, the duplicate
was refused, and the case printed "ok" while quietly incrementing the failure
count -- two failures with nothing marked FAIL anywhere in the output. Found by
instrumenting the counter rather than re-reading the checks. The macro
evaluates once now.

Left unmatched and stated in the doc: package effective-feerate aggregates sum
the plain vsize, so a sigop-dense package member is priced slightly cheaply.
Single-transaction admission, which is what the option is aimed at, is correct.

One gate run failed on test_wallet_txlog's torn-write case. Unrelated to this
change and not reproduced: it passes standalone in both trees, 40 of 40 in a
loop and under concurrent copies, and the next full gate passed 321 of 321.
The underlying hazard is real though -- that test writes to hardcoded /tmp
paths shared by every tree on the box instead of the suite's per-test private
directory. Recorded, not yet fixed.

## 11:50-12:30 UTC -- package feerates aggregate the adjusted vsize (deploy au)

The residue left over from this morning's bytespersigop work. Both aggregate
sites -- submitpackage in main.c and the 1p1c relay path in tx_relay.c --
summed the plain BIP141 vsize handed to them by mpol_package_well_formed's
structural walker. That walker cannot count sigops: they need the UTXO view,
which it does not have. Core aggregates over entry sizes and an entry's size
is the adjusted figure, so a sigop-dense member was priced slightly cheaply
inside a package.

The adjusted figure now comes back out of the dry run. mpool_policy_test
gained a vsize_out beside its existing fee_out, threaded down through
mpol_add_core and up through tx_accept_test_reason. It is published as soon as
the size is known, before any rejection can return, because a member that
fails only on fee still contributes its size to the package total. Both
callers use it and fall back to the walker's figure only for a member rejected
before the policy layer ran, which is never counted in a total anyway.

A per-call out-parameter, deliberately, and not another "last value" global.
The leak fixed a few hours earlier in this same file was exactly a global set
before a call and consumed later. Carrying its fix in a second one would have
repeated the mistake while claiming to close it -- the signature change costs
six call sites and buys correctness by construction.

## 14:15-14:40 UTC -- new targeted mutations: SIGHASH_SINGLE's three answers, and P2WSH's size exemption

Following the oracle restoration, added the new coverage that was actually
asked for: resource-limit and sighash edge cases beyond what already
existed. Both new classes came from reading Core's source and this
project's code side by side, not from guessing at likely shapes.

SIGHASH_SINGLE with no matching output turns out to be three different
rules, not one rule with three implementations. Legacy substitutes the
whole sighash with a constant. BIP143/v0 zero-fills only the hashOutputs
field inside an otherwise ordinary preimage -- a narrower and different
substitution, explicitly excluded from the legacy path by a guard in
SignatureHash itself. Taproot does neither: the sighash cannot be computed
at all, and the spend is unconditionally invalid before a signature is ever
checked. Only the legacy case had a differential before today.

The taproot addition is a regression test for a real, already-fixed
consensus false accept from 2026-08-22 that has carried zero coverage
against Core since the day it landed -- the diagnostic script that found it
no longer exists in the tree, and nothing else names this input shape. The
old code carried BIP143's zero-fill over into taproot verbatim, computing a
signable hash where Core computes none; a hundred and thirty of the nine
hundred and forty-five vectors that caught it were this exact case on real
mainnet transactions. The new test signs with that old, wrong formula on
purpose, not a garbage signature that would fail for an unrelated reason --
confirmed by computing both formulas over identical inputs and checking
they produce different hashes, so the test is known to discriminate rather
than coincide by accident.

The second addition: a P2WSH witnessScript is not bounded by the same
520-byte limit a P2SH redeemScript is, for a structural reason rather than
a deliberate exception. A redeemScript has to arrive as a scriptSig push,
so the generic push-size limit catches it before it is even considered. A
witnessScript instead arrives as the last item of the witness stack, popped
off before Core's "no witness item over 520 bytes" check runs over what
remains -- invisible to that check, bounded only by the ordinary
ten-thousand-byte script-size limit. Confirmed our own implementation
already gets this right, by excluding the popped index from its per-item
size loop, before writing anything -- the value here is checking that
against Core, not against a reading of the file.

A third candidate did not survive contact with the opcode budget. The idea
was to test the witness stack's own item-count ceiling, checked before the
script ever runs, as something distinct from the stack growing during
execution. The reject side was trivial to build. The accept side was not:
consuming anywhere near a thousand pre-existing items down to the one that
must remain costs more opcodes than Bitcoin Script's own two-hundred-and-one
limit allows by any mechanism it has, confirmed by arithmetic before writing
a line of test code. Dropping it felt like the right call -- a test that
cannot be made to discriminate correctly is worse than no test, which is
exactly why this project tracks mislabelled probes as their own category.

One thing attempted and correctly refused: verifying the taproot test's
teeth by temporarily putting the historical bug back into the real source
file. The permission system blocked it, appropriately, as reintroducing a
documented consensus false accept even for a moment. I did not look for a
way around that. Instead I proved the same point safely, in pure Python,
by computing the correct and the buggy sighash formulas over the same
inputs and confirming they differ -- enough to know the test isn't
accidentally vacuous, without touching consensus code at all.

Full run: 79 synthesized cases, up from 74, 96 rule mutations, 7,805
interpreter probes, zero divergences, zero engine failures. Pure Python
change to validation/synth_corpus_diff.py, no daemon or assembly touched,
no gate rebuild needed. Committed and pushed as d8e7279.

## 15:20-16:16 UTC -- the three RPC bugs from the audit, fixed

Fixed all three correctness bugs the earlier re-audit found, in one worktree,
each verified against a real fixture rather than trusting a clean compile.

gettxoutproof used to refuse unconditionally without a block hash, citing
"no txindex" -- true two weeks ago, false since the transaction index
landed. It now resolves the block from the index on the first requested
txid, exactly Core's own order (the index only, never the mempool, since a
proof only makes sense for a confirmed transaction). Built a real synthetic
archive and index in the existing test fixture to prove it: the proof
obtained by txid alone is byte-identical to the one obtained with an
explicit block hash, and the resulting proof round-trips through
verifytxoutproof cleanly.

getnetworkinfo reported every network's proxy as empty and its credential
randomization as off, regardless of what was actually configured, even
though per-connection SOCKS5 randomization is real and running. It now
reports the genuine configured proxy per network, matching Core's own
wiring exactly: randomization applies to the clearnet and onion proxies,
never to the I2P bridge or to CJDNS, neither of which has anything
resembling that concept. Wiring it in surfaced a real linking problem: the
lightweight command-line client links this file but never actually runs the
code path that needed the daemon's configuration state, and adding that
dependency broke its build. Rather than pull a whole configuration parser
into a tool that has no use for one, one narrow accessor function is
exposed as a weak reference, matching a pattern already used elsewhere in
this same file for exactly this situation. Verified live after deploying:
since Tor, I2P, and the generic proxy were switched off on this node
earlier today, the RPC now honestly reports empty everywhere, which is
proof the fix reflects the real configuration rather than a different
hardcoded answer.

getaddressinfo always reported that an address was not the wallet's, was
not watched, was not change, and had no known public key, no matter what
the wallet actually held. It now answers from the same key window the
wallet already searches when listing unspent coins or handling a rescan,
rather than reimplementing that search with a different, possibly
disagreeing limit. A fast match by a short identity gets confirmed by
rebuilding the full output script and comparing it exactly, which matters
most for the newest address type, where that short identity is only a
fragment of a longer value and could otherwise coincide by chance. Verified
against a real, seeded wallet across every address type it supports,
including a legacy address where the real public key now comes back
instead of an empty string, and against a real, unrelated address to
confirm it correctly reports as not the wallet's own.

Full gate green twice, in the worktree and again on main, three hundred and
twenty-one tests each time with nothing failing. Deployed as `av`; the node
sits at the oracle's height with no fatal lines. This closes every item in

## 60,000 cases later: one error-code divergence, and it is not a port bug

Re-ran the interpreter differentials on fresh seeds: **900,000 `fuzz_script_diff`
cases over 3 seeds, 0 mismatches; 60,000 `fuzz_verify_diff` whole-input cases
over 3 seeds, 0 verdict mismatches, 1 code-only mismatch.** Case 10911 of seed
`0x3ee41b08` (tmpl=bare, mut=flip-script-byte): both reject, ours says 24
(`SIG_DER`), Core says 54 (`SIG_FINDANDDELETE`).

Root cause, in one sentence: Core performs `FindAndDelete(scriptCode, sig)` and
its `CONST_SCRIPTCODE` verdict at the TOP of `EvalChecksigPreTapscript`
(interpreter.cpp:330, and the same loop at 1146 for CHECKMULTISIG), *before*
`CheckSignatureEncoding`, whereas ours performs that search inside the C checker
callback (`asm/bitcoin_scriptverify.c:186`), which the interpreter reaches only
after `interp_sig_encoding_ok` and `interp_pubkey_encoding_ok`.

The triggering shape is worth keeping, because it is the kind of thing only a
differential finds: a bare CSV-guarded P2PK `025faf00 b2 75 21<pub> ac` whose
scriptSig pushes the 2-byte value `5faf`. `CSV`/`OP_DROP` leave that value
sitting in the signature slot at `OP_CHECKSIG` -- not a signature, so the spend
must fail -- and it is also a literal three bytes into the very scriptCode being
executed, so Core's strip finds it and answers `SIG_FINDANDDELETE` without ever
looking at the encoding. Same verdict, different rule credited.

Two things I got wrong on the way there, both worth keeping. My first replay
attempted the shim with the fuzz dump's 4th field as the scriptPubKey; that
field is the *prevout list* (`ser_spent`: per-input amount + spk), so the shim
executed a truncated script and both engines said `BAD_OPCODE` -- which looked
like "the mismatch does not reproduce" and nearly ended the investigation there.
And the hand-typed prevout blob in the first draft of the reproducer script was
two bytes short. Both caught only by going back to the harness's own serializer
and parsing the blob properly.

`validation/findanddelete_order_repro.sh` now carries it: exact tx, scriptSig,
prevouts and flags, one line to each engine, exit 1 while the codes differ and
exit 0 once they agree -- so it can be dropped into a regression run the moment
the fix lands instead of being re-derived.

Deliberately NOT fixed on this branch. `asm/bitcoin_interp.asm`'s
`interp_checksig` has the identical order and the search itself is shared C, so
x86 answers `SIG_DER` too: this is a gap this project has with Core, not a
divergence between the two architectures, and changing the ARM interpreter alone
would create exactly the arch drift the port exists to avoid -- with no way to
verify an x86 `.asm` change on an aarch64 box. Written up in `FEATURE_GAPS.md`
with the shape of the fix: only the ERROR arm needs the search (when the
encoding checks pass, the callback's existing `-5` already produces Core's
answer), so it costs nothing on the path every block takes, and it does not
duplicate the strip the callback performs anyway.

## 16:20-17:10 UTC — ARM: SAVE-AREA-ALIAS ported into the AArch64 ABI auditor

The last open item on the port's own TODO ("port the x86 auditor's
SAVE-AREA-ALIAS check") is done: `scripts/abi_callee_saved_audit_a64.py` now
walks each function's frame in entry-sp coordinates and reports a
statically-addressed store that lands on a callee-saved save slot while that
slot is live. Gated by `make -C port/arm64 abi-a64-check` (selftest first),
with `abi-a64-audit` printing findings plus the reason for every frame it could
not follow.

The x86 auditor already had this check; the AArch64 twin did not, and the class
is not hypothetical here — GLV's `TAB[8]` overlapping AUXX/ZR/AI/DGE
(2026-09-01) was found by hand. Three things had to be built before the check
could mean anything on this tree:

* **A frame walk, not a linear pass.** Labels (including `.cc_const:`-style
  local labels and `1f`/`1b` numeric ones), pre/post-index sp moves, `x29`
  anchoring, and both-states exploration where a label is reached at two depths.
* **`.equ`/`.set` resolution.** The port's frame maps are symbolic —
  secp256k1_glv_mul.S is `.equ TAB,0x120 / .equ AUXX,0x320 / ... /
  .equ FRAME,0x6C0` and the stores read `[sp,#TAB]`. Unresolved, those stores
  have no address at all and the check is blind in exactly the frames it exists
  for.
* **Register-held fixed frames.** `cons_verify` is `mov x26,#0x0100 /
  movk x26,#0x0010,lsl #16 / sub sp, sp, x26`: a fixed 1 MiB+256 frame wearing a
  register's clothes. Constants are followed only into registers that move sp,
  and any other write forgets them.

Coverage went 647 → **753 of 759 functions followed**, 0 violations. The 6 left
unmodelled are named with their reason rather than silently skipped: five
`bitcoin_cli` commands whose `LB x9` macro feeds a `sub sp, sp, x9` (macro
bodies are not expanded), and `point_scalar_mul_glv`, whose frame base is `x28`
with an alignment-clamped sp — i.e. the GLV function itself is still outside the
check, and saying so matters because it is the function the check is named
after. Covering it needs offsets as ranges, recorded in TODO.

Five bugs in my own implementation, each caught by a different kind of evidence:

1. `parse_items` skipped every `.`-leading line, so **local labels were not
   labels** and every branch to one looked unresolvable: 91 functions written
   off as "not followed". The coverage line I had just added said 112 of 759,
   which is far too many to be true — the count was the clue, not the code.
2. `extract_functions` cuts a line at its first `;` (a NASM habit) so
   `#48 /* buf at sp+0..31 ; sp stays 16-aligned */` is severed *inside* the
   comment, the paired `/*...*/` regex then matches nothing, and the operand
   text carries the comment — 23 more functions mis-read as dynamic frames.
3. Treating *any* store of a callee-saved register as its save slot made
   `fd_write_all`'s `str x19,[sp,#0]` (storing an fd into a `pollfd` on the
   stack) the save slot, reported the following `strh w1,[sp,#4]` (the struct's
   own `events` field) as clobbering x19, and — worse — dropped the real slot 48
   bytes higher out of the model. First save wins; later stores are data.
4. `1 << 16 - 1 << shift` is not `((1<<16)-1) << shift`: Python binds `-`
   tighter than `<<`, so the `movk` mask was wrong and `store_prune` stayed
   unmodelled until the precedence was made explicit.
5. `norm_reg()` answers only for x19-x30, but sp-adjuster registers are usually
   x9/x14/x26 — needed a normalizer that does not filter, or the constants are
   tracked for registers that never move sp and missed for the ones that do.

**The check was proven to have teeth three ways**, because a check that cannot

## 17:30-19:30 UTC — the SIG_FINDANDDELETE ordering fix, both arches in one commit, deployed as arm-6

The last open consensus-adjacent item on the TODO is closed. Core's
`EvalChecksigPreTapscript` strips the signature from the scriptCode
(`FindAndDelete`) at its TOP -- before `CheckSignatureEncoding` and
`CheckPubKeyEncoding` -- and finding it under `CONST_SCRIPTCODE` is
`SIG_FINDANDDELETE` (interpreter.cpp:330). Ours ran the strip inside the C
checker callback, which the interpreter reaches only AFTER its encoding
checks, so an encoding-invalid signature that also occurs inside its own
scriptCode was answered `SIG_DER` (24) where Core answers `SIG_FINDANDDELETE`
(54). Both reject; the 60,000-case verify differential found it as the single
code-only mismatch of the day, and `validation/findanddelete_order_repro.sh`
reproduced it in one line.

The fix lands on BOTH architectures in one commit (f7d28ce) because the
x86 `interp_checksig` has the identical order and the search is shared C.
The four encoding-error arms of `interp_checksig` funnel through one new
error site that, under `CONST_SCRIPTCODE`, runs the same strip the
CHECKMULTISIG loop already uses (`script_push_encode` + 
`script_find_and_delete` over `[pbegincodehash, pend)`, the
`cms_needle`/`cms_scstrip0` scratch -- free here, CHECKSIG never runs inside
that loop) and answers `-5` when the stripped length comes back shorter than
the source, keeping the encoding error otherwise. An empty signature strips
with the `OP_0` needle exactly as the C checker does on the accept path, and
the scriptCode is capped at 10000 bytes like the checker's own guard, so the
dstcap sentinel is unreachable. Nothing on the accept path moves and it gains
no scan. Two asm-reality notes from the port: AArch64's `cmp` immediate tops
out at 4095, so the 10000 cap goes through a register (`cmp x3,x9`); and the
x86 `-5` must be written as a FULL 64-bit value into the holder register
(`mov r14,-5`, then `mov rax,r14`) -- the ARM file's own comment warns that a
32-bit write zero-extends and the error reads as checksig-TRUE.

**Verified, in the order that could have caught a mistake:**
  * repro: `ours: accept=0 err=54    core: accept=0 err=54` -- exit 0;
  * `fuzz_verify_diff` 3 seeds x 20,000 whole-input cases, INCLUDING the seed
    (0x3ee41b08) that found the divergence: VERDICT-MISMATCHES=0,
    **code-only-mismatches=0** -- the standing divergence is gone;
  * `fuzz_script_diff` 100,000 cases: MISMATCHES=0;
  * `synth_corpus_diff` 79 cases / 96 rule mutations / ZERO DIVERGENCES
    (report regenerated, accept-parity 79/79, mutations 96/96);
  * native sweep round 19: pass 308 / fail 4 env-only / bench-ok 12 / built
    19 / skip 13, build-fail 0 -- and the first round whose printed summary
    is honest after the aed6533 fix (bench-ok 12, no phantom `11 1` rows);
  * x86: `nasm -f elf64 -Werror` assembles the edited interp clean; its
    execution gate runs where main's suite runs.

Two CHECKMULTISIG observations made while implementing, both verdict-safe and
deliberately NOT changed today: the up-front strip loop raises
`SIG_FINDADDDELETE` for ANY on-stack signature found in the scriptCode before
the matching loop, where Core interleaves per-signature (an encoding-invalid
sig 0 preempts a later signature's FAD in Core, not here) -- and that strip
