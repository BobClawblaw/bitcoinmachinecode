# 2026-08-25

## resumefix: close the WAL-vs-checkpoint window (the 963915 resume-REJECT)

Root cause of the 2026-08-24 production failure, now fixed and regression-
locked. The one-block window was already closed (per-block checkpoint + boot
recovery), but three gaps combined into an unrecoverable state:

1. **Drift can be multi-block.** persist_applied_height failure used to warn
   AND CONTINUE ("safe, puts/dels are idempotent" — false since Stage D
   verifies before applying), and the reorg reconnect's checkpoint failure
   also continues. A dead process then leaves a ghost RUN, not one block.
2. **Boot recovery healed only applied+1.**
3. **The killer: apply_block_at blindly undo_discard()ed the height before
   applying** — destroying the one piece of data that could reverse a ghost
   application, right before the fresh apply rejected on the ghost's own
   already-spent inputs. From that moment the state was unrecoverable and the
   DEGRADED retry loop span forever. Production hit exactly this at 963915.

Fix (daemon/utxo_live.c):
- `rollback_unapplied_block()` — shared ghost-rollback helper (tolerant undo
  replay + created-output removal + discard), used by both:
- **the ghost guard in apply_block_at**: an undo file at a height above the
  checkpoint is rolled back, never discarded, before the fresh apply; refuse
  to apply if rollback fails. Every apply is now idempotent — the DEGRADED
  retry loop and reorg re-applies heal instead of corrupting.
- **multi-block boot recovery**: utxo_live_recover_partial_block finds the
  whole contiguous ghost run and rolls it back DESCENDING (disconnect is
  LIFO — the chained-spend case makes the order load-bearing).
- **persist failure now stops catch-up at the block boundary** instead of
  growing an unbounded ghost run on a disk that can't write 12 bytes.

tests/test_utxo_ghost_resume.c (23 checks, in `make test`): a 2-block ghost
run with spends chained ACROSS the ghost blocks, healed through a simulated
restart; the guard healing a re-applied ghost in-process; final state
byte-consistent. **Negative control run against unfixed main: the test
reproduces the production failure exactly** (FATAL apply, catchup -1,
phantom outputs left in the set) — 7 FAILs on old code, 23/23 PASS on new.
Related suites all green: catchup_crash_resume, crash_recovery, checkpoint,
apply_block_rollback, catchup_shutdown, reorg, cross_tx_verify.

## hscapture: getpeerinfo versions — a frame overlap ate every real peer's version payload

`getpeerinfo` (and the `[dl] outbound` log line) showed blank version/subver/
services for every peer. gdb against a live peer produced the smoking gun: the
handshake's cmd buffer contained `"0.4/"` — the tail of `/Prometheus:30.0.4/`.

`node_handshake`'s frame had TWO overlaps of the incident-#11/#31 class:
`plen@-0xd8` sat inside `cmd[8..11]`, and the 128-byte payload buffer at
`-0x140` spanned up to `-0xc1` — placing cmd at payload offset 96. Any peer
version payload longer than 96 bytes overwrote cmd with its own tail, the
"version" compare failed, and the capture never ran. Every real Core peer
sends 102–125 bytes; only short lab payloads (86B, empty UA) fit — which is
exactly why the loopback test never caught it. Two bonus defects fixed in the
same pass: a >128-byte version failed the WHOLE handshake (p2p_read -2 →
fail), silently dropping any peer with a long UA (cap now 256); and both
handshakes loaded the u32 plen with an 8-byte read, dragging in garbage.

Fixed layout (payload @-0x2e0 cap 256, plen @-0xc8, frame 0x338 — which also
restores 16-byte RSP alignment at the calls). test_bitcoind's fake peer now
sends a REALISTIC 102-byte version with a UA and asserts exact captured
len/proto/services/UA — the old 86-byte fake is documented as the reason the
bug survived. Verified against 7 real mainnet peers: all capture exact
lens/UAs incl. the 125-byte FutureBit ones. Diagnostic probes kept in
tests/hs_{seq,cap}_probe.c. abi-check, callee-saved-check, stack-align, and
all 12 handshake/net/sync suites green.

## peermeters: getpeerinfo byte counters + last-activity from TCP_INFO

getpeerinfo's bytessent/bytesrecv/lastsend/lastrecv were 0 (documented gap --
per-peer I/O is buried in the asm node_sync_multi; /proc/pid/io is aggregate).
Filled from the kernel: the worker's publish loop reads getsockopt(TCP_INFO)
per live fd and publishes bytes_acked/bytes_received + last_data_sent/recv into
the shared peer table -- no asm changes, no double counting, kernel-
authoritative. The struct is read by offset into a local mirror of the stable
tcp_info uapi layout (the glibc header here lacks the byte fields), guarded by
the returned optlen so an older kernel just leaves those fields 0. rpc_node.c
reports them; test_rpc_node asserts them. Deploys with the next restart.
