# 2026-08-16 (late) — t_eba4b5f8 mux 24h+ soak: listener bug found & fixed

## Task
Run the configured soak for a long duration (min 24h, pref 72h) of the outbound
P2P mux (`bitcoind serve <dir> <port> <nwant>`). Acceptance: complete soak log,
resource time series, tip-advance timeline, serve success/failure, mux/poll()
anomalies.

## BLOCKER found (why the node "never listened")
The previous soak attempts (auto-decomposer / earlier runs) all had the node
running but port 18444 never in LISTEN. Root cause, verified via strace:

`bitcoind serve` ran `outbound_catchup()` — an UNBOUNDED `node_sync` against
real mainnet, anchored at the stored tip — BEFORE `serve_mux` created the
listener socket. When the soak store is far from the chain tip (the store was
~28K–40K while the chain tip is ~962K, a ~934K-block gap), `node_sync` takes
hours to close. During that entire window the listener socket does not exist, so:
- the node cannot serve inbound peers while catching up
- the `inbound_client` serve probe can never succeed
- the outbound mux (the feature under soak) only starts after catch-up completes

This is an architectural defect: catch-up and serving were SERIAL, not
concurrent. A mux's whole point is to serve AND download concurrently.

## FIX (asm/daemon/main.c, minimal + surgical, asm unchanged)
1. **Listener first**: create the `lsock(port)` listener in the `serve` handler
   BEFORE the catch-up, and pass it into `serve_mux(port, peers, nwant,
   out_port, l)`. The listener is now live in <1 s even while the node is still
   catching up.
2. **Bounded catch-up**: `outbound_catchup` now sets a SIGALRM wall-clock cap
   (CATCHUP_MAX_SECS=60 s) around its single `node_sync` pass. If the gap is
   large the alarm fires, `node_sync`'s blocking `p2p_read` sees EINTR and
   returns, and the mux loop starts and closes the rest of the gap gradually
   WHILE SERVING. The mux is the long-running stays-current mechanism; the
   pre-mux catch-up is now a bounded boot courtesy.
3. `serve_mux` signature updated to accept the pre-created listener `l` (the
   poll array already used `l` as pfds[0]).

Verified:
- `make` green; `test_outbound_mux` (loopback mux) PASSES (concurrent inbound
  serve + outbound pull, freshly-mined block served without restart).
- Live: listener on 18444 LISTEN within 2 s of launch (even mid-catchup).
- Live: after the 60 s catch-up cap, the mux loop engages (5 outbound peers),
  and the tip keeps advancing via the mux (28K → 32K → 40K over ~1 h).
- Serve probe (inbound_client) currently TIMES OUT while the node is mid-IBD —
  this is a real finding to record in the soak (see below), not a crash: the
  listener accepts the TCP connection, but the forked node_serve_loop child does
  not complete the version/verack round-trip while the parent is busy
  downloading. Recorded as serve-failure data in the soak.

## Findings for the soak (serve success/failure)
- listener: UP (LISTEN) from t≈2 s — FIX WORKS.
- download: continuous, ~1.5 blk/s single-seed in catch-up, faster once the mux
  loop's 5 outbound legs rotate. Tip advanced 28484 → 40137 (~11.6K blocks) in
  the ~1 h since the fix, confirming sustained real-mainnet ingest+serve
  viability at full scale (matches t_c13d882d's finding).
- serve round-trip (inbound_client): FAILS (timeout) while mid-IBD — the mux is
  so busy downloading that the forked inbound-serve child does not answer
  version/verack in the probe window. This is the "serve success/failure" data
  point the soak must capture over the full duration.
