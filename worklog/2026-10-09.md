# 2026-10-09

## -maxtxfee was parsed and never read (branch fix/2026-10-09-maxtxfee)

An outside architecture review of the README said `maxtxfee` enforcement
was missing. Checked against the code, that was half right. The wallet
does enforce a ceiling on every funding path (WAL-17, 2026-09-03) and in
bumpfee, but it was the constant `BF_MAXTXFEE_SAT` (Core's 0.1 BTC
default). `maxtxfee=` in the config was parsed into `g_cfg.maxtxfee_sat`,
counted as applied, and read by nothing. An operator setting
`maxtxfee=0.01` got no warning and a 0.1 BTC cap, and the refusal text
told them to "raise -maxtxfee", which did nothing.
`docs/FEATURE_GAPS.md` called it implemented, while the README listed it
as not implemented; neither was right.

The fix:

- `g_cfg.maxtxfee_sat` defaults to 0.1 BTC (it was 0, commented "no
  cap").
- main.c hands it to the wallet with the other policy defaults
  (`rpc_wops_defaults.maxtxfee_sat`), and both checks read it.
- The parser refuses a non-amount (it used to `atof` "lots" to 0).
- Core refuses a value under the minrelay fee for 1 kvB. This node keeps
  0.1 BTC and says so, the config's usual answer.
- Over 1 BTC it warns, as Core does.

Tests:

- `test_rpc_wallet_ops` replaces the WAL-17 "not tested, no way in" note
  with a case: at maxtxfee=100 sat a 141-sat fundrawtransaction is refused
  -4, and at 0.1 BTC it funds.
- `test_node_config` checks the default, 0.01, 'lots', 0, and 500 sat
  under a raised minrelay.
- With the constant put back and the old parser restored, each fails one
  check (`fee 0.00000141` funded; `parse (1000000 0 0 500)`).
- Built and run at nice 19 beside run 45; the full gate follows the run.

## Run 41 against run 45: the 17 minutes, and the frozen copy's pages

Run 45 reached ready 1,011 s after run 41 (14,713 s against 13,702 s). The
per-block `[bench] block` lines put it on the applier: the two runs reach
575k together, and between 575k and 875k run 45's downloader sits at
450-930 blocks ahead of the apply with 160 in flight (apply-bound). Summed
over the whole sync: `get` +1,092 s, the freeze (`flush`) +488 s, `put`
-305 s. Cause: M2 (#407) made `dbcache` the total, so the memtable went from
2^25 slots / 6,144 MB to 2^24 / 3,072 MB -- twice the freezes (231 against
110) and twice the runs on disk at any time (mean 26.3 against 13.8).

The freezes. A run 45 freeze took 2.4 s (run 41: 0.9 s) though the copy
measures 0.12-0.24 s at production size. A diagnostic sync with the freeze
timed in parts (gate 0, WAL drain 0, fork ~20-40 ms) left the copy itself
at 0.5-4.9 s, and /proc/vmstat across two freezes showed why: 1,531
huge-page faults and 1,742 direct-compaction stalls. M2 released the frozen
copy's pages at every adopt, so each freeze faulted ~3 GB of huge pages
back, each behind a compaction on a box whose memory is page cache.

The fix: the copy keeps its pages. The peak does not move -- live and frozen
are both in the dbcache budget and both resident at every freeze -- only the
mean between flushes does. The same diagnostic sync with the fix: freezes
2-16 took 250-354 ms (two passes before it: mean 1,754 and 2,747 ms, max
4.9 s), 113 huge-page faults across 15 freezes. On run 45's 231 freezes that
is ~480 s off the applier. The `[bench] freeze` line now names its parts
(drain+copy, gate, fork). `test_utxo_fork_trim` pins the pages kept; with
M2's MADV_DONTNEED put back it fails two checks.

The lookups (measured, not changed here). The flush runs' Bloom filters are
capped at 4 MiB (BLOOM_MAX_BYTES): a 19M-record run gets 1.76 bits/key and
passes 55% of absent keys, each then a ~500 ns sparse search + scan, ~350 ns
per run per lookup. Sized at 14 bits/key (32 MiB) the same run passes 2% and
costs ~30 ns. Per spent input `get` was 1,248 ns in run 41 and 1,624 ns in
run 45 over the same 1.80 billion inputs (575k-875k). The cap is in the
flush scratch layout, the merge's scratch and the asm fallback's TLS bloom
copy; lifting it is its own change. The three FNV hashes are also recomputed
per run, ~50 ns each time, with the same seeds for every run.
