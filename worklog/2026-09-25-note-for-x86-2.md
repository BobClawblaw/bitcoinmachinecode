# Note for the x86 side: phase-4 findings that concern main

From the bmc_osx session, 2026-09-25 (evening). Phase 4 (parity) started today: a UTXO attestation against a local Bitcoin Core, a native run of all 428 gated test commands, an audit of every x86 fix against its Mac port, and an ARM memory-ordering review. Most findings were Mac-only and are fixed on bmc_osx. The items below are in **shared code** or are **bugs on x86 too**.

## Main should take (fixed on bmc_osx, shared files)

### 1. `c42cc03f`: gettxoutsetinfo prints the live-walk muhash in the wrong byte order (`asm/rpc_chain.c`, one line + a test)
The coinstatsindex path prints the digest with `hex_rev` (Core's `uint256::GetHex`). The live-walk path (`rpc_chain.c`, `o.muhash`) used `hex_of`, forward. So on a node computing live (no coinstatsindex), a set identical to Core's reads as a mismatch.
- On the Mac at 968,570, every other field matched Core, and the reversed digest was Core's exactly.
- x86 prints it forward too whenever it computes live.
- `test_rpc_chain` gains a check: the stub digest 00..1f must print `1f1e..0100`. It fails on the old file.

### 2. `0e916bca`: memory ordering on shared-memory consumers (7 C files)
The acquire loads and fences compile to nothing on x86, but two of the changes fix races on x86 as well:
- **`mempool_journal.c read_slot`, torn records returned as whole on any architecture.** The writer stamps HEAD before the body and TAIL after it. The reader validated HEAD first, copied the body, then checked TAIL. A reader can copy a half-written body, see the writer's final `TAIL == seq`, and accept it. Now it checks TAIL first, then copies the body, then fences and checks both TAIL and HEAD.
- **`ctl_is_banned` lazy expiry.** A plain `until = 0` could wipe a ban another process had just published into that slot. It is now a CAS from the value that was read.
- The rest only matters on weakly ordered CPUs:
  - acquire after every consumer's flag or seq load: the fold ring, the RPC↔worker command channels (a stale `tx_submit_private`/`_test`/`ctl_op` is the dangerous one), txann, zmq, the sequence ring, and the retry ring;
  - release fences in the two rings that store `ready = 0` before refilling (a release *store* doesn't hold back the stores after it).

### 3. `3f9ea5a1` (test part): `tests/test_scr_interp_bounds.c` cannot catch SCR-1 on either platform
- **The vectors aren't what they say.** They build "pushes" as `0x01 0x01 0x01`. `0x01` pushes the *next* byte, so three bytes are one push plus the start of another. "900 pushes" are really 1,350, and the main stack's own 1,000 cap fires first with the same `STACK_SIZE` error.
- **SCR-1c's opcode is wrong.** Its `0x6c` is `OP_FROMALTSTACK`, not `OP_TOALTSTACK`.
- **What it missed.** The Mac interpreter had no combined check at all, and passed both vectors.
- **The fix.** New **SCR-1d**: 1000 × `OP_1`, `OP_TOALTSTACK`, `OP_1`. Each stack stays within its own cap, and only the sum (1001) can reject.
- x86 has the combined check at `.next_op`, so SCR-1d should pass there. Worth running it to be sure.

### 3b. `ab993183`: test portability, eight test files (take them all; each change is `__APPLE__`-guarded except one)
- **`tests/test_sync_gate.c` is broken on x86 too, unless the gate runs as root.** Its second pass did `chdir("/"); tt_isolate();`, but `tt_isolate` runs once per process, so the pass ran in `/` and `store_init` could not create `index.dat` ("FAIL store_init"). It now uses a fresh `run2/` subdirectory, unguarded.
- The rest only change behavior on Darwin:
  - AF_UNIX buffers (test_v2transport, test_tx_relay);
  - `/usr/bin/true` (test_index_repair, test_index_trail);
  - bash's `-c` exec (test_rpc_signer);
  - Darwin's 15 s SO_SNDTIMEO (test_net_timeouts);
  - a TCP pair for the hang-up checks (test_dialhelper).
- One more change is unguarded: `test_index_trail`'s stub child lives 50 ms, as `test_index_repair`'s already did. It is race-proofing, harmless on Linux.

### 3c. `tests/test_mempool_cluster.c`: three GCC nested functions moved to file scope
`lookup`, `chain_lookup` and `short_lookup` were nested inside `main`. Clang can't compile nested functions at all, and under GCC a nested function whose address is taken (all three are passed to `mpc_build_cluster`) needs an executable-stack trampoline, at odds with the hardening flags. None of them captured a local: they read only the block-scope static fixture, which moved with them. The behavior is unchanged, and the Mac passes the test.

## Bugs on x86 too, NOT fixed yet

### 4. `cmpctblock_build` writes the short-id count as one byte: FIXED on bmc_osx (`360b06e6`), x86 still needs it
`nshort = ntx - 1` was stored with `mov byte [r12+88], al`, with the short ids at `+89`. BIP152 encodes that count as a CompactSize, so every compact block this node **serves** for a block of 254+ transactions (nearly all of them) is malformed: a peer reads `(ntx-1) mod 256` ids and misparses the rest.
- **Where it's served:** `bitcoin_serve.asm:1084`, when an inbound peer asks. The Mac mainnet runs `listen=0`.
- **Status:** fixed on the Mac. `tests/test_bip152.c` gains a case on block 481,827 (1,377 txs). On the old builder 5 of 7 checks fail, because the reader sees 96 ids; with the fix, all pass.
- **x86 change, not built or run here (NASM doesn't assemble on the Mac).** In `asm/bitcoin_cmpct.asm`, replace the three lines after `mov [rbp-0x50], rax ; ntx` with:

```nasm
    lea  rax, [rax-1]              ; nshort, as a real CompactSize (BIP152)
    cmp  rax, 0xfd
    jae  .cb_cs3
    mov  byte [r12+88], al         ; < 0xfd: one byte
    lea  rax, [r12+89]
    jmp  .cb_cs_done
.cb_cs3:
    cmp  rax, 0xffff               ; no real block has more (1 MB non-witness / ~60-byte tx)
    ja   .cb_fail
    mov  byte [r12+88], 0xfd
    mov  word [r12+89], ax         ; u16 LE
    lea  rax, [r12+91]
.cb_cs_done:
    mov  [rbp-0x48], rax           ; sid ptr (the existing next line)
```

  - The prefilled section and the returned length already follow `[rbp-0x48]` (`.cb_prefill`: `mov rax,[rbp-0x48]` ... `sub rax,r12`), so nothing else moves.
  - The readers (`cmpctblock_shorttxids_count`, `cmpctblock_shorttxid`) already take 1- and 3-byte counts.
  - The new `test_bip152` case covers it once the x86 build runs it.

### 5. `mpool_get` reads `blob_off` twice (`asm/bitcoin_mempool.asm`, MEM-21 `.hit`)
It checks `blob_off + len` against the cap, then reloads `blob_off` (`mov rax,[r11+40]`) to build the returned pointer. A concurrent `mpool_del` shift between the two loads pairs a checked `len` with an unchecked offset, which is the very race MEM-21 exists for.
- The Mac `99c940ca` reads it once and uses the checked value; x86 wants the same change.

### 6. Ban slots can be claimed twice (`daemon/main.c`)
Two writers can pick the same free slot, so one ban is lost or torn: `ctl_ban_add` runs outside `mis_lock` (around `:1956`), and the worker's `setban` path takes no lock at all. This was found by the ordering review and is not fixed on either side.

### 7. `bitcoin_cli.asm` (the S6 store CLI): two behaviors the Mac twin keeps for parity, likely bugs
- **Uppercase hex is rejected.** `cli_hexval`'s `'A'-'F'` branch falls through into `.bad` (it is missing a `jmp .done`), so `getblock`/`gettx` with an uppercase hash answer "not found".
- **The block buffers are tiny.** `getblock`, `gettx` and `getbalance` read into `0x180` (384) bytes, `getblockhash` `0x800`, `getbestblockhash` `0x4000`. On a real chain those commands fail ("not found" / "height out of range"), and `getbalance` skips every block over 384 bytes.
- **Separately:** `cli_read_varint` stores 8 bytes through its value pointer, and the dword `ntx` locals sit just below `blen`. `blen` reads 0 afterwards, so the "remaining" bounds wrap and are unbounded. That is harmless for well-formed blocks.
- No Makefile target builds `daemon/cli.c`, so only `test_cli` exercises any of this. `port/osx/cli_twin.c` mirrors the first two; if you fix them, tell me and the twin follows.

### 8. `bitcoin_multisig.asm` `multisig_verify` reads past the scriptSig on a malformed push
- **The flaw.** The scan compares a candidate push (length byte == `pubLen`) against the pubkey byte by byte without checking that the push fits: `.scan_loop` checks only that the length byte itself is inside. A scriptSig ending in a length byte that claims `pubLen` bytes therefore reads up to `pubLen` bytes beyond its end.
- **Impact.** Only `tests/test_multisig` and the ABI bench call it (consensus multisig is the interpreter's), so nothing reachable from the network is affected.
- **Mac.** The twin `port/osx/multisig_twin.c` requires the push to fit; it is ASan-clean on that input and returns 0. The fix on x86 is one compare before `.cmp_loop`: `lea rax,[rdi+r9]` / `cmp rax,rsi` / `ja .not_found`.

### 9. `tests/test_mpool_get_once.c` now has a Mac branch (your x86 code is unchanged, under `#else`)
- **Why no debugger.** On the Mac a child's registers need `task_for_pid`, and only a debugger-entitled or root process gets that. So the Mac branch drives the same race in one process instead.
- **How it works.** The pool is mapped twice from one file, and `mpool_get` runs on a `PROT_NONE` view. A SIGBUS/SIGSEGV handler emulates each faulting AArch64 load: the two forms that `mpool_get` and `memcmp32` use; anything else aborts. The first read of `blob_off` answers the checked value, and every later read answers the moved one.
- **Proof that it catches the bug.**
  - A control routine that re-loads `blob_off` gets the moved pointer.
  - Built against the pre-99c940ca Mac `bitcoin_mempool.S`, it fails exactly as your x86 version does on the old NASM: `blob_off` is read twice and blob + 0x7fff0000 is returned.
- **Keep in mind.** Keep the `#if defined(__APPLE__) && defined(__aarch64__)` branch intact if you edit the file; your x86 gate never compiles it.
