# Note for the x86 side: phase-4 findings that concern main

From the bmc_osx session, 2026-09-25 (evening). Phase 4 (parity) started today: a UTXO attestation against a local Bitcoin Core, a native run of all 428 gated test commands, an audit of every x86 fix against its Mac port, and an ARM memory-ordering review. Most findings were Mac-only and are fixed on bmc_osx. The items below are in **shared code** or are **bugs on x86 too**.

## Main should take (fixed on bmc_osx, shared files)

### 1. `c42cc03f`: gettxoutsetinfo prints the live-walk muhash in the wrong byte order (`asm/rpc_chain.c`, one line + a test)
The coinstatsindex path prints the digest with `hex_rev` (Core's `uint256::GetHex`). The live-walk path (`rpc_chain.c`, `o.muhash`) used `hex_of`, forward. So on a node computing live (no coinstatsindex), a set identical to Core's reads as a mismatch.
- On the Mac at 968,570, every other field matched Core, and the reversed digest was Core's exactly.
- x86 prints it forward too whenever it computes live.
- `test_rpc_chain` gains a check: the stub digest 00..1f must print `1f1e..0100`. It fails on the old file.

### 2. `0e916bca`: memory ordering on shared-memory consumers (7 C files)
The acquire loads and fences compile to nothing on x86, but two of the changes fix races on x86 as well:
- **`mempool_journal.c read_slot`, torn records returned as whole on any architecture.** The writer stamps HEAD before the body and TAIL after it. The reader validated HEAD first, copied the body, then checked TAIL. A reader can copy a half-written body, see the writer's final `TAIL == seq`, and accept it. Now it checks TAIL first, then copies the body, then fences and checks both TAIL and HEAD.
- **`ctl_is_banned` lazy expiry.** A plain `until = 0` could wipe a ban another process had just published into that slot. It is now a CAS from the value that was read.
- The rest only matters on weakly ordered CPUs:
  - acquire after every consumer's flag or seq load: the fold ring, the RPC↔worker command channels (a stale `tx_submit_private`/`_test`/`ctl_op` is the dangerous one), txann, zmq, the sequence ring, and the retry ring;
  - release fences in the two rings that store `ready = 0` before refilling (a release *store* doesn't hold back the stores after it).

### 3. `3f9ea5a1` (test part): `tests/test_scr_interp_bounds.c` cannot catch SCR-1 on either platform
- **The vectors aren't what they say.** They build "pushes" as `0x01 0x01 0x01`. `0x01` pushes the *next* byte, so three bytes are one push plus the start of another. "900 pushes" are really 1,350, and the main stack's own 1,000 cap fires first with the same `STACK_SIZE` error.
- **SCR-1c's opcode is wrong.** Its `0x6c` is `OP_FROMALTSTACK`, not `OP_TOALTSTACK`.
- **What it missed.** The Mac interpreter had no combined check at all, and passed both vectors.
- **The fix.** New **SCR-1d**: 1000 × `OP_1`, `OP_TOALTSTACK`, `OP_1`. Each stack stays within its own cap, and only the sum (1001) can reject.
- x86 has the combined check at `.next_op`, so SCR-1d should pass there. Worth running it to be sure.

### 3b. `ab993183`: test portability, eight test files (take them all; each change is `__APPLE__`-guarded except one)
- **`tests/test_sync_gate.c` is broken on x86 too, unless the gate runs as root.** Its second pass did `chdir("/"); tt_isolate();`, but `tt_isolate` runs once per process, so the pass ran in `/` and `store_init` could not create `index.dat` ("FAIL store_init"). It now uses a fresh `run2/` subdirectory, unguarded.
- The rest only change behavior on Darwin:
  - AF_UNIX buffers (test_v2transport, test_tx_relay);
  - `/usr/bin/true` (test_index_repair, test_index_trail);
  - bash's `-c` exec (test_rpc_signer);
  - Darwin's 15 s SO_SNDTIMEO (test_net_timeouts);
  - a TCP pair for the hang-up checks (test_dialhelper).
- One more change is unguarded: `test_index_trail`'s stub child lives 50 ms, as `test_index_repair`'s already did. It is race-proofing, harmless on Linux.

### 3c. `tests/test_mempool_cluster.c`: three GCC nested functions moved to file scope
`lookup`, `chain_lookup` and `short_lookup` were nested inside `main`. Clang can't compile nested functions at all, and under GCC a nested function whose address is taken (all three are passed to `mpc_build_cluster`) needs an executable-stack trampoline, at odds with the hardening flags. None of them captured a local: they read only the block-scope static fixture, which moved with them. The behavior is unchanged, and the Mac passes the test.

## Bugs on x86 too, NOT fixed yet

### 4. `cmpctblock_build` writes the short-id count as one byte: FIXED on bmc_osx (`360b06e6`), x86 still needs it
`nshort = ntx - 1` was stored with `mov byte [r12+88], al`, with the short ids at `+89`. BIP152 encodes that count as a CompactSize, so every compact block this node **serves** for a block of 254+ transactions (nearly all of them) is malformed: a peer reads `(ntx-1) mod 256` ids and misparses the rest.
- **Where it's served:** `bitcoin_serve.asm:1084`, when an inbound peer asks. The Mac mainnet runs `listen=0`.
- **Status:** fixed on the Mac. `tests/test_bip152.c` gains a case on block 481,827 (1,377 txs). On the old builder 5 of 7 checks fail, because the reader sees 96 ids; with the fix, all pass.
- **x86 change, not built or run here (NASM doesn't assemble on the Mac).** In `asm/bitcoin_cmpct.asm`, replace the three lines after `mov [rbp-0x50], rax ; ntx` with:

```nasm
    lea  rax, [rax-1]              ; nshort, as a real CompactSize (BIP152)
    cmp  rax, 0xfd
    jae  .cb_cs3
    mov  byte [r12+88], al         ; < 0xfd: one byte
    lea  rax, [r12+89]
    jmp  .cb_cs_done
.cb_cs3:
    cmp  rax, 0xffff               ; no real block has more (1 MB non-witness / ~60-byte tx)
    ja   .cb_fail
    mov  byte [r12+88], 0xfd
    mov  word [r12+89], ax         ; u16 LE
    lea  rax, [r12+91]
.cb_cs_done:
    mov  [rbp-0x48], rax           ; sid ptr (the existing next line)
```

  - The prefilled section and the returned length already follow `[rbp-0x48]` (`.cb_prefill`: `mov rax,[rbp-0x48]` ... `sub rax,r12`), so nothing else moves.
  - The readers (`cmpctblock_shorttxids_count`, `cmpctblock_shorttxid`) already take 1- and 3-byte counts.
  - The new `test_bip152` case covers it once the x86 build runs it.

### 5. `mpool_get` reads `blob_off` twice (`asm/bitcoin_mempool.asm`, MEM-21 `.hit`)
It checks `blob_off + len` against the cap, then reloads `blob_off` (`mov rax,[r11+40]`) to build the returned pointer. A concurrent `mpool_del` shift between the two loads pairs a checked `len` with an unchecked offset, which is the very race MEM-21 exists for.
- The Mac `99c940ca` reads it once and uses the checked value; x86 wants the same change.

### 6. Ban slots can be claimed twice (`daemon/main.c`)
Two writers can pick the same free slot, so one ban is lost or torn: `ctl_ban_add` runs outside `mis_lock` (around `:1956`), and the worker's `setban` path takes no lock at all. This was found by the ordering review and is not fixed on either side.

### 7. `bitcoin_cli.asm` (the S6 store CLI): two behaviors the Mac twin keeps for parity, likely bugs
- **Uppercase hex is rejected.** `cli_hexval`'s `'A'-'F'` branch falls through into `.bad` (it is missing a `jmp .done`), so `getblock`/`gettx` with an uppercase hash answer "not found".
- **The block buffers are tiny.** `getblock`, `gettx` and `getbalance` read into `0x180` (384) bytes, `getblockhash` `0x800`, `getbestblockhash` `0x4000`. On a real chain those commands fail ("not found" / "height out of range"), and `getbalance` skips every block over 384 bytes.
- **Separately:** `cli_read_varint` stores 8 bytes through its value pointer, and the dword `ntx` locals sit just below `blen`. `blen` reads 0 afterwards, so the "remaining" bounds wrap and are unbounded. That is harmless for well-formed blocks.
- No Makefile target builds `daemon/cli.c`, so only `test_cli` exercises any of this. `port/osx/cli_twin.c` mirrors the first two; if you fix them, tell me and the twin follows.

### 8. `bitcoin_multisig.asm` `multisig_verify` reads past the scriptSig on a malformed push
- **The flaw.** The scan compares a candidate push (length byte == `pubLen`) against the pubkey byte by byte without checking that the push fits: `.scan_loop` checks only that the length byte itself is inside. A scriptSig ending in a length byte that claims `pubLen` bytes therefore reads up to `pubLen` bytes beyond its end.
- **Impact.** Only `tests/test_multisig` and the ABI bench call it (consensus multisig is the interpreter's), so nothing reachable from the network is affected.
- **Mac.** The twin `port/osx/multisig_twin.c` requires the push to fit; it is ASan-clean on that input and returns 0. The fix on x86 is one compare before `.cmp_loop`: `lea rax,[rdi+r9]` / `cmp rax,rsi` / `ja .not_found`.

### 9. `tests/test_mpool_get_once.c` now has a Mac branch (your x86 code is unchanged, under `#else`)
- **Why no debugger.** On the Mac a child's registers need `task_for_pid`, and only a debugger-entitled or root process gets that. So the Mac branch drives the same race in one process instead.
- **How it works.** The pool is mapped twice from one file, and `mpool_get` runs on a `PROT_NONE` view. A SIGBUS/SIGSEGV handler emulates each faulting AArch64 load: the two forms that `mpool_get` and `memcmp32` use; anything else aborts. The first read of `blob_off` answers the checked value, and every later read answers the moved one.
- **Proof that it catches the bug.**
  - A control routine that re-loads `blob_off` gets the moved pointer.
  - Built against the pre-99c940ca Mac `bitcoin_mempool.S`, it fails exactly as your x86 version does on the old NASM: `blob_off` is read twice and blob + 0x7fff0000 is returned.
- **Keep in mind.** Keep the `#if defined(__APPLE__) && defined(__aarch64__)` branch intact if you edit the file; your x86 gate never compiles it.

### 10. `rpc_commands.c` `getmemoryinfo`: `#ifdef __GLIBC__` around mallocinfo (your build is unchanged)
- **What changed.** Without glibc, `"mallocinfo"` now returns `-8 "mallocinfo mode not available"`. That is exactly what Core's `rpc/node.cpp` answers when built without `HAVE_MALLOC_INFO`, i.e. on macOS. The Mac used to answer `-1 "malloc_info failed"` from a failure stub, which is now deleted.
- **The "stats" message.** Its suggestion to use mallocinfo is kept only under `__GLIBC__`.
- **Tests.** `test_rpc_control` expects the Core refusal on non-glibc builds.
- **Checked.** The glibc branch was syntax-checked with `__GLIBC__` forced on.

### 11. `tests/test_rpc_responsive.c` section C: one unmeasured getindexinfo before the three measured rounds
- **Why.** The first getindexinfo on a thread pays a one-time cost unrelated to the tail. On the Mac it is 0.55-1.07 ms at every tail size (1 record, 24k and 2.4M were all measured); every later call is ~0.025 ms at every size. With the first call measured, worst-of-3 was that warm-up, so the test failed 4 of 5 runs on a loaded Mac.
- **Still guarded.** Each measured round grows the tail first, and a reader that re-scans from byte 0 (simulated by wrapping the dispatch) still fails the test at 5.6 ms.
- **x86.** The change is harmless there.

### 12. `daemon/addr_hist.c` was not thread-safe, and the Esplora facade calls it from several threads (x86 production too)
- **The bug.** `ah_lookup` returned, and `realloc`'d, ONE global result buffer, and `ah_scan` rebuilt the run table and `munmap`'d replaced runs, all with no lock. Concurrent `/address` requests could free a buffer another thread was still copying into or reading, or unmap a run under a reader.
- **Seen on the Mac.** `test_rpc_esplora_stress` crashed in `ah_lookup`'s memmove in 2 of 5 runs ("4 threads on /address at once"). x86 passes by timing only.
- **Fix (in shared code, so you get it when you merge).**
  - A mutex covers every run-table and mapping access, held for a whole lookup (a binary search and a copy).
  - The result buffer is per thread (a `pthread_key` with a destructor, so a connection thread per request frees its buffer on exit).
- **After the fix.** 10/10 stress runs pass; `test_addr_hist`, `test_rpc_esplora` and `test_addr_index_tail` still pass. The Esplora backend for mempool.space is the production caller.

### 13. `daemon/wallet_cli.c` `secret_prompt`: echo off BEFORE the prompt (`ce7837de`)
- **The bug.** `tcsetattr(TCSAFLUSH)` after the prompt discarded an answer that arrived in between, and then `fgets` waited forever.
- **Now.** The order matches `readpassphrase(3)`.
- **Evidence.** `test_cli_prompt` hung intermittently under load (with the pre-fix CLI: 1 hang in 2 runs; with the fix: 8/8 pass). The race is platform-independent.

### 14. `tests/test_txvb_wprog_stable.c` could not pass on a freshly fetched fixture, on either platform
- **The mismatch.** It builds its only coin store from `blk_482566.prevouts` (`bx == NULL`, no in-block index). Since its 09-24 rewrite, `validation/fetch_block_prevouts.py` leaves out outputs created inside the block, so tx 271 spends a coin the store never had: "input references a missing/already-spent UTXO".
- **The fix.** The test now adds the block's own outputs, keyed by the witness-stripped txid, unless the file already has them (old-format fixtures keep working).
- **On the Mac.** With a fixture fetched today from a local Core: 5015 fetched + 3087 in-block, and block 482566 verifies through the adversarial one-buffer store.

### 15. `bitcoin_store_fast.asm`: `MAP_MAGIC` at `st+120` is inside the fd cache
- **The overlap.** The fd cache is `st+64 + slot*8` for 8 slots, so slot 7 is `st+120..127`. That is where `MAP_MAGIC` is kept.
- **The effect.** `store_rd_fd` of any `file_no & 7 == 7` overwrites the magic. The next map call then takes the cache for uninitialised and clears its slots without `munmap`. Each time, that leaks a mapping of up to a 128 MiB blk file and loses the cache. Only `bmc_build_block_filters` maps.
- **Found.** 2026-09-26, by the differential test of the Mac port's `bitcoin_store_fast.S`: the magic changed on an fd-cache fill.
- **On the Mac.** The magic is now at `st+384`, past the map slots (every Mac caller's state is 4096 bytes).
- **On x86** the struct floor is 256 bytes (`test_ibd_blocks.c`'s `stb2/stb3[256]`, `test_wallet.c`'s 1024), so `st+256` is NOT free there. Two places that are: the reserved qword of map slot 0 (`st+128+24`), which nothing reads, or the 4 bytes at `st+52` (after `prune_height`) with a dword magic. Either keeps every existing caller.
- **Also still on main** (checked 2026-09-27 against `781bc354`): item 7's `cli_hexval` falls from the `'A'-'F'` branch into `.bad` (no `jmp .done`).

### 16. A mutated block (witness mismatch) is marked BLOCK_FAILED_VALID -- the real chain tip gets invalidated (shared C; fixed on bmc_osx 2026-09-27)
- **What happened.** Mainnet 968,824 on the Mac node: a peer's compact block prefilled the coinbase without its witness. The sync drain's `cons_verify` passed it (PoW and the txid merkle root do not see witnesses), the block was stored, and `utxo_live`'s witness-commitment phase refused it with `bad-witness-nonce-size`. The apply treats every verification refusal as a consensus reject: `chain_invalidate_block` marked the REAL block's hash in `invalid.dat`, truncated the archive and rolled headers back. The next peer's delivery connected it 10 s later only because that path never consults the mark; the mark itself stayed until a manual `reconsiderblock`.
- **Why it is wrong.** The block hash commits to no witness data; Core's `IsBlockMutated` / `BLOCK_MUTATED` never marks a header for `bad-witness-nonce-size`, `bad-witness-merkle-match` or `unexpected-witness`. A single peer can otherwise get a node to reject the chain tip until "a heavier chain avoids it".
- **The fix (shared C, on bmc_osx; the Mac's assembly drain is not involved).** `cmpct_recv.c` checks the witness commitment of every completed reconstruction and falls back to a full getdata (Core's `FillBlock` → `CheckBlock`); `utxo_live.c` classifies a witness-commitment failure as MUTATED and calls a new hook that drops the bytes without a mark (`reorg.c` `chain_drop_mutated_block`, `main.c` `dl_drop_mutated_block`). Tests: `test_cmpct_recv` and `test_connect_reject` phase 5. The commit will come as a PR against main.

### 17. `legs_heard_within` (#316) does not build on Darwin: `struct tcp_info` / `tcpi_last_data_recv` are Linux (shared C; a Darwin branch is on bmc_osx)
- **What broke.** `daemon/main.c`'s new `legs_heard_within` reads `tcpi_last_data_recv` through `TCP_INFO`. macOS declares `struct tcp_info` without defining it (private), so the merged tree failed to compile here ("variable has incomplete type").
- **On bmc_osx.** An `#if defined(__APPLE__) && defined(TCP_CONNECTION_INFO)` branch, next to the Linux one, with the same contract: `tcp_connection_info`'s `tcpi_rxbytes` counts every byte that arrived whoever read it, so a leg's last-heard time is the last time that count was seen to change, remembered per leg at the granularity of the calls (every pass's bookkeeping, every probe gate). A socket new to its slot (new fd, new local port, or a count that went down — the fd number is reused by the next dial) has been heard only if its count is already non-zero; with nothing received yet it has never been heard, however long ago it was opened — the first draft counted a fresh socket as heard now, and `test_pass_silence_strike` (three fresh, silent legs) caught it. The pattern `dh_tcp_state` already uses. `test_pass_silence_strike` and `test_announce_claim` pass on the Mac with it.
- **For main.** Take the branch as is when the next osx PR comes; nothing changes for x86.

### 18. Issue #294: a restart mid-sync sizes the memtable steady-state against a bulk-shaped store (shared C; fixed on bmc_osx 2026-09-28)
- **What happened.** Gap 3,345 (< 50,000), `utxo.dat` 0.25 GB (just under the 256 MB WAL rule), and 17 runs totalling 42 GB: both sizing rules stood down, the load probed 17 runs per lookup through a 64 MB memtable and applied nothing for 25 minutes at 100% CPU, in silence. `bmc.utxobulkgapblocks=500` made the same load finish in 162 s.
- **The fix.** A third rule on the STORE'S SHAPE: `utxo_live_pick_bulk_shape(runs, run_bytes, compact_threshold, run_budget)` in `utxo_live_sizing.h` — bulk when the runs are at or past the compaction threshold or their bytes past the 35%-of-RAM run budget the compactor already uses. `utxo_live_init` scans the datadir for `utxo_run_%06u.dat` (the manifest is not loaded yet at that point) and, whatever the verdict, logs the shape before the load ("store shape: N run file(s), X GB ... a lookup probes up to N runs"), so a long load has its reason in the log — `utxo_lsm_reload` says nothing while it runs. `test_utxo_sizing` pins the new rule (the #294 restart is bulk twice over; the gap rule is unchanged beside it). Suggestion 3 of the issue (compact before catching up) is not taken: bulk sizing removes the grind, and a merge under a small gap runs on the normal path.
- **For main.** Take `utxo_live_sizing.h`, the `utxo_live_init` block (needs `<dirent.h>`) and the test additions as they are.

### 19. Issue #304: a synced node runs the parallel downloader for a cluster's false claim (shared C; fixed on bmc_osx 2026-09-28)
- **What happened.** Two agreeing peers passed `dl_trigger_height`'s gate — but they were a cluster of Knots peers on a fork bmc's own probe rejects, and the `(noop_best, noop_tip)` memo did not survive a new tip; 60–130 s runs with the worker stopped, 0 blocks, after every start and every re-arm.
- **The fix.** Two rules about WHO is believed, in `main.c` beside `dl_trigger_height`: a leg whose sync pass is failing (`g_sync_fail_streak[i] > 0`: those peers' passes end in sync-budget closes because their headers do not connect) does not vote; and after a run that found nothing, every leg whose announce was at or above the trigger height is remembered BY HOST (`dl_claim_memo_note`, 32 entries, `DL_CLAIM_MEMO_S` = 6 h, across tips) and does not vote meanwhile, whatever it claims next — the false chain keeps growing, so the memo is on the peer, not the number. Logged as "<host> announced H and the download found nothing above T: its announces are not believed for 6 h". The `(claim, tip)` memo stays. `test_parallel_trigger` pins the memo (note / active / expiry / a repeat note / the table wrapping) and the per-leg rule. The issue's first direction (a cheap header probe of one claiming peer before the run) is not taken: the legs' pass results already say whether a peer's headers connect, and the memo makes a wrong run a once-per-6-h event per peer.
- **For main.** Take the `main.c` hunks (the memo block after `dl_trigger_height`, the vote filter at the `hs[]` build, the note after `dl_catchup`) and the test additions.
