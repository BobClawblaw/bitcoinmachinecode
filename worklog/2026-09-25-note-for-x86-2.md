# Note for the x86 side: phase-4 findings that concern main

From the bmc_osx session, 2026-09-25 (evening). Phase 4 (parity) started today: a UTXO attestation against a local Bitcoin Core, a native run of all 428 gated test commands, an audit of every x86 fix against its Mac port, and an ARM memory-ordering review. Most findings were Mac-only and are fixed on bmc_osx. The items below are in **shared code** or are **bugs on x86 too**.

## Main should take (fixed on bmc_osx, shared files)

### 1. `c42cc03f`: gettxoutsetinfo prints the live-walk muhash in the wrong byte order (`asm/rpc_chain.c`, one line + a test)
The coinstatsindex path prints the digest with `hex_rev` (Core's `uint256::GetHex`). The live-walk path (`rpc_chain.c`, `o.muhash`) used `hex_of`, forward. So on a node computing live (no coinstatsindex), a set identical to Core's reads as a mismatch.
- On the Mac at 968,570, every other field matched Core, and the reversed digest was Core's exactly.
- x86 prints it forward too whenever it computes live.
- `test_rpc_chain` gains a check: the stub digest 00..1f must print `1f1e..0100`. It fails on the old file.

### 2. `0e916bca`: memory ordering on shared-memory consumers (7 C files)
The acquire loads and fences compile to nothing on x86, but two of the changes fix races on x86 as well:
- **`mempool_journal.c read_slot`, torn records returned as whole on any architecture.** The writer stamps HEAD before the body and TAIL after it. The reader validated HEAD first, copied the body, then checked TAIL. A reader can copy a half-written body, see the writer's final `TAIL == seq`, and accept it. Now it checks TAIL first, then copies the body, then fences and checks both TAIL and HEAD.
- **`ctl_is_banned` lazy expiry.** A plain `until = 0` could wipe a ban another process had just published into that slot. It is now a CAS from the value that was read.
- The rest only matters on weakly ordered CPUs:
  - acquire after every consumer's flag or seq load: the fold ring, the RPC↔worker command channels (a stale `tx_submit_private`/`_test`/`ctl_op` is the dangerous one), txann, zmq, the sequence ring, and the retry ring;
  - release fences in the two rings that store `ready = 0` before refilling (a release *store* doesn't hold back the stores after it).

### 3. `3f9ea5a1` (test part): `tests/test_scr_interp_bounds.c` cannot catch SCR-1 on either platform
- **The vectors aren't what they say.** They build "pushes" as `0x01 0x01 0x01`. `0x01` pushes the *next* byte, so three bytes are one push plus the start of another. "900 pushes" are really 1,350, and the main stack's own 1,000 cap fires first with the same `STACK_SIZE` error.
- **SCR-1c's opcode is wrong.** Its `0x6c` is `OP_FROMALTSTACK`, not `OP_TOALTSTACK`.
- **What it missed.** The Mac interpreter had no combined check at all, and passed both vectors.
- **The fix.** New **SCR-1d**: 1000 × `OP_1`, `OP_TOALTSTACK`, `OP_1`. Each stack stays within its own cap, and only the sum (1001) can reject.
- x86 has the combined check at `.next_op`, so SCR-1d should pass there. Worth running it to be sure.

## Bugs on x86 too, NOT fixed yet

### 4. `cmpctblock_build` writes the short-id count as one byte (`asm/bitcoin_cmpct.asm`, ~line 758; Mac `bitcoin_cmpct.S:567`)
`nshort = ntx - 1` is stored with `mov byte [r12+88], al`, and the short ids follow at `+89`. BIP152 encodes that count as a CompactSize.
- **Effect:** every compact block this node **serves** for a block of 254+ transactions (nearly all of them) is malformed. The serve path (`bitcoin_serve.asm:1084`) sends one when an inbound peer asks.
- **Mac exposure:** none; the Mac mainnet runs `listen=0`.
- **Fix:** write a real CompactSize and move the short-id pointer (and the prefilled section after it) by its width. `cmpctblock_shorttxids_count` has to read it the same way.
- The header comment in the Mac file still says "single-byte txcount only".

### 5. `mpool_get` reads `blob_off` twice (`asm/bitcoin_mempool.asm`, MEM-21 `.hit`)
It checks `blob_off + len` against the cap, then reloads `blob_off` (`mov rax,[r11+40]`) to build the returned pointer. A concurrent `mpool_del` shift between the two loads pairs a checked `len` with an unchecked offset, which is the very race MEM-21 exists for.
- The Mac `99c940ca` reads it once and uses the checked value; x86 wants the same change.

### 6. Ban slots can be claimed twice (`daemon/main.c`)
Two writers can pick the same free slot, so one ban is lost or torn: `ctl_ban_add` runs outside `mis_lock` (around `:1956`), and the worker's `setban` path takes no lock at all. This was found by the ordering review and is not fixed on either side.
