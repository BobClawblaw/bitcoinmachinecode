## Round 1 — the osx node hammered the reference node; three defects behind it

- [x] **Stopped the traffic.** `~/bmc_osx_deploy/stop.sh` → SIGTERM, clean
      exit. The parent (pid 57253, download worker 38173) had been up since the
      09-12 20:59Z boot, but the pathology began at **13:31Z today**, when the
      download worker took over the legs: from there until the stop at 14:04Z
      the node dialled `192.168.5.242:8332` **8,986 times in 33 minutes** --
      4.5 completed connect/close cycles a second, 260-284 a minute, at a box on
      the same LAN -- with **345 pass-helper crashes** interleaved. Zero dials
      are recorded in the two days before 13:31Z, and the log otherwise reads
      like an ordinary keep-up run, which is why it went unnoticed.
- [x] **Defect 0 (the trigger, not a code bug): the conf named the wrong port.**
      `bmc_mainnet_conf` said `connect=192.168.5.242:8332`. .242's P2P port is
      8333; 8332 is its RPC port. TCP completes against an HTTP listener, the
      P2P version message never happens, the peer hangs up:
      `[dl:0] 192.168.5.242 connection closed theirs (revents 0x11) after 0s;
      unread: (nothing)`. A wrong port should cost the node one peer; it must
      not cost the peer a denial of service. Fixed in the deploy home (backup
      kept as `bmc_mainnet_conf.bak-20260914`).
- [x] **Defect 1 (the real bug, shared code): the reconnect backoff was
      consulted and then ignored.** `mux_next_peer()` -- "the ONE place outbound
      legs are established", its own comment -- walks the pool and marks each
      candidate `held` when it is under dial-memory backoff, already carried by
      another live leg, or on an anonymity network. Having found nothing free it
      dialled `peers[p]` **anyway**: the verdict decided nothing. With the
      one-host `connect=` pool that meant one candidate, always `held`, always
      dialled. The dial memory had the address filed under DM_REFUSED with a 10
      minute backoff doubling to 6 hours, and answered NO every time, in every
      one of those ~800k dials. Now the verdict gates the dial: no free
      candidate means no dial this pass and the caller's retry stamp re-drives
      the slot. An operator-named peer (`connect=`/`addnode=`) is still retried
      whatever the memory says -- Core does not apply addrman's triedtime to
      fixed seeds, and `-connect` has to mean "keep trying this one" -- but at
      Core's `CONNECT_INTERVAL` (60 s), stamped inside `mux_next_peer` itself,
      because several callers zero their own stamp on the way in (`mux_out_
      nextretry[i] = 0`) and a crashed pass helper does exactly that.
- [x] **Defect 2 (the osx crash in the same loop): `port/osx/net_twin.c` called
      the write hook through the wrong prototype.** `p2p_write()` invoked
      `g_p2p_write_hook` as `(int, u32)`. The hook grew `cmd`/`cmdlen` on
      2026-09-12 for getpeerinfo's `bytessent_per_msg`, `asm/bitcoin_net.asm`
      was updated the same day, this twin was not, and the installed hook
      (`main.c` `p2p_upload_pace`) read x2/x3 as the command pointer.
      `rpc_msg_index` then ran strcmp over garbage: the crash log's
      `FATAL-CRASH: signal 11 si_code=2 si_addr=0xa` at
      `p2p_upload_pace+180` is the return address of `bl _rpc_msg_index` --
      disassembly of the deployed binary shows the twin's `blr` loading the hook
      with x0=fd, x1=plen and nothing in x2/x3. Every pass of the download
      worker died (`exit 139`), and the parent answered each death by
      re-dialling. The twin now passes all four arguments, matching the asm.
- [x] **Evidence, both directions.** A unit harness (`abi_check`: socketpair +
      the four-argument hook, asserting the bytes the hook is handed) against
      `git show HEAD:port/osx/net_twin.c` **segfaults, exit 139** -- the
      deployed failure, reproduced deterministically in seconds; against the
      patched twin all eight assertions pass, on the payload and the
      empty-payload path alike. The same contract is now pinned in
      `asm/tests/test_p2p.c` for the x86 side, which until today still declared
      the two-argument form.
- [x] **Defect 3 (why this took a detour): a config warning that lied.** Every
      line was pre-parsed numerically, so any key whose value is not a number
      announced `connect=192.168.5.242:8332 is not a usable number -- reading it
      as 0` at boot -- false, `cfg_addlist()` had parsed host and port
      perfectly and stored 8332. The DMN-9 verdict is now taken at the parse and
      cashed in by the key that needed the number (`clamp_int` for integers, an
      explicit report in the handful of BTC/kvB branches that use `atof`).
      Checked against a probe conf: `dbcache=abc`, `bmc.dialratelimit=lots`,
      `maxconnections=99999999999999`, `dustrelayfee=nope` still all warn;
      `connect=`, `addnode=`, `bind=`, `wallet=` are quiet and parse right.
- [x] Native build green: `port/osx/build_daemon.sh` → LINK OK, no new warnings
      from the changed blocks.
- [x] Deploy home updated (`bmcbitcoind` replaced, previous binary kept as
      `bmcbitcoind.pre-fix-20260914`), conf corrected to :8333, node left

### Open, deliberately not touched today

- **The serve parent has no dial memory at all.** `g_dialmem` is mmap'd by the
  parallel downloader (main.c ~6058) and by the download worker (~7119) only, so
  every gate at `mux_next_peer`/`dh_reserved_pick` reads NULL in the parent's own
  mux loop, and its POLLHUP re-dial (~9910) does not even note the failure. The
  manual-peer floor added today bounds that loop now; the memory should be
  created once, in the parent, before it forks.
- **x86 test sweep on the reference box before this merges:** `test_redial`
  (re-dial a dead leg), `test_outbound_mux`, `test_p2p` (now asserting the
  4-argument hook), `test_dial_memory`, `test_node_config`. `test_redial` and
  `test_outbound_mux` drive the parent mux, where `g_dialmem` is NULL, so the
  new gate is inert there by construction -- if either fails, that assumption is
  what broke, not the gate.
- A local loopback repro of the leg-rotation phase is worth having: an empty
  datadir never reaches it (measured against a fake accept-and-close peer: 4
  dials in 30 s from the header-fetch phase, against the deploy's 4.5 a second
  once the download worker owns the legs), so today's proof of the gate is
  code-level plus the unit harness, not an e2e soak.
