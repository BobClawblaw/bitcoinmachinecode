## The delete path timed in parts: a transaction's outputs in neighbouring slots

Run 46's `put.del` was ~480 ns per spent input over 575k-875k, about half of
`put`. A 60 s perf of the applier (pdiag, main's code, ~740k) left most of it
unattributed -- the asm has no unwind info and `memcmp_asm`/`utxo_hash` are
shared with the lookups -- so a diagnostic branch (40cbd3c1, not merged)
timed `utxo_lsm_del` in parts with `rdtsc` and counted the probes, on a fresh
sync (pdiag2). Over 575k-793k, 1.2 billion deletes, 79% of them memtable hits:

| part | ns per delete |
|------|---------------|
| WAL append | 16 |
| memtable delete | 190 |
| tombstone step | 124 |

330 of the bench line's 478 ns; the rest is the call and the timer brackets.
A hit's backward shift scanned 10.8 slots, re-hashing each entry (an 8-step
FNV byte loop and a `div`) and moving 2.9 of them with a per-byte copy; the
tombstone probe took 1-6 steps a call, each a random read of `tomb_buf`.

Cause: the memtable, the tombstone set and the in-block index all placed a
key at FNV(txid[0..8]) XOR index under the mask. The index flips only low
bits, so a transaction's outputs sat side by side and every multi-output
transaction made a run of full slots, which linear probing and the backward
shift walk. The FNV part alone spreads evenly (2^23 random txids: 6,600,357
distinct home slots, uniform expectation 6,601,320).

The fix (branch perf/2026-10-10-memtable-hash):
- `utxo_hash`, the tombstone probe and `outpoint_hash` (the in-block index):
  (txid bytes 0..7 XOR index) times 0x9E3779B97F4A7C15, bits 32.. under the
  mask. The txid needs no hashing of its own; the multiply carries the index
  into every bit above it. Nothing persists a slot position: the checkpoint and
  the WAL hold records, reload re-puts them, the tombstone set is rebuilt from
  `tomb_buf`, the frozen copy is probed by the same functions. The Bloom hash
  (`mac_bloom_h`) is in the run files and is unchanged.
- The backward shift computes each entry's home slot inline (no call, no
  `*48`, no `div`).
- `memcpy_asm` and `mac_memcpy` are `rep movsb` (FSRM), `memcmp_asm` compares
  8 bytes at a time; all three were per-byte loops (~6% of the applier's CPU).

`tests/bench_utxo_probe` (single-output keys, so the probe lengths are the
same on both sides; this is the per-operation cost alone), 2^26 slots:

| | main | fix |
|---|---|---|
| put, 50% load | 194 ns | 119 ns |
| get hit, 50% | 196 ns | 122 ns |
| get miss, 50% | 84 ns | 63 ns |
| get hit, 75% | 208 ns | 131 ns |
| get miss, 75% | 200 ns | 181 ns |

`tests/test_utxo_hash_spread`: 2^20 slots at 50% from 8,192 transactions of 64
outputs; mean run holding a key 5.08 and longest 40 with the fix, 328 and
1,728 with the old hash (A and B fail). Half the transactions deleted, the rest
read back, the deleted half re-put: with the shift loop's inline home slot
missing its `shr` those checks fail (46,814 / 80,192 wrong).

Also seen in the profile, not changed here: the applier waits on the coinstats
fold worker's ring (`ring_push`, 42% of its context switches, booked under
`csi`), and SHA-256 is ~14% of its CPU.

## Run 47: deletes 42% faster, inserts twice as slow, ready 174 s later

Run 47 synced this branch (82d8a98a) from scratch. PASS: muhash identical to
Core's at 970,816. Ready 12,049 s, against run 46's 11,875 s; daemon CPU
20,265 s (run 46: 20,602). Stage sums, run 46 -> run 47, in seconds:

| heights | put.del | put.ins | apply total | wall |
|---------|---------|---------|-------------|------|
| 0-575k | 456 -> 257 | 143 -> 219 | 2,503 -> 2,383 | 3,447 -> 3,467 |
| 575k-875k | 897 -> 489 | 240 -> 425 | 4,904 -> 4,748 | 5,824 -> 5,945 |
| 875k-tip | 281 -> 194 | 82 -> 146 | 2,259 -> 2,288 | 2,533 -> 2,568 |

The delete did what the counters said it would (-695 s). The insert lost
323 s: the old hash put a txid's outputs side by side, so the insert of
output k+1 found output k's line loaded; spread, each insert is its own miss,
and nothing warms an output's slot the way idxbuild_on_input warms a spend's.
The apply total fell 247 s, but the wall rose: run 47's applier caught up to
the download more often (lag under 50 at 14 heartbeats, run 46 at 7; mean lag
261 against 383), so between blocks it waited on peers.

Fix: idxbuild_on_output prefetches the output's home slot a phase before
STAGE B's insert, as idxbuild_on_input does for the spend.
