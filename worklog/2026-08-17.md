# 2026-08-17

## Built-in multi-peer catch-up (dl_catchup) — committed to main (3ab60ca)

Replaced the external `unified_ibd.c` / `hole_ranges.py` / `backfill_holes.sh`
/ `sync_chain.sh` pipeline (built earlier this session as a standalone tool)
with a version of the same engine ported directly into `asm/daemon/main.c`, so
`bitcoind serve` self-heals archive holes and catches up to the real chain tip
on its own — no external tooling required for normal operation.

New in `main.c`:
- `dl_catchup(dir, min_workers)`: orchestrator. Sources peers via the
  existing `dl_bootstrap`/`dl_pool_from_book` (DNS-seed bootstrap into the
  persisted `amr` address book — the same discovery `serve_download_worker`
  already used), extends `headers.dat` incrementally (resumes from the last
  stored header, not a genesis refetch), computes the current archive gap
  directly from `index.dat` as ONE combined span (any hole below the stored
  tip + everything missing up to the real tip), then forks `>=8`
  chunk-claiming workers to fill it.
- `dlc_worker`: pulls 200-block chunks from a shared `mmap`'d atomic counter
  (`__sync_fetch_and_add`) — work-stealing, so a worker on a fast peer just
  keeps claiming more chunks instead of idling on a static pre-split shard.
  Skips any chunk that's already fully archived (`dlc_chunk_all_present`),
  so the same span safely covers real gaps and already-filled heights in one
  pass. Persistent connection reused across chunks instead of
  reconnect-per-chunk.
- `dlc_probe_round`: bounded non-blocking-connect liveness probe (mirrors
  `serve_download_worker`'s existing technique). This is deliberately the
  ONLY peer source for `dlc_headers`/`dlc_worker` — no fallback to raw
  unconfirmed pool entries, because `tcp_connect_ip` is a plain blocking
  connect with no connect-phase timeout and a black-holed host can hang it
  for minutes (hit this directly during testing — a header-phase fallback to
  unconfirmed peers stalled the whole synchronous boot for 3+ minutes on one
  bad candidate before the fix).

Replaces the old single-peer, 60s-capped `outbound_catchup()` call at
serve-mode boot. Runs synchronously (user's explicit choice over a
background-serve-immediately alternative): the node won't accept any
connection until catch-up finishes, which needs no writer-coordination with
the steady-state download worker since they never run concurrently.

Debugging notes from getting this right:
- First version's liveness probe dialed the WHOLE discovered pool (100+) at
  once and only found 1/140 live — capping the simultaneous-dial burst at
  `MUX_MAX_OUT*3` (matching `serve_download_worker`'s own proven cap) didn't
  fix it; the real fix was running several bounded rounds (8s poll each)
  instead of one shot, since real peer handshakes often take longer than a
  few seconds to complete.
- Header-phase success check was wrongly `added>=0` instead of `added>0`
  (matching `unified_ibd.c`'s own fork-based convention) — a peer returning
  exactly 0 new headers on an empty store was being treated as "done"
  instead of "try the next candidate."

`unified_ibd.c` itself picked up the same work-stealing engine (dynamic
chunk claims via the shared counter, `chunk_all_present` skip-check,
persistent connections, and a much deeper peer pool — `MAXPEERS` raised from
24 to 160, loading all of `good_internet_peers.txt` instead of just the first
24, plus a live-retry fallback for peers marked down at the one-time startup
probe) — kept as a standalone ops tool, no longer load-bearing for the daemon.
New driver scripts: `hole_ranges.py` (finds gaps in `index.dat`, has a
`--span` mode), `backfill_holes.sh` (one combined-span `unified_ibd` call
over current holes), `sync_chain.sh` (chains hole-fill into extending to the
real tip via a sentinel `end_h` that auto-clamps to the true header count).

Verification: two isolated smoke tests against a fresh scratch store —
(1) empty store, fresh bootstrap, full pipeline through to `serve_mux`'s
"serving on port" handoff; (2) re-run against the same partially-filled
store, confirming incremental header resume ("already current") and the
combined span correctly narrowing to just the remaining gap. Both clean,
zero holes after.

## index.dat scans ported to asm (bitcoin_idxscan.asm), benchmarked, deployed

`dl_catchup`'s archive-gap scan (`index.dat`'s 48-byte positional records,
first-4-bytes-non-zero = present) runs every 10s status tick and every worker
chunk-claim, and was reimplemented separately 5 times in C plus twice in
Python. Consolidated into `asm/bitcoin_idxscan.asm`: `idxscan_tip`,
`idxscan_first_hole`, `idxscan_all_present`, `idxscan_progress`.

First cut (one `pread64` syscall per record) was a REGRESSION — 2-15x
slower than the C baseline's buffered `stdio` `fread`, since glibc already
amortizes its own `read()` syscalls across a ~4KB window. Fixed by batching
into a 192KB static buffer (4096 records/read, scanned in memory) — had to
go bigger than stdio's own window to actually win. Also hit the project's own
documented golden rule directly while fixing this: placed two scratch locals
in `idxscan_progress` at `[rbp-8]`/`[rbp-16]` without allocating stack space
first, silently corrupting the saved `rbx`/`r12` in the callee-saved save
area — caught via a `-O0 -g` debug rebuild + gdb backtrace before it ever
touched the live daemon.

Verified byte-identical to the C originals on the live archive
(`asm/tests/bench_idxscan.c`, snapshots `index.dat` first so it's safe to run
against the concurrently-writing daemon — an initial run without the
snapshot showed a spurious 1-record mismatch that was just the live writer
landing a block mid-comparison, not a real bug). Benchmarked on the real
~814k-record archive: `idxscan_tip` 47.6x, `chunk_all_present` 43.6x,
`idxscan_first_hole` 4.5x, `idxscan_progress` 4.0x faster than the C
versions.

Swapped `main.c`'s four `dlc_*` functions to delegate to the asm exports,
smoke-tested the full daemon (not just the bench harness) against a scratch
copy of the real archive for 40s under `timeout`, then killed and relaunched
the live production daemon on the new binary. Confirmed via log: resumed
cleanly at 816152/962831 (84.77%), no crashes, all 16 workers active.

## build_hash_index ported to asm — found and fixed a critical idx_hash bug

Next asm-conversion candidate: `build_hash_index` (the boot-time O(1)
hash->height index build used for `getdata`-by-hash serving) — 185.9s on the
real archive, paid on every `serve`/`follow` boot before the node can accept
any connection. Wrote `idx_build_from_file` (`asm/bitcoin_idx.asm`, buffered
pread64, same approach as `idxscan`) to replace the per-record C loop.

Benchmarking it in isolation surfaced something much bigger than the C-loop
overhead: `idx_put` on 400,000 real block hashes took 15.8s vs 0.04s for
400,000 synthetic random hashes into the identical table — a data-dependent
pathology in `idx_hash` itself, not the new conversion (confirmed via a
synthetic control test). Root cause: `idx_hash` only hashed the first 8
bytes of the 32-byte key, and every real block hash's leading bytes are
near-zero by proof-of-work construction, so real inputs carried almost no
entropy in that window — dumping the actual bytes showed literal
`0x00000000` first-4-bytes on every sampled record. An XOR-fold attempt (to
counter FNV-1a's separately-known weak low-bit avalanche) didn't help, since
the real problem was insufficient entropy going in, not output mixing. Fixed
by hashing all 32 bytes.

Real-archive result: full-archive index build went from ~186s to ~0.1s
(~1800x). Since `idx_get` shares the same hash function, this also speeds up
every live `getdata`-by-hash lookup during normal serving, not just boot —
this bug had likely been silently degrading production serving performance
the whole time, unrelated to anything in today's dl_catchup work.

Added a permanent regression guard to `asm/tests/test_idx.c` (500,000 keys
sharing an identical first-8-byte prefix at production table scale) —
verified it actually discriminates by temporarily reverting `idx_hash` and
confirming the test times out, then restoring the fix and confirming it
passes in ~0.13s. Along the way, found and cleaned up several stale
ROOT-OWNED `/tmp/*test*` scratch directories (leftover from an earlier
root-run `make test`, unrelated to this work) that were causing unrelated
test failures (`test_cli`, `test_addrmgr`) and blocking verification. Full
`make test` now green (65/65 harness blocks, `MAKE_EXIT=0`).

Swapped `main.c`'s `build_hash_index` to call `idx_build_from_file`, smoke-
tested via gdb directly against the compiled daemon binary and the real
archive (826,746 heights indexed, no crash), then redeployed to the live
production daemon (killed + relaunched, resumed catch-up cleanly). The fix
takes effect the next time this boot reaches `build_hash_index`, once
catch-up finishes.

## check_chain.c O(n²) dup detector fixed + chainctl.c archive_tip swapped

Third asm-adjacent fix today, found via a fresh candidate survey:
`check_chain.c`'s duplicate-block-hash detector (a standalone integrity-audit
tool, not the live `dl_catchup` daemon) was genuinely O(n²) despite its own
comment claiming O(n) — a nested loop doing a linear scan against every
previously-seen hash for each new record. At the real archive size
(~962,831 blocks) that's ~4.6×10^11 comparisons, and `chainctl.c` reruns
`check_chain` after every ~8000-block chunk during a full IBD, so the cost
compounds badly across a run.

Fixed by reusing `idx_init`/`idx_put` (`bitcoin_idx.asm`, already written and
validated earlier today for `build_hash_index`) instead of the manual
nested-loop scan — turns O(n²) into O(1)-amortized-per-insert. Also swapped
`chainctl.c`'s `archive_tip()` (a per-record `fseek`+`fread` backward scan,
same superseded pattern `idxscan_tip` already replaced elsewhere) to call
`idxscan_tip()` directly via a chdir-in/chdir-out wrapper.

Benchmarked on real truncated archive slices (validated the O(n²) fit first:
50k→0.36s, 100k→1.46s, 150k→3.26s, 300k→13.09s, 400k→23.30s, matching a
quadratic curve almost exactly) vs the new O(n) version at the same sizes
(50k→0.007s, 400k→0.089s). Full real archive (879,800 stored records):
extrapolated old ~135s vs measured new 0.198s (~680x, and the gap only
grows as the archive does). Cross-checked correctness two ways: dup counts
matched the old version exactly at every tested scale, AND the full-archive
run reported `duplicate rec: 19192` — exactly the duplicate-hash count
found independently during the `idx_hash` investigation earlier today.

One close call: an early verification attempt ran the real `chainctl`
binary directly against the live production `data/` directory to sanity-
check `archive_tip`, which immediately spawned 8 `unified_ibd` workers
against the same archive the live `dl_catchup` daemon was actively writing
to. Killed immediately (no corruption — flock-based append coordination
would likely have protected the archive either way, but the extra network/
disk load and process contention was unintended). Redid verification safely
via gdb calling `archive_tip()` directly against a scratch copy instead.

Full `make test`: 65/65 harness blocks green, exit 0 -- these C-only
changes touch no asm files already covered by the suite, and the two
rebuilt binaries (`check_chain`, `chainctl`) aren't Makefile/test-suite
targets (built manually, same as before this change).

## crawler.c fork-state bug fixed; addrgather.c investigated and left alone

Fifth pass today. After a fresh survey found no strong "next check_chain"
(mempool policy has the right O(n^2) shape but zero daemon call sites --
tx-relay isn't wired up yet, so nothing to benchmark against in production),
picked up a real correctness bug the survey noticed in passing instead:
`crawler.c`/`addrgather.c` both `fork()` per-seed workers, and the agent's
read was that per-worker state never propagates back to the parent, so the
final report/output file is always empty.

Verified this carefully rather than taking the characterization at face
value, since the two files turned out to be genuinely different:
- **`crawler.c`**: confirmed correct. `seen[MAXSEEN][40]`/`seen_n` were a
  plain static array -- each `fork()`'d child got its own copy-on-write
  private copy, so every `mark_seen()` a child did was invisible to the
  parent. `out_file` was always written empty; "crawl complete: N distinct"
  always reported N=0. (The live discoveries themselves weren't lost --
  each child's `printf()` goes through the inherited, genuinely-shared
  stdout fd -- only the in-memory dedup table and the file/summary built
  from it were broken.)
- **`addrgather.c`**: NOT broken the same way. Read `bitcoin_addrmgr.asm`'s
  `amr_add`/`amr_count`: both are entirely file-backed via a single fd
  (`peers.dat`, opened once in the parent before fork) -- there's no
  in-memory table to lose across fork at all. Verified empirically with a
  throwaway local probe (fork N children, each calls `amr_add`, check the
  parent's `amr_count` after `waitpid`): state correctly survived fork
  every time. Also stress-tested the theoretical concern (concurrent
  children sharing one fd's file offset, unprotected `lseek`+`write`) two
  ways -- distinct IPs from 40 concurrent children (expect all 40 present)
  and the SAME IP from 40 concurrent children (expect exactly 1, testing
  the dup-check race) -- 5/5 trials each, zero lost writes, zero
  duplicates. Left it alone: fixing code that isn't actually broken isn't
  the goal, and the empirical evidence didn't support the original
  characterization for this file.
### Fix (crawler.c only)
Moved `seen[]`/`seen_n` into a `MAP_SHARED|MAP_ANONYMOUS` mapping created
in the parent before the fork loop, so every child inherits the same
physical pages instead of a private copy. The check-and-insert itself
still needs cross-process mutual exclusion (two children could otherwise
both pass `is_seen()` for the same endpoint before either calls
`mark_seen()`, or race on the shared `seen_n` slot index) -- guarded with
`flock()` on a dedicated lock file derived from the output path
(`<out_file>.lock`). Per the flock lesson already learned elsewhere in
this codebase: each child opens its OWN fd to the lock file rather than
inheriting one from the parent, since flock locks belong to the open file
description, not the path -- a fork-inherited fd would not actually
exclude siblings from each other.
### Verified
Wrote a throwaway probe mirroring the exact mechanism (30 concurrent
children, each marking 3 endpoints distinct to itself plus 2 shared across
every child, exercising both the propagation fix and the dedup-race guard
together): parent's final count and the written `out_file`'s line count
both correctly landed on 92 (=30*3+2) across 3/3 runs -- previously would
have been 0/empty. Full `make test`: 65/65 green, exit 0 (crawler.c isn't
a Makefile/test-suite target, built and verified manually).

## secp256k1_fe.asm: mulx-based fe_mul, shipped as a small verified win

Different kind of investigation today: not more C-to-asm conversion, but
whether EXISTING asm crypto primitives could be faster with better
instruction selection. Survey found `fe_mul`/`fe_sqr` (secp256k1 field
multiplication, the single most-executed operation during ECDSA verify)
still using plain schoolbook `mul`/`adc` -- no BMI2 (`mulx`) or ADX
(`adcx`/`adox`) despite the host CPU (AMD Ryzen 9 9950X3D) supporting both.
`sha256.asm` was separately confirmed already optimal (CPUID-gated SHA-NI
hardware path, already dispatching correctly on this host).

Given the correctness stakes (this underlies every signature verification
in the node), took the conservative option: swapped `mul` for `mulx` in
`fe_mul`'s Phase 1 (the 256x256->512-bit schoolbook multiply) while
leaving the accumulation structure and the entire Phase 2 reduction
byte-for-byte untouched. Deliberately did NOT attempt the more aggressive
parallel double-carry-chain restructuring (`adcx`/`adox` running two
independent accumulation streams) that would be needed to actually realize
the ~20-35% BMI2/ADX typically gives on this pattern -- that requires
reworking the accumulation itself, not just the multiply instruction, and
carries meaningfully higher risk of a subtle bug on security-critical code.

### Verification (before trusting this anywhere near production)
- Built the OLD (pre-edit) fe_mul under renamed symbols
  (`objcopy --redefine-sym`) to compare side by side with the new version
  in one binary.
- Wrote an independent third reference implementation (plain
  `__uint128_t` schoolbook multiply + fold-reduction, NOT transcribed from
  either asm version) as a second witness.
- 100,000,000 random trials (plus fixed edge cases: 0, 1, p-1, p itself,
  and all pairwise combinations; plus forced-out-of-canonical-range
  operands on a fraction of trials) comparing new vs old: **zero
  mismatches**. Independent-reference cross-check on a subsample: zero
  mismatches there too.
- Full `make test`: 65/65 green (covers real ECDSA/Schnorr/multisig/P2SH/
  taproot vectors, not just synthetic fe_mul cases).
- Confirmed `cons_verify` (used by `dl_catchup`'s live block download)
  does NOT call into secp256k1/fe_mul at all -- purely structural
  validation (PoW/merkle/txid), so this change has zero interaction with
  the currently-running live daemon. Confirmed separately that
  `secp256k1_fe.o` isn't part of `DAEMONOBJS` at all (only test binaries
  and `wallet_cli`/`KEYSOBJS`) -- no live-daemon redeployment applicable.

### Benchmark: modest, reported honestly
| | old (`mul`/`adc`) | new (`mulx`) | speedup |
|---|---|---|---|
| fe_mul throughput (20M calls) | 82.5 Mops/s | 83.7 Mops/s | **1.015x** |

Far short of the ~20-35% a fuller BMI2/ADX rewrite could give -- the
serial dependency between each term's carry-out (threaded through one
register across all 4 terms of a row) was always the real bottleneck, and
swapping the multiply instruction alone doesn't break that chain. Reported
this honestly rather than oversell it.

**Superseded same day by v2, below** -- decided to examine the fuller
rewrite after all rather than stop at v1.

## secp256k1_fe.asm v2: adcx/adox parallel-chain fe_mul (supersedes v1 above)

Before attempting the fuller rewrite, measured where fe_mul's time
actually goes (rather than trusting the general BMI2/ADX literature
figures at face value): built a Phase-1-only variant and timed it against
the full function. Result: **Phase 1 (the multiply) is ~81% of total cost,
Phase 2 (reduction) ~19%**. This sets a real ceiling -- even a perfect
Phase-1 speedup can't beat that 81% share -- and translates the
literature's ~25-30% Phase-1-only figure into a more realistic **~20-25%
end-to-end estimate** for this specific codebase's reduction strategy.

### Design
Four independent row computations (`a[i] * B`, each a 1x4->5-limb
product), rows 0/2 accumulated via the `adcx` chain (CF), rows 1/3 via
`adox` (OF) -- since two rows using DIFFERENT flags share no dependency,
the CPU's out-of-order engine can overlap e.g. row 1's `mulx`/`adox` work
with row 0's still-retiring `adcx` chain. This is the actual mechanism
BMI2/ADX speedups come from; v1's mulx-only substitution kept everything
on one serial chain, which is why it barely moved the needle. Each row
writes to its own scratch buffer; the 4 rows are then combined into the
final 8-limb product via a separate, ordinary `add`/`adc` merge (deliberately
low-risk: same ripple-carry style already proven elsewhere in this file).
Every row's chain opens with `xor ecx,ecx` (clears both CF and OF) so no
row can inherit a stale carry left by an earlier row sharing its flag
(rows 0 and 2 both use CF and must not leak into each other).

### A real bug caught by the verification pipeline
First build crashed on the very first call: `sub rsp, 224` in the
prologue (the row buffers need more scratch than v1's 64 bytes) but the
epilogue still had the old `add rsp, 64` -- a 160-byte stack mismatch that
corrupted the return address on every single call (`rip=0`, every register
zeroed, per gdb). This is precisely the codebase's own long-documented
"golden rule" class of bug, just from a mismatched prologue/epilogue pair
rather than a scratch slot overlapping the save area. Caught immediately
by the verification harness (first run: zero output, straight segfault) --
never got near make test, let alone production. Fixed by matching the
epilogue's `add rsp` to the new allocation size; re-verified clean after.

### Verified (same rigor as v1, repeated against the TRUE original)
- Built the true original (pre-any-change, `git show HEAD:...`) under
  renamed symbols for a clean side-by-side comparison, plus the same
  independent `__uint128_t` third reference used for v1.
- 150,000,000 random trials + edge cases: zero mismatches vs. the
  original, zero mismatches vs. the independent reference.
- Full `make test`: 65/65 green.
- Same live-daemon-independence facts as v1 still hold (`cons_verify`
  doesn't touch secp256k1; `secp256k1_fe.o` isn't in `DAEMONOBJS`).

### Benchmark and an honest diagnosis of the gap
| | original | v2 (adcx/adox) | speedup |
|---|---|---|---|
| fe_mul throughput (30M calls) | 83.8 Mops/s | 94.7 Mops/s | **1.13x** |

Better than v1 (1.015x) but short of the ~20-25% estimate. Traced why by
isolating the row-computation cost alone: it really did get the hoped-for
parallelism win, ~44% faster (0.3035s -> 0.1693s per 30M calls) -- but the
separate merge pass this design needs (since rows write to independent
buffers rather than accumulating in place) costs ~0.078s, consuming
roughly 58% of the raw row-computation savings. The clean row independence
that made the parallel chains safe to reason about is also what gives most
of the gain back. A design that accumulates in place while still using two
chains could close that gap further, but reintroduces much of the
complexity/risk the independent-rows approach was chosen to avoid, for a
return that's already diminishing at this point -- not pursued.

### Decision
Ship v2 (1.13x, fully verified) in place of v1 (1.015x). Not pursuing a
further merge-eliminating redesign of this specific function.
