## CUDA acceleration workbench (asm/cuda/) — committed to main

Added an experimental CUDA acceleration tier for the crypto core, built and
verified on this host (RTX 5090, SM 12.0, CUDA 13.3). Scope is a working,
correctness-first batch SHA-256/SHA-256d accelerator plus an auto-detecting,
fallback-safe dispatcher. NOT yet wired into the assembly node binary — hash
batching is exercised via C harnesses only. The assembly crypto remains the
always-on correctness anchor.

Components (`asm/cuda/`):
- `cuda_sha256.cu` + `cuda_sha256.h`: batched SHA-256 / SHA-256d kernel
  (1 thread per message, FIPS 180-4) + opaque host ABI. Correctness-first scalar
  body; output bit-for-bit identical to the assembly oracle.
- `libbmc_cuda.so` (build target): kernels + launchers built as
  a runtime-dlopen'able shared object, exporting the C symbols the dispatcher
  resolves via dlsym.
- `cuda_autodetect.c`: single gated entrypoint `bmc_sha256d_batch(out, msgs, idx,
  count)`. Probes once (cached): dlopen libbmc_cuda.so + cudaGetDeviceCount for a
  real "any usable device" check. Routes to CUDA only when (device present AND
  count >= 512 amortization threshold AND not BMC_CUDA=0); on any CUDA error, no
  device, or small batch, falls back bit-exact to the proven asm `sha256d` loop.
  Introspection: `bmc_cuda_detected()`, `bmc_cuda_was_used()`.
- `cuda_verify.cu`: correctness gate vs the repo's own assembly oracle over FIPS
  vectors, every Bitcoin padding edge (len 55/56/57/63/64/65), a 200B and 1000B
  message, and 10,000 random messages (sha256d). ALL PASS, 0 failures.
- `cuda_bench.cu`: honest whole-batch wall-clock comparison vs asm `sha256d`.
  Measured 17-18x GPU/CPU at N=1,000,000; ~3.4x at N=1,000; CPU wins at N=100
  (~0.6x) — the crossover confirms the batch-only fit (GPU never helps single
  hashes vs SHA-NI). Note: numbers dip when the shared RTX 5090 is under vLLM
  load.
- `cuda_autodetect_test.c`: routing + digest matrix, fresh process per mode
  (probe state is cached). default -> CUDA, BMC_CUDA=0 -> CPU, batch 100 (<
  threshold) -> CPU, BMC_CUDA_LIB=/nonexistent -> CPU fallback. Digests match the
  asm oracle in every mode. ALL PASS.
- `Makefile`: `make verify` / `make bench` / `make detect` / `make all`.
- `WORKING.md`: full feasibility analysis + ranked roadmap (hashing Tier 1/2,
  secp256k1 batch-verifier Tier 3, HMAC/BIP32 Tier 4), integration seam, and the
  audit stance.

Verification (fresh rebuild, `make all`):
- cuda_verify: ALL PASS (0 failures)
- cuda_bench: cross-check OK; ~17-18x at 1M (unloaded), dips under GPU load
- cuda_autodetect_test: ALL PASS (routing + digests, 0 failures)

Build artifacts (`cuda_verify`, `cuda_bench`, `cuda_autodetect_test`,
`libbmc_cuda.so`) are *.o/*.so/binary and git-ignored; only sources + docs are
tracked. To rebuild: `make asm` (for oracle objects) then `make all` in
`asm/cuda/`.

Deliberately NOT wired into `bitcoind`/`bitcoin_cli` yet; that is the Tier-1 next
step and should get its own card. Per KANBAN convention, the CUDA path stays
optional/behind the runtime probe until a full mainnet IBD runs hash-for-hash
against the CPU path in a differential CI.

## Refined CUDA roadmap recorded in PLAN.md §12 (no kanban impact)

After the txid-offload PoC (cuda_txid_poc.py, commit f8db03f) proved per-block GPU
offload is slower, refined the deferred CUDA candidates in PLAN.md §12. Key
conclusion recorded: CUDA pays ONLY on large batches of independent hashing in
CPU-bound OFFLINE work; live IBD is network/disk-bound and is NOT a CUDA target.
Ranked deferred candidates: A) bulk PoW/header re-audit (best, ~18x, kernel
exists), B) cross-block txid/re-index recompute (build-out of the PoC), C)
address/key-derivation scale-out (needs RIPEMD-160 batch kernel), D) secp256k1
ECDSA/Schnorr batch verify (big, most value). NOT targets: live IBD, per-block
cons_verify, single hashes, per-derivation HMAC. Kanban board and running corpus
untouched.

Decided (per request) NOT to start the CUDA->node Tier-1 wiring now, to avoid
interrupting the running kanban batch. The remaining integration roadmap
(Tier 1 wire bmc_sha256d_batch into the node; Tier 2 secp256k1 batch verifier;
Tier 3 HMAC/BIP32/BIP39 batch) is recorded in `PLAN.md` section 12 as DEFERRED,
gated on a free worker. The asm/cuda/ accelerator itself remains committed and
pushed to main (`24da54b`); only the node hookup is deferred.

## Differential-consensus gate: outcome + honest post-mortem (t_a6b10dab -> done)

The broad differential-consensus corpus run (card `t_a6b10dab`, the compliance
gate that DEFINES "done") was stalled for hours, then unblocked and completed.
Honest record of what happened and what it does/doesn't mean.

**1. The gate was un-runnable until fixed (the real blocker).** Every corpus run
aborted on two harness bugs, not on row work:
  - IndexError on short/malformed shim output (unguarded per-surface parsing)
  - BrokenPipeError when a consensus_shim subprocess died mid-conversation
These were infrastructure fragility that prevented the gate from completing at
ANY worker count. Fixed in b9698ad (ShimDied exception, respawn-and-retry once,
defensive parsing on every surface, shim_crash degrade path). The "slow card" was
actually a CRASHING card; the crash-tolerance fix (not more workers) is what made
completion possible.

cleanly in ~40 min (2406.4s):

  MUT run=37 agree=37; divergences = 0.
Report: validation/corpus_diff_report.{json,txt} (2026-08-16T01:55Z).

~40 min) is strong signal, not completion. Full-chain, hash-for-hash differential
across the ENTIRE chain is still REQUIRED before consensus can be called done.
That remains the honest gate.

Downstream card t_c13d882d (540GB full-chain ingest) is now unblocked.

**Next step (recommended, not started):** run the FULL-chain differential (all
