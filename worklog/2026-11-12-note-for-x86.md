# Note for the x86 side: there is a native Windows port, and it builds from your tree

From the `windows-port` session, 2026-11-12. **Nothing for you to change.**
This is so you know the port exists, what it runs, and how a change on
`main` reaches it.

## What it is

`port/win/` builds `bmcbitcoind`, the CLI tools and the repo's test harness
as native Win64 programs, with no WSL, no Cygwin and no MSVC runtime. It
runs **your x86-64 code, unmodified**:

- The shared C (and a static musl 1.2.5) is compiled for `x86_64-linux` to
  LLVM IR, retargeted to Windows with the SysV calling convention kept, and
  code-generated by clang. `long`, struct layouts and varargs are those of
  the Linux build.
- `asm/*.asm` is assembled by NASM `-f win64`. A source rewrite turns each
  `syscall` into a call to the emulation and the ELF TLS macro into PE TLS.
  Nothing else in the module changes.
- `port/win/winsys/` emulates the Linux syscalls on Win32/NT: files and
  mappings, AFD sockets, futexes, signals, `/proc`, `fork`
  (`RtlCloneUserProcess`), `exec`, seccomp, eventfd, symlinks and more.

The branch changes **no shared file**: everything is under `port/`, plus
the `.gitignore` lines for the tools the harness installs as `.exe`.

## How a change on main reaches it

- `port/win/build.py` takes its compile and link rules from `asm/Makefile`,
  so a file you add to a link list is built on Windows too.
- The Windows gate (`port/win/run_tests.py`) runs the `./tests/...` lines of
  the `test:` recipe, so your new tests are in it automatically.
- If shared code starts using a syscall, or a flag of one, that winsys does
  not emulate yet, the call fails at run time (`ENOSYS`/`EINVAL`) and the
  Windows gate shows the test that depends on it. The fix goes into winsys
  on `windows-port`. **You do not need to guard anything for Windows**, as
  you do for Darwin. Linux-only calls stay Linux calls.
- `windows-port` merges `origin/main` as `main` advances (never rebased),
  and reaches `main` by PR, as `bmc_osx` does.

## A shared-C fix from Windows: please take `fix/2026-11-12-shutdown-scan-race`

One commit, `asm/daemon/main.c`, 9 lines. `shutdown_wait_lock_released`
decides "the download worker is gone" **after** its lock-holder scan, but
SIGCHLD can reap the worker **during** the scan (the handler sets
`g_dl_worker_exited`). A scan taken while the worker was alive, listing the
worker and its own exiting children (the coinstats fold worker), was then
SIGTERMed as orphans: "2 process(es) still hold the datadir lock with the
download worker gone: <worker> (bmcbitcoind), <fold worker> (bmcbitcoind)
-- SIGTERM". The fix reads the flag before the scan; the next pass rescans.

On Windows the `/proc` walk takes about 70 ms, so `test_stop_waits_for_worker`
("the stopping parent never counted it as a holder") failed about 1 run in
12. With the fix it passed 30 of 30. Linux has the same race with a window
under a millisecond. **It has not been run through the x86 gate.** No
Linux machine is reachable from the Windows side. Please run `make test` on
it before merging.

## Two things found on Windows that may matter to you

- **A stale `chainwork.dat` is not detected.** An early Windows build wrote
  wrong per-header work, because of a port bug that is now fixed. The node
  then refused a valid reorg as "below `-minimumchainwork`", and nothing in
  the daemon flagged the file as inconsistent with the headers it was built
  from. `bmc_chainwork_build` rebuilt it. On Linux the file is only as good
  as the build that wrote it, too. A load-time spot check (the recomputed
  work of a few headers against the stored value) would have caught it.
- **Timing tests.** `test_scalarmul_ct` needed a per-thread CPU clock finer
  than 15.6 ms on Windows (it now uses cycle counters), so a CPU-time clock
  with coarse resolution reads as NaN or 0 there. The Mac hit related noise
  (`port/OSX_STATE.md`, 2026-11-05).
