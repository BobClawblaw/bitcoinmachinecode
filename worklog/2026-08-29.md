## filter builder: profiled, corrected, and honestly reported (`91bb745`)

- [x] **Diagnosis:** `strace` over 20 blocks counted **33,432 `munmap`,
      33,492 `mmap`, 33,406 `open`, 69,805 `pread64`** — ~1,670 full
      map-and-unmap cycles *per block*, one per prevout. The syscalls were
      never the cost; the **lock** was. `mmap`/`munmap` take `mmap_lock` for
      WRITE, so every resolver thread serialised, and each `munmap` shot down
      TLBs across all cores. That is why raising `BFI_THREADS` 8 → 64 had
      changed nothing. Mapping each blk file once takes those counts to
      **0 / 1,003 / 900 / 46**.
- [x] **Dedup:** inputs spending the same parent repeated the whole lookup,
      and round-robin striping handed consecutive inputs — the ones most
      likely to share a parent — to *different* threads with private caches.
      Grouping by parent txid: over 1000 blocks, 5,505,050 inputs collapse to
      4,577,099 distinct parents (**1.20x**).
- [x] **NO SPEEDUP IS CLAIMED, and that is the point.** A 1000-block run of
      the *unmodified* builder, repeated as a drift control, came in at
      **8.87 blk/s against 7.51 for the same binary earlier** and 8.54 for the
      best optimised variant. The spread between two identical runs exceeds
      the gap being measured, because the live daemon competes for the device.
- [x] **Measured and rejected:** batched `madvise(WILLNEED)` prefetch did
      exactly what it was designed to do — queue depth 7.5 → ~500 — and ran
      **5.67 blk/s**. The device delivers 12–17k reads/s whether the queue
      holds 7 requests or 533, so depth was never the constraint. Removed,
      with the numbers left as comments.
- [x] Same lesson twice more: adding `MADV_RANDOM` to the txid index was
      **2.2x slower**; removing it from the archive was also worse. Two
      mappings, opposite answers, neither guessable from byte counts.
- [x] **Corrected estimate:** ~8 blk/s measured, so the remaining ~194,000
      blocks is **~7 hours**, not the 50 the old log's decayed rate implied.

# BIP324 v2 encrypted transport — the crypto and framing layers

Five layers, each pinned against real published vectors before the next one
was written. Nothing here is wired into the p2p code yet; the daemon's
behaviour on the network is unchanged by this work.

| layer | vectors | source |
|---|---|---|
| ChaCha20, Poly1305, HKDF | RFC 8439 / RFC 5869 | landed earlier (`4fb7707`) |
| field square root | 61 | generated from Python `pow(a,(p+1)//4,p)` |
| ElligatorSwift decode | 76 | **official BIP324** `ellswift_decode_test_vectors.csv` |
| ElligatorSwift encode | 32 × 8 = 256 | **official BIP324** `xswiftec_inv_test_vectors.csv` |
| BIP324 ECDH | 7 | official packet-vector inputs, secret via Core's Python |
| FSChaCha20 / FSChaCha20Poly1305 | 3 + 2 | Core `crypto_tests.cpp` |
| full packet cipher | 7 | **official BIP324** packet vectors, end to end |
| transport state machine | property tests | two transports wired to each other |

## what the vectors caught

**`sqrt(-3)` was off by one nibble in every limb.** I transcribed
`0x47d8d27ae1cd5f85…`; it is `0x7d8d27ae1cd5f852…`. The map still returned
points genuinely on the curve — all three branches of xswiftec do — so nothing
short of a published x value could have shown it. Caught by checking against
Python before running the official vectors.

**The secret key was being reduced mod p.** `ellswift_be32_to_fe` reduces,
which is right for the field elements u and t and wrong for a scalar. A key of
`0xff…ff` is above the group order and must be REFUSED; reduced mod p it
becomes a small number that passes every range check and yields a public key
no other implementation agrees with. The boundary test (`n`, `n-1`, all-ones)
found it. Scalars and field elements are different types living in the same 32
bytes, and `be32_to_scalar` now says so.

**`chacha20_crypt` discards leftover keystream.** Correct for RFC 8439, where
every message starts fresh. Wrong for BIP324's length cipher, which encrypts
three bytes per packet out of ONE continuous stream. The FSChaCha20 wrapper
carries the partial block itself. Core's vectors check the pre-rotation output
against a continuous ChaCha20 for the full interval, which is exactly the
check that catches this — 4096 chunks on one vector.

**`next_message` blanked the string it had just handed out.** It returned a
pointer into `msg_type` and then zeroed `msg_type[0]` to mark the message
consumed, so every caller read an empty command name. Replaced with a separate
`msg_ready` flag. The handshake tests passed throughout; only checking the
delivered message type found it.

## the reporting trap, again

The first cut of the packet-vector test used a `cmp_hex` that printed nothing
on success. Session ids and garbage terminators were being compared and were
correct — but the log showed no line for them, so a vector field that had
failed to extract would have compared against an empty string, succeeded
vacuously, and looked identical. `cmp_hex` now reports every comparison and
treats a wrong-length expectation as a failure, and the test counts how many
vectors were checked in full versus by suffix and asserts the total.

Every vector extractor also cross-checks its own parse against an independent
count of the call sites in Core's source, and exits rather than emit a
partial set. A regex that quietly matches 5 of 7 vectors is the same failure
in a different costume.

## details worth remembering

- **The HKDF salt carries the network magic.** v2 has no plaintext message
  headers, so chain separation lives entirely in the key derivation. A mainnet
  and a testnet node exchange keys successfully and then never find each
  other's garbage terminator. Asserted directly in both test files.
- **The ECDH hash order is by role, not by who is computing.** Both peers hold
  the same two 64-byte strings in opposite local roles and must sort them the
  same way. A one-sided vector passes with the ordering inverted; the pair
  agreement test does not.
- **The garbage has no length prefix**, because a length would be structure and
  the whole point is that the stream looks like nothing. The receiver scans for
  a terminator it can only compute after the key exchange — bounded at
  4095 + 16 bytes, which is the one place in the handshake where a peer
  controls how much we buffer.
- **The version packet's AAD is the sender's garbage**, which is what binds
  those unencrypted bytes to the session. Flipping one garbage byte in flight
  is accepted at the time and breaks the version packet, which the test pins.
- **One differing byte in the first 16 proves v2.** A v1 peer always opens with
  magic + `version` + five NULs, so a responder may answer with its key
  immediately rather than waiting for 64 bytes. Tested at all 16 positions.

## memory checking

Both new test binaries are clean under ASan + UBSan, leaks included.

Valgrind is not usable on anything that reaches `sha256_full`: `sha256.asm`
uses the SHA-NI instructions (57 occurrences of `sha256rnds2`/`sha256msg1/2`)
and valgrind cannot emulate them, so the process dies with SIGILL. This is not
new and not ours -- the existing `tests/test_sha256` fails the same way. ASan
instruments rather than emulates, so it works fine. Worth knowing before
someone reads a SIGILL as a real defect.
