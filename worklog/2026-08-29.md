## deploy `al`: the second pre-deploy review (00:40–01:15)

Five more defects in the anon-networks work, on top of the seven found on
08-28. Committed as `0500925`:

- [x] **`externalip` was parsed, documented in the sample conf, and never
      read.** An operator behind a NAT set it and the node went on announcing
      whatever its peers claimed. This became the session's governing rule:
      *a setting that is accepted and then ignored is worse than one that is
      absent.*
- [x] **`dl_resolve1` refused every IPv4 literal when DNS was blocked** — on
      the theory that a literal behind a proxy leaks. It does not; there is
      nothing to resolve. What it actually did was drop the operator's own
      `addnode=`/`connect=` from both the book and the catch-up pool, and
      since DNS seeds are skipped behind a proxy too, **a proxied node could
      come up with no bootstrap source at all**.
- [x] `dlc_probe_round` opened raw sockets past a configured proxy.
- [x] Stream isolation applied only to onion dials; Core randomises SOCKS5
      credentials for every proxied connection.
- [x] **The first cut of the literal fix was itself wrong** — it dialled the
      address inline at the top of `outbound_connect` and returned, skipping
      the budgeted path below, where the SIGALRM dial budget wraps *both* the
      connect and the handshake and where `dial_fail_errno` carries the errno.
      `test_dial_budget` measured **46s against a 20s budget** and a bare
      "connect failed" where `ECONNREFUSED` belonged. The literal is now
      parsed early and dialled late: one dial path, one budget, one place the
      errno is reported.

## filter builder: profiled, corrected, and honestly reported (`91bb745`)

- [x] **Diagnosis:** `strace` over 20 blocks counted **33,432 `munmap`,
      33,492 `mmap`, 33,406 `open`, 69,805 `pread64`** — ~1,670 full
      map-and-unmap cycles *per block*, one per prevout. The syscalls were
      never the cost; the **lock** was. `mmap`/`munmap` take `mmap_lock` for
      WRITE, so every resolver thread serialised, and each `munmap` shot down
      TLBs across all cores. That is why raising `BFI_THREADS` 8 → 64 had
      changed nothing. Mapping each blk file once takes those counts to
      **0 / 1,003 / 900 / 46**.
- [x] **Dedup:** inputs spending the same parent repeated the whole lookup,
      and round-robin striping handed consecutive inputs — the ones most
      likely to share a parent — to *different* threads with private caches.
      Grouping by parent txid: over 1000 blocks, 5,505,050 inputs collapse to
      4,577,099 distinct parents (**1.20x**).
- [x] **NO SPEEDUP IS CLAIMED, and that is the point.** A 1000-block run of
      the *unmodified* builder, repeated as a drift control, came in at
      **8.87 blk/s against 7.51 for the same binary earlier** and 8.54 for the
      best optimised variant. The spread between two identical runs exceeds
      the gap being measured, because the live daemon competes for the device.
- [x] **Measured and rejected:** batched `madvise(WILLNEED)` prefetch did
      exactly what it was designed to do — queue depth 7.5 → ~500 — and ran
      **5.67 blk/s**. The device delivers 12–17k reads/s whether the queue
      holds 7 requests or 533, so depth was never the constraint. Removed,
      with the numbers left as comments.
- [x] Same lesson twice more: adding `MADV_RANDOM` to the txid index was
      **2.2x slower**; removing it from the archive was also worse. Two
      mappings, opposite answers, neither guessable from byte counts.
- [x] **Corrected estimate:** ~8 blk/s measured, so the remaining ~194,000
      blocks is **~7 hours**, not the 50 the old log's decayed rate implied.

## Core options, three batches

**Batch one** (`8ec9f1d`, deploy `am`) — the five the audit ranked highest:

- [x] `minimumchainwork` — absent entirely, not even a constant. Per-chain
      defaults from Core's `kernel/chainparams.cpp`; the fork-choice path now
      refuses a candidate below the floor even when it is heavier than our tip.
- [x] **The test caught a real bug here.** Core spells the value BIG-endian;
      this node's accumulator is 16 bytes LITTLE-endian
      (`bitcoin_chainwork.asm` says so, and `chainwork_cmp` reads the high
      qword from `+8`). Comparing across the two **inverted the check** —
      low-work chains would have passed. Same family as the `parse_varint` and
      `peers.dat`-port bugs. A 256-bit floor that will not fit the 128-bit
      accumulator now **fails closed** rather than truncating into something
      weaker than configured.
- [x] RPC **cookie authentication** — Core's format exactly, `0600`, deleted
      on shutdown. Credential compare made constant-time.
- [x] `bantime` + automatic misbehaviour scoring at Core's 100 points. Found
      while implementing: **`ctl_is_banned` guarded only the dial path**, so a
      banned peer could simply connect to us and be served. `setban` looked
      enforced while it was half enforced.
- [x] `-datadir=` / `-conf=`, and real gates for `blockfilterindex` /
      `coinstatsindex`.

**Batch two** (`d12f728`) — `permitbaremultisig` (a real gate now;
`getmempoolinfo` had **reported** it as a hardcoded 1 while nothing could set
it), `networkactive`, `forcednsseed`, `pid`. `fixedseeds` **declined**: Core's
gates a hardcoded IP seed list this node does not have.

**Batch three** (`70aee61`, deploy `an`) — four `-*notify` hooks in
`daemon/notify.c`, and the systemic fix:

- [x] The substituted `%s` is **sanitised** to `[A-Za-z0-9._:/-]`. Core hands
      the value to a shell; for a hash that is harmless, for an alert
      **message** it is not. The test asserts a real injection attempt does not
      execute.
- [x] Double fork — not just hygiene: the SIGCHLD reaper **counts** children to
      enforce `MAX_INBOUND`, and a notify process must not be miscounted.
- [x] **`whitelist=rpc` had been sitting in the live config doing nothing.**
      Unknown keys are ignored deliberately (the file is shared with consumers
      that handle `rpcport`, `dbcache`), so a blanket warning would be wrong.
      There is now an explicit list of unimplemented Core options, each named
      at boot. It fired against the real config on the first boot of `an`.

Parity **~37% → ~44%**. The audit's "~40 cheap and real" estimate was mine and

## the part worth remembering: a green gate lied three times

1. A new Makefile rule sat **above** the `$(RPCLIBS)` definition. Make expands
   prerequisites when the rule is READ, so it expanded to nothing — the rule
   depended on none of its 37 objects while still linking correctly. Caught by
   `prereq-check`.
2. The new test **built but never ran** for a whole gate cycle: the `test:`
   target lists binaries as prerequisites *and* runs them from a separate
   explicit recipe list, and only the first had been updated. `MAKE_EXIT=0` was
   entirely truthful and said nothing about any of the five new features.
3. At deploy time, quoting a **stale heartbeat** would have manufactured a
   phantom 74-txout discrepancy. The shutdown line is the only honest
   pre-restart figure.

Also backed out: running the gate with `make -j8`. 25 test files bind ports and
the Makefile declares no `.NOTPARALLEL`, so parallel runs can collide and
produce failures that are not real.

**What actually works:** grepping the gate log for the *test's own output* —
proof the assertions executed — rather than trusting the exit code.
