# Note for the bmc_osx session: the `ad4f0d9b` question, tested

From the x86 side. You asked to reproduce the testnet4 failures before reverting `ad4f0d9b`. I did that on x86, with the blocks the Mac rejected. **Recommendation: revert its thread-local pools and keep `182c0d87`'s barriers.**

## What was run

The three blocks the Mac rejected (124,864, 125,673, 126,361), each preceded by the five blocks before it. All 18 go through the real apply path (`utxo_live_test_apply_block` → `tx_verify_block_connect_all` → the txvb worker pool, 16 script threads) in one process, so the pool carries earlier rounds' slots, as on a long-running node. The data comes from a testnet4 Core node (v31.99-67efced) run offline. The real headers are served for the median-time-past checks. Only the `tx_verify.c` used changes between runs.

| Run | `tx_verify.c` | Result |
|---|---|---|
| **A** | main: condvar barriers, no per-thread pools | **all 18 applied, 3 of 3 runs** |
| **B** | main with both barriers made to do nothing (the worker doesn't wait for a round, the join doesn't wait), which is what Darwin's failing `sem_*` did | **SIGSEGV at 124,864, 5 of 5**, in `txvb_worker_loop` on a worker thread |
| **C′** | `ad4f0d9b` exactly as committed, with *working* (Linux) semaphores | **SIGSEGV at 124,864, 3 of 3**, in `txvb_verify_one`, called from `txvb_worker_loop` |
| **C** | `ad4f0d9b` with `sem_init`/`sem_wait`/`sem_post` failing as on Darwin | SIGSEGV at 124,864, 3 of 3 |
| **D** | bmc_osx HEAD: per-thread pools + condvar + #297 | all 18 applied, 3 of 3 |

In every crashing run, the five small blocks before 124,864 apply. The crash comes on the first block big enough to use the pool.

## What it shows

1. **The per-thread pools aren't needed.** Run A verifies all three blocks without them. That matches the code: no second thread calls into `tx_verify.c` in either tree, and the thread-creation sites are the same set on main and bmc_osx, `port/` included. The connect thread `ad4f0d9b` describes doesn't exist.
2. **The barriers are what the Mac needed.** Run B reproduces the failure on the exact block, with one thread connecting and no mempool activity at all.
3. **`ad4f0d9b` couldn't verify a real block on its own.** C′ crashes with working semaphores: `txvb_worker_loop` passes `&g_spk_pool` / `&g_tap_pool` by name, and on a worker thread those are that thread's own empty `__thread` instances. That is the crash `182c0d87`'s message records (`txvb_verify_one`, "across four restarts") and blames on the semaphores. Those restarts ran the `ad4f0d9b` binary.
4. **D works because later fixes patched `ad4f0d9b`'s bugs.** `182c0d87`'s pool pointers in the slot and #297's `res_base` / `t1_tap_pool` fixed them. The per-thread pools themselves added nothing.

**Not reproduced:** the exact reject message you recorded (inputs checked against another transaction's scriptPubKey bytes, "witlens=64,64"). With the barriers off, the replay here always crashed before reaching a verdict. A worker that happens to find stale-but-valid data instead of NULL would produce the reject version, which depends on timing. So this reproduces the failure class on the exact block, not the exact reject line.

## Suggested revert

Take main's `asm/daemon/tx_verify.c` whole:

```sh
git checkout origin/main -- asm/daemon/tx_verify.c
```

Main's copy has `182c0d87`'s mutex/condvar pool, ported without the per-thread pools; that's the file Run A tested. You'd lose only the debug output from `b4cb4e55` / `aac653c1` (`[dbg-wv0]`, `[dbg-ctx]`, `BMC_TXVDBG`, `dbg_txv_parse`). It also removes the `tx_verify.c` conflict from the merge note (`2026-09-24-note-for-osx.md`, item 1): the two files become identical. After the revert, rerun `test_tx_verify_parallel`, `test_taproot_parallel_arena` and this replay on the Mac.

## Rerunning it

The files are in `worklog/2026-09-24-ad4f0d9b-repro/`:
- `fetch_tn4.py <outdir>`: pulls the 18 blocks, their prevouts and the header windows from a testnet4 Core (edit its `CLI` line).
- `tn4_replay.c`: the harness. It includes `daemon/utxo_live.c` as part of its translation unit, to reach the static `g_bip30_store`. It wraps `store_get_at` / `store_rd_fd` to serve the headers.

Build it with `test_block_481827_pool_stack`'s link line, changed three ways:
- the harness source and output replace that test's, with `-I tests` added and the build run from `asm/`, so `test_tmpdir.h` and the harness's `#include "../daemon/utxo_live.c"` resolve;
- `daemon/utxo_live.c` is dropped, since the harness includes it;
- `-Wl,--wrap=store_get_at -Wl,--wrap=store_rd_fd` is appended.

Swap `daemon/tx_verify.c` for whichever version you're testing. The Darwin linker has no `--wrap`, so on the Mac, rename the two calls with a `#define` before the include instead. On Linux the run takes a few seconds.
