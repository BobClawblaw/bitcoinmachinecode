### 00:04–02:07 — the benchmark suite, and the four ABI bugs it found

- [x] `cffe48b`: three-tier benchmark suite vs Bitcoin Core
      (`scripts/bench_vs_core.sh`). Writing it found four ABI bugs, which is
      the point worth recording: a benchmark that only produces ratios is a
      weaker instrument than one that has to *call* every function correctly.
- [x] `26fc55c`: **twenty-one functions returned the caller's callee-saved
      registers full of their own locals.** `abi-check` audits stack
      alignment and had been green throughout; register preservation is a
      different question and nothing was asking it.
- [x] `438557e`: incident #26 — the witness item cap rejected a real
      500,003-item input. The cap was a guess; the wire's own bound (one byte
      minimum per item, block ≤ 4 MB) is the only sound one.
- [x] `8d16736`: the BIP340 challenge preimage was a process-global buffer.
      **Latent, not live** — corrected the same day in `8c2531d` after
      checking both call sites: `schnorr_verify` is reachable only through
      `taproot_verify_input`, which ran sequentially at the time.
- [x] `22c8a60`: MuHash3072 set hash + `gettxoutsetinfo` differential. This is
      the instrument that makes "our UTXO set IS Core's" a measurement rather
      than an inference — count, amount and bogosize are all blind to a
      per-entry height field; only a set hash sees it.

### 01:55 — incident #28: SETcc writes eight bits

- [x] `ccf695b`: eleven numeric opcode handlers computed a boolean on top of
      the decoded operand (`test r14,r14 / setnz r14b`), leaving the operand's
      upper 56 bits. **11,780 divergences from Core across 63,036 generated
      scripts, 5,050 of them false-ACCEPT.** Not reachable by replaying the
      chain: Core-running miners never mined a block that exercises it.
      Fixed with `movzx` after all twelve SETcc sites.

### 19:05–19:37 — incidents #32 and #29

- [x] `9e3bf99`: incident #32 — `utxo_get`/`utxo_del` probe loops had **no
      termination bound**, so a full table was an infinite loop. `utxo_put`
      already had one. Also: WAL flush at the catch-up downshift, and SIGTERM
      handled during reload. My first claim that the bound would make an
      undersized reload "fail loudly in seconds" was **wrong** — it converts an
      infinite loop into an O(records × slots) crawl unless the caller also
      checks the "full" return, which needed a second fix.
- [x] `e3ba5f1`: incident #29 — **coinbase outputs must overwrite**, as Core's
      `AddCoins` does (`overwrite = check_for_overwrite ? HaveCoin(...) :
      fCoinbase`, and ConnectBlock defaults it false). Mainnet has two such
      duplicates; ours held the earlier height, Core holds the later. Height
      feeds the 100-block maturity rule, so between 91,880 and 91,980 we would
      have accepted a spend Core rejects.

### 19:54–20:19 — the network layer was measuring itself wrong

- [x] `038481e`: **`poll()` returns on the first ready descriptor, not after

- [x] `4d75e4a`: **the same bug in `dlc_probe_round`**, found because the

### 20:34 — Core parity on the set definition itself

- [x] `ca842e3`: **provably-unspendable outputs never enter Core's chainstate**
      (`AddCoin` returns early for leading-`OP_RETURN` or >10,000-byte
      scripts). We stored them: **252,101,123 of 417,948,516 entries**, so
      `live_utxo` read ~2.5× Core's `txouts` and the set was only comparable
      through a read-time filter. Filter moved to write time in both writers,
      sharing `utxo_script_unspendable` with the differential tooling so the
      writer and the verifier cannot disagree. Heartbeat label `live_utxo=` →
      `txouts=`. Also: `mux_redial` renamed `mux_next_peer` (it never redialled
      the same host — it advances to the next pool entry), and a `new block:
      height=N hash=…` line from one choke point.
