The localization plan wrote itself once count/total_amount/bogosize were

height, coinbase byte, same-length script bytes, or outpoint keys — and
the sharpest probe target was the BIP30 duplicate-coinbase boundary,
where the builder's own tally said put_dup=2.

Ground truth from the oracle: the two duplicated txids each appear twice
(d5d27987… at 91812+91842, e3bf3d07… at 91722+91880), and Core's
chainstate holds the SECOND copy of each (heights 91842/91880 — a later
duplicate coinbase REPLACES the earlier coin, same value/script, new
nHeight). Our store held the FIRST copy of each (91812/91722). Exactly
two coins, height byte only — count/sum/bogosize untouched, which is why
only muhash could see it. put_dup=2 is precisely these two dropped puts.

Mechanism: utxo_store_put ALWAYS appends the WAL record (with height and
coinbase) and then calls the memtable utxo_put, which returns 0 on an
existing key WITHOUT updating; build_utxo's on_output treated r==0 as a
benign duplicate and moved on. The second put died in the memtable and
its WAL record was truncated at the next checkpoint.

Fix (a69e166a): on r==0, tombstone the old generation and insert fresh
(del+put — the exact sequence fuzz_lsm pins against the Python model), in
BOTH the serial on_output path and the -j pipeline's arena applier. The
-j edit initially read the script pointer after p += slen — caught in
self-review and rewritten with the pointer captured before advancing.
Proven on the bug itself: rebuilding 90000..92000 with the fixed binary
(serial AND -j 4) yields heights 91842/91880, matching Core's
confirmations.

Live-store repair (asm/daemon/repair_bip30_heights.c, new): with the
daemon stopped it reloads the store (2^24 sizing, no forced flush),
ASSERTS the stale state (get must show 91812/91722 and the 50 BTC
coinbase — refuses otherwise), tombstones each stale coin and re-puts it
with Core's height and the exact 67-byte P2PK script, verifies in-memory,
and leaves four WAL records for the daemon's normal replay. No third
rebuild of a 165M-entry store; the daemon picked the coins up on its next
boot and probes confirm 91842/91880 through BOTH read paths.
