# Run 24 — full index set, and a getblock defect it exposed

Started 2026-09-16 14:42 UTC on `/mnt/2tbssd/bmc-run24`, build `0d5f4044`,
ports 8464 P2P / 8463 RPC / 3006 Esplora. Config: `addrindex=1` (set before
sync, which is the only way to get it), `coinstatsindex=1`,
`blockfilterindex=1`, `txindex=1`, `maxconnections=48`, journal 2,000,000.

This is NOT a time comparison against run 23 or against Core: it carries four
indexes where run 23 carried one, so it is doing strictly more work. It exists
to give BlockYard a node with every capability turned on.

## BlockYard sees it

`npm run check` against the new node entry reports:

                   node, Esplora facade on :3006, mempool departure journal

average with 90 s timeouts. Chart contamination was already fixed by per-node

One caveat there is INVERTED for bmc and will bite whoever reads it: the real
log is `<datadir>/main/debug.log` (it carries the `[dlc]`/`[dl]`/`[config]`

## Defect: getblock is frozen at the boot tip for the whole of IBD

CONFIRMED, reproducible, and it blocks BlockYard's block rendering on any
syncing node.

`getblock <hash>` returns `-5 Block not found` for every block above a fixed
height, at EVERY verbosity, while the node keeps syncing:

    height 0 … 10,880    served
    height 10,881 …      "Block not found"

The cut did not move as the tip went 159,440 → 193,360; it is not a lag. It is
not patchy either — 16 sampled heights above the cut all failed, so it is a
clean prefix, not the out-of-order holes IBD would produce. `getblockhash`
works at every height and agrees with `getbestblockhash`; only the hash→height
lookup fails. The same build in production serves the very hash the bench node
rejects, at verbosity 1 and 3 — so the code is fine and the *state* is not.
Block bodies are present on disk (blk00000–4, 670 MB; index.dat 46 MB).

### Root cause: a probe budget in a caller-saved register

`idx_put` and `idx_get` in `asm/bitcoin_idx.asm` both held their linear-probe
budget in **r8** across `call memcmp_exact`:

    mov  r8,  [r12+8]        ; probe budget
    inc  r8
    ...
    call memcmp_exact
    ...
    dec  r8
    jz   .full

and `memcmp_exact` writes `r8b` on every byte it compares:

    mov  r8b, byte [rdi+rcx]

r8 is caller-saved under the SysV ABI, so this is `memcmp_exact`'s right. The
budget is therefore overwritten in its low byte by a byte of the stored hash on
the first collision, and from then on it counts down from a value the data
chose:

  * in `idx_put`, `dec / jz .full` may never reach zero, so a full table spins
    forever instead of reporting full;
  * in `idx_get`, `dec / jz .notfound` fires EARLY, so a key that IS in the
    table is reported absent -- `getblock` answering "Block not found" for a
    block the archive holds.

Below capacity none of this shows, because a probe terminates on an empty slot
long before the budget matters. It only bites at or near a full table. The
by-hash table is sized from the tip AT OPEN, so a node that opens its store
mid-IBD sizes for the tip it had then and fills as the sync runs past it --
which is why this is an IBD-only symptom and why production, which opened on a
complete chain, never showed it.

The fix spills the budget to the stack in both routines. Stack alignment at the
calls is unchanged.

### Why the cut is a clean prefix, and why it never moves

This was the part that resisted explanation while the cause was unknown, and it
falls out of the same bug. A corrupted budget in `idx_put` can also reach zero
EARLY, so `idx_put` reports "full" on a table with room to spare. `idx_sync`
reads that as a real table-full:

    int r = idx_load_range(g_idx, g_idx_tip + 1, tip);
    if (r == 2){
        if (!idx_alloc(g_idx_slots * 2)) return;   /* g_idx_tip = -1 */
        if (idx_load_range(g_idx, 0, tip) != 0) return;   /* leaves it at -1 */
    }
    g_idx_tip = tip;

so it doubles the table and reloads from height 0 -- and that reload stops at
the same premature "full", because it is re-inserting the same keys in the same
order. The table ends up holding a PREFIX of the chain, and every later refresh
rebuilds exactly that prefix. Hence a clean cut rather than scattered misses,
and a cut that does not move as the tip advances: measured at 10,880 with the
node at 159,440, at 193,360, and still 10,880 at 356,682.

The doubling loop is not the bug and does not need its own fix; it was
faithfully reacting to a lie from `idx_put`.

### Getting there: three wrong turns, recorded

1. *`idx_sync` advancing `g_idx_tip` past unfolded heights.* The first theory,
   and wrong. `test_rpc_chain_growth` was written to prove it and passes both
   in-process and cross-process (the node's real arrangement).
2. *`idx_put` degrading quadratically as the table fills.* Measured directly:
   65,536 inserts to 100% full in 0.05 s. Not quadratic.
3. *The growth test as the regression pin.* It reproduced the hang at
   GROWN=70000 -- and then PASSED with the fix reverted. Whether the corrupted
   budget loops forever depends on which hash bytes land in `r8b`, so that test
   is not a pin for this defect. The deterministic pin is the new full-table
   case in `tests/test_idx.c`, which hangs (SIGALRM, exit 142) against the
   unfixed assembly and passes against the fixed one.

The third one is the one worth remembering: the reproduction that FOUND the bug
was not a test that CATCHES it.

### About `test_rpc_chain_growth`

It is kept as the regression guard cross-process archive growth never had --
not as the pin for this defect, for the reason above:

  1. *In-process growth* — open the view at a low tip, append more through the
     same store handle, look the new blocks up. Passes. (This shape is too weak
     anyway: one shared handle lets the reader see the writer's appends for
     free, which is not how the node is arranged.)
  2. *Cross-process growth* — the writer forked into its own process with its
     own `store_init`, the reader refreshing through `store_reload` off
     index.dat, which IS the node's arrangement. Also passes: blocks appended
     after open resolve by hash.

## Still open

`getblock` on the running run 24 node is still broken -- it is running the
binary built before the fix. Restarting it picks up the fixed binary and
resumes from the datadir (it does not re-sync), and that is the way to get a
node BlockYard can render blocks from. Production is not exposed today, because
it opened on a complete chain, but it carries the same assembly.
