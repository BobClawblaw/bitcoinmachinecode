# Run 24 — full index set, and a getblock defect it exposed

Started 2026-09-16 14:42 UTC on `/mnt/2tbssd/bmc-run24`, build `0d5f4044`,
ports 8464 P2P / 8463 RPC / 3006 Esplora. Config: `addrindex=1` (set before
sync, which is the only way to get it), `coinstatsindex=1`,
`blockfilterindex=1`, `txindex=1`, `maxconnections=48`, journal 2,000,000.

This is NOT a time comparison against run 23 or against Core: it carries four
indexes where run 23 carried one, so it is doing strictly more work. It exists
to give BlockYard a node with every capability turned on.

## BlockYard sees it

`npm run check` against the new node entry reports:

    node kind      bitcoinmachinecode (0d5f4044) — address history from the
                   node, Esplora facade on :3006, mempool departure journal
                   (2,000,000 records), download worker map

                   to build its own

which is the capability handshake working end to end: BlockYard skips its own
30-minute / 124 GB address index build because the node advertises one.

The three objections recorded in `server/config.js` against monitoring a bench
node were re-measured and no longer hold on this build. Eight concurrent
`getblockcount` calls: 1–2 ms each, 4 ms wall. The recorded figures were 18–32 s
average with 90 s timeouts. Chart contamination was already fixed by per-node
rings.

One caveat there is INVERTED for bmc and will bite whoever reads it: the real
log is `<datadir>/main/debug.log` (it carries the `[dlc]`/`[dl]`/`[config]`
tags `collect/logparse.js` parses). The run directory's console log stops after
26 boot lines. For the old bench harness it was the other way round.

## Defect: getblock is frozen at the boot tip for the whole of IBD

CONFIRMED, reproducible, and it blocks BlockYard's block rendering on any
syncing node.

`getblock <hash>` returns `-5 Block not found` for every block above a fixed
height, at EVERY verbosity, while the node keeps syncing:

    height 0 … 10,880    served
    height 10,881 …      "Block not found"

The cut did not move as the tip went 159,440 → 193,360; it is not a lag. It is
not patchy either — 16 sampled heights above the cut all failed, so it is a
clean prefix, not the out-of-order holes IBD would produce. `getblockhash`
works at every height and agrees with `getbestblockhash`; only the hash→height
lookup fails. The same build in production serves the very hash the bench node
rejects, at verbosity 1 and 3 — so the code is fine and the *state* is not.
Block bodies are present on disk (blk00000–4, 670 MB; index.dat 46 MB).

### Two hypotheses ruled out

`asm/tests/test_rpc_chain_growth.c` was written to reproduce it and does NOT.
It is kept because a test that fails to reproduce still narrows the search, and
because cross-process archive growth had no regression guard at all before it:

  1. *In-process growth* — open the view at a low tip, append more through the
     same store handle, look the new blocks up. Passes. (This shape is too weak
     anyway: one shared handle lets the reader see the writer's appends for
     free, which is not how the node is arranged.)
  2. *Cross-process growth* — the writer forked into its own process with its
     own `store_init`, the reader refreshing through `store_reload` off
     index.dat, which IS the node's arrangement. Also passes: blocks appended
     after open resolve by hash.

So the by-hash index does follow a growing archive across processes at this
scale, and the defect needs something the fixture does not have — scale, or
`blk` file rotation, or the table-doubling path.

### Mechanism not yet established

The suspect is `idx_sync` in `asm/rpc_chain.c`:
it folds `(g_idx_tip, tip]` into the by-hash table and unconditionally sets
`g_idx_tip = tip` afterwards, and its table-full recovery path
(`idx_alloc(g_idx_slots * 2)` then a full reload) returns early without
restoring `g_idx_tip`. Reading alone did not settle it: `public_tip_cap` returns
`min(connected, stored)`, so a growing `getblockcount` proves `ST_TIP` is NOT
frozen, which means `idx_sync` IS being called over the missing range and the
entries still do not become findable. That contradiction is the next thing to
resolve, and the way to resolve it is an instrumented `idx_count` on a
THROWAWAY syncing node on its own port -- not more reading, and not by
restarting run 24, which would reset the boot tip and hide the thing.

One numeric coincidence worth checking first: the cut sits at 10,880, and the
table is sized `(tip_at_open + 1) * 4` floored at `1 << 16`. If the tip at open
was 2,720 then `(2720 + 1) * 4 = 10,884` -- within four of the observed cut.
That is either the answer or a distraction, and it is cheap to settle.

Why production never showed it: production opened its store when the chain was
already complete, so the boot-time fold covered everything.
