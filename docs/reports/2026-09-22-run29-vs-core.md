# Run 29: a repeat of run 28, same commit, same Core baseline

2026-09-21 to 2026-09-22. Node commit `1562ae86` (identical to run 28's), Bitcoin
Core v31.1 baseline `core31` on the same machine and drive.

**The short version.** Run 28 (`docs/history/2026-09-21-run-28-vs-core/`) gave
one clean, unpolled bmc-vs-Core pair and left one thing unmeasured: bmc's own
run-to-run spread. Run 29 answers that — same code, same box, same drive, run
again — and gives a second point on the same `core31` baseline. bmc again
finished with a UTXO set MuHash-identical to Core's.

## How it was measured

Both runs used the same machine and the same drive as run 28:

- AMD Ryzen 9 9950X3D (16 cores, 32 threads), 123 GiB RAM
- Corsair MP600 PRO XT 8 TB NVMe (`/mnt/nvme8tb`, `ext4`) for both datadirs —
  `core31` and `run29` are two directories on the *same partition*
- the public mainnet peer-to-peer network, no local peers

Same settings both sides (`run29/phase.log` CONF line; `core31/bitcoin.conf`):

| setting | bmc | Core |
|---|---|---|
| dbcache | 8192 | 8192 |
| txindex, blockfilterindex, coinstatsindex | on | on |
| maxconnections | 48 | 48 |
| peers downloading blocks at once | 8 | 8 (fixed in Core) |
| CPU niceness | 0 | 0 |
| build | commit `1562ae86` (same as run 28) | v31.1 release, built from source |

**Nobody called either node's RPC during IBD.** `run29/phase.log` carries no
"WARN ... something is polling the run" line (run 27 and run 28 both did, at
different severities); `core31/watch.log` records the one false-positive from
its own outbound P2P connection, fixed, and no RPC call for the rest of the
run. The IBD-end times below are timestamps the nodes wrote themselves, not
the moment a monitor noticed.

**One continuous process, both sides.** `run29/phase.log` has a single
`DAEMON pid=3150999` line and no restart; `core31` was the rerun built
specifically to be un-restarted (see run 28's report for why the *first* Core
baseline, with a 12 s mid-run restart, was set aside for this purpose).

## Against run 28: bmc's own run-to-run spread

The one thing run 28's report flagged as unmeasured: "each side ran once.
Nobody has measured the run-to-run spread yet." Run 29 is the same commit run
again, so it answers that for bmc's side (not Core's — see below).

| | end of IBD | elapsed to live tip | live-tip height |
|---|---:|---:|---:|
| run 28 | 18:24:02 | 18:25:28 | 967,924 |
| run 29 | 18:28:54 | 18:35:23 | 968,154 |
| **spread** | **4 m 52 s (0.44%)** | 9 m 55 s | — |

A small, reassuring spread on identical code. It does not by itself explain
which side (peer conditions, disk state, scheduling noise) contributed it, and
it is one data point, not a distribution.

## What was not clean

- **The runs were not simultaneous, and not even close.** Core ran 09-19 to
  09-20; bmc run 29 ran 09-21 to 09-22, two full days later. Different peers,
  different real-time network conditions, and the live chain grew roughly 341
  blocks in the gap — which is also why the two "live tip" heights above
  (968,154 for bmc, 967,813 for Core) are not the same block. This is the same
  caveat run 28's report carried; it is not resolved here, only repeated with
  the honest number attached.
- **Core has still only run once.** Run 29 gives a second bmc data point on
  this exact protocol; there is still exactly one Core run (`core31`) that
  this and run 28 both compare against. Core's own run-to-run spread on this
  hardware is unmeasured.
- **Same commit as run 28.** This run does not test any code that changed
  since 09-20 — deliberately, since its purpose was repeatability, not a
  fresh result. It does not speak to any change made after `1562ae86`.
- **One machine.** As with every report in this series: this says nothing
  about other hardware, other storage, a cloud VM, or a spinning disk.

## Is this an honest comparison of IBD performance against Core?

As far as this project's own standard for "clean" goes (matched device,
matched settings, matched peer concurrency, no RPC polling, end-of-IBD read
from each node's own log rather than an external observer) — **yes, by that
standard this pair is clean**, in the same way run 28's was. It is not
withdrawn the way the 09-17 run 26 comparison was, because the thing that sank
that one — two different storage devices in the same sentence — does not
apply here: `core31` and `run29` are two directories on the same partition of
the same drive.

What it is **not** is a controlled, repeated, statistically powered benchmark.
It is two single-shot, non-simultaneous runs of real mainnet IBD, two days
apart, at whatever peer and network conditions happened to exist during each
window. The 4 m 52 s spread between run 28 and run 29 on identical bmc code is
the only run-to-run evidence available on either side, and it only covers
bmc's own variance, not Core's. A genuinely rigorous claim would want Core run
at least twice on this same drive too, and ideally several bmc/Core pairs
alternated on the same days to average out network conditions — none of which
has been done.

So: **an honest comparison, not a rigorous one.** The 5.5% figure is real,
measured the same way twice now with a small and consistent margin (5.5% here,
5.9% on run 28), and the UTXO-set match is independent, hash-based correctness
evidence rather than a timing claim. But it describes this machine, this
drive, these two specific windows in September 2026 — not a general claim
about bmc versus Core on other hardware, under other conditions, or forever.
