# Run 26: every index built during the sync, and a chain identical to Core's

2026-09-17. Node commits `e2f1e53c` → `3a3289b8`, Bitcoin Core v31.1 oracle on the
same machine.

> **CORRECTED 2026-09-17, and INTERNAL — not published.** The wall-clock
> comparison this report drew against Bitcoin Core is **withdrawn**. It set run
> 26's 19h 34m beside a 19h 14m Core baseline and called that "within about 2%
> while building five indexes". Those two runs were not on the same storage:
> the Core baseline ran on a **Samsung Portable SSD T5** (0.40 GiB/s sequential
> write), run 26 on a **Corsair MP600 CORE XT NVMe**. A Core run handicapped by
> a portable SSD against a bmc run on NVMe is a comparison of disks, not of
> implementations.
>
> The original version listed three caveats on that number — the ten restarts,
> the mid-run binary swap, the Core baseline's unrecorded index settings — and
> missed the one that mattered most. **There is currently no valid IBD
> wall-clock comparison between this node and Core.** A matched pair is
> scheduled: both on the same device, both with every index they support, both
> with their config recorded before launch.
>
> Nothing else in this report is affected. The parity results below are
> comparisons of content, not of time, and they stand.

**The short version.** A full mainnet initial block download by an independent
Bitcoin full node written in x86-64 assembly, finishing with a chain identical to
Core's block for block and a UTXO set identical to Core's coin for coin — while
building **five indexes concurrently with the sync**, including two that Core has
no equivalent for. When the download ended, nothing started: no post-sync index
build, no adoption pass, no supervisor waiting for the initial download to finish.
That absence is the result this run was built to demonstrate.

txindex=1             coinstatsindex=1          blockfilterindex=1

`bmc.catchupworkers=8` is the download concurrency, matched to Core's

concurrency is where IBD comparisons usually go wrong, so it is controlled here.

## Timeline, stated honestly

| | |
|---|---|
| fresh start from genesis | 2026-09-16 21:10:55 UTC |
| download complete (967,385/967,385) | 2026-09-17 16:45:16 UTC |
| **wall clock** | **19h 34m** |

| downtime | 11m 33s across 9 restart gaps |
| boots | 10 |
| average throughput | 10.7 MB/s |

**This is not a benchmark-grade wall clock, and it should not be quoted as one.**
Run 26 was restarted ten times. Nine of those were deploy-and-debug cycles on the
evening of 09-16 while defects found *by* the run were being fixed; the tenth, at
08:12 on 09-17, was a deliberate binary swap to pick up two fixes. The binary
therefore changed underneath the run. A clean single-binary IBD number needs a
run that is left alone from genesis to tip.

**And there is no Core number to set beside it.** The last clean Core baseline
on this box (2026-09-13, unhandicapped, 8 peers, no `coinstatsindex`) finished
966,808 blocks in 19h 14m — but it ran on the **Samsung Portable SSD T5**,
0.40 GiB/s sequential, while run 26 ran on **NVMe**. Putting those two numbers
in the same sentence compares storage, not software, and the earlier version of
this report did exactly that. Withdrawn.

Three further reasons that baseline could not carry the comparison anyway: run
26's ten restarts; the binary changing underneath it; and the baseline's
`txindex`/`blockfilterindex` settings never having been recorded — only that it
carried no `coinstatsindex`.

So the honest position is that **this report measures correctness, not speed.**
The wall clock above is an operational fact about run 26 and nothing more. A
matched pair — same device, same day, every index each node supports, configs
recorded before launch, per-segment timings so one stalling peer is visible — is
what would settle it, and it has not been run yet.

## The result this run existed to prove

Before this work, a fresh sync ended with four things still to build, by hand or
by a supervisor that refused to start until IBD was over: `txindex` and
`txospenderindex` (each a full walk of the archive), the address history (three
passes, ~700 GB of temp), and the block filters. `coinstatsindex` was invalidated
at height 91,842 by the first BIP30 duplicate coinbase and stayed gone.

Run 26 ended with all five at the tip and **nothing queued**:

```
txindex                    synced=True   967,450
txospenderindex            synced=True   967,450
basic block filter index   synced=True   967,450
addressindex               synced=True   967,450
coinstatsindex             synced=True   967,450
```

The trailing builders' state at the tip is the same state they held mid-sync:

```
[trail] txindex: runs reach 959999; the next run starts once 12693 more heights
        are ready | txospender: ... | addr_hist: ...
```

The IBD boundary was a non-event. `index_repair`, the supervisor that used to wait
for the sync and then walk the whole archive, never logged a line.

Work done during the sync, by the trailing builders:

|---|---|---|
| txindex | 48 | 8 |
| txospender | 48 | 8 |
| addr_hist | 47 | 9 |

## Disk, both nodes, measured

| | bmc run 26 | Core oracle |
|---|---|---|
| `blk*.dat` (blocks) | **716.6 GiB** | **716.6 GiB** |
| `rev*.dat` (undo) | 246.6 GiB | 100.0 GiB |
| txindex | 26.2 GiB | 68.8 GiB |
| block filter index | 12.2 GiB | 12.3 GiB |
| coinstatsindex | 1.8 GiB | 0.2 GiB |
| UTXO set on disk | 12.9 GiB (LSM runs) | 10.6 GiB (chainstate) |
| address history + tail | 203.5 GiB | *no equivalent* |
| txospender index | 91.5 GiB | *no equivalent* |
| **total datadir** | **1312.3 GiB** | **917.6 GiB** |

Three things worth reading off that table:

- **The block data matches to the tenth of a GiB.** Both nodes store 716.6 GiB of
  `blk*.dat`. That is an independent check on the archive alongside the hash
  comparison.
- **The txindex is 2.6× smaller than Core's** — 26.2 GiB against 68.8 GiB — because
  it is a set of sorted runs with a sparse index, not a LevelDB keyspace. The
  filter index is a wash and `coinstatsindex` is larger.
- **The undo store is 2.5× Core's**, 246.6 GiB against 100.0 GiB, and that is a
  deliberate, load-bearing cost. This node keeps each spent prevout's script and
  value in its block's undo record, which is what makes a height range
  self-contained — and that is precisely what makes the address history buildable
  in runs during the sync instead of by a whole-chain join afterwards. The 700 GB
  of temp the old builder needed existed because it had no undo to read.

Net of the two indexes Core has no equivalent for, the datadir is 1017.2 GiB
against Core's 917.6 GiB, and the difference is almost entirely that undo store.

## What this does and does not establish

**Does:** that an assembly implementation reaches Core's exact chain and Core's
exact UTXO set over the full mainnet history; that five indexes, two of them
without a Core counterpart, can be built entirely during the initial download;
that the post-sync phase can be removed rather than shortened.

**Does not:** any IBD wall-clock comparison with Core. Run 26 was restarted ten
times, changed binaries mid-run, and the only Core baseline available ran on
slower storage. Nor does it establish steady-state serving
performance — address history on one of the most-used addresses on the chain
(`1dice8EM…`, 3.2 M transactions through the Esplora facade) answers a balance in
4.6 s and 100,000 txids in 11.8 s. Acceptable for a page load; unmeasured under
concurrency, and worth attention before anyone calls it fast.

## Reproducing the parity check

```bash
H=967450
bmc-cli  gettxoutsetinfo muhash $H
bitcoin-cli gettxoutsetinfo muhash $H
```

Pin `$H` on both sides. Comparing a live tip against a live tip is how this
project previously talked itself into a UTXO divergence that did not exist.
