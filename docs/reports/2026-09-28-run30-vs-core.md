## What changed since the last pair

The operator repaired a bad backhaul on this box's network link on 2026-09-28,
between run 29 (09-21/22) and run 30. Every earlier pair in this series — run
27 / core31 (09-18/19), run 28, run 29 / core31 (09-21/22) — was measured over
the bad link, so **run 30's wall clock cannot be compared to run 29's 18 h 29 m
or to core31's 19 h 33 m**: the link, not the code, is the first-order change.
Hence this Core rerun, on the same drive and the same link, 21 minutes after
run 30's daemon stopped.

Run 30 is also the first IBD on the 2026-09-28 tree (#329–#335: the MuHash
inverse, the ElligatorSwift multiplies, ChaCha20 in AVX2, SHA-1/SHA-512,
Base58, the comb at every private-key multiply, SHA-256 hashed in place,
the block filter builder). None of those is on the block-apply hot path
except the SHA-256 change; no speed claim is made for them here.

**Reading the rows with care.** Through 800,000 bmc is 55–59% ahead at
every row, and the margin is not narrowing: 57% at 600,000 and 57% at
800,000. That is not what the old-link pair did. Run 29 vs core31 narrowed
from 41% at 100,000 to 10.8% at 400,000, 6.9% at 500,000 and 4.8% at
900,000, and the first draft of this file (19:15Z, Core at 581,594) expected
the same shape here. It has not appeared by 800,000.

The candidate explanation, to be tested against the end-of-IBD figure and
not asserted before it: on the old link both nodes were bound by the link
for most of the chain, so their clocks converged toward the link's rate and
hid the difference in how they use it; on the repaired link neither is
link-bound, bmc's eight parallel download workers keep the apply fed, and
Core's fixed set of download peers with its per-peer in-flight limits does
not. Per 50,000 blocks between 600,000 and 800,000 Core takes 43–56
minutes where bmc takes 17–24. Whether Core's time at those heights is
download or apply is not readable from its default log (no per-block
download timing), so this file does not say which; a Core run with
`-debug=net` on the same link would.

What the rows do establish: on this box, this drive and this link, bmc
reaches every height through 800,000 in 41–45% of Core's time, with both
nodes on identical index and cache settings and neither polled.

## What is and is not clean

- **Same drive, same partition, same link, same protocol, 21 minutes
  apart** — the closest pairing in this series (the earlier pairs were days
  apart).
- **Sequential, not simultaneous**, as before: the two never shared the
  NVMe or the link, and the live chain grows between them.
- **Production and the Core oracle were running on the box during both**,
  as during every pair; neither node was polled.
- **One Core run on the new link, one bmc run on it.** Run-to-run spread on
  the new link is unmeasured on both sides. The bmc side's old-link spread was
  4 m 52 s between runs 28 and 29.
- **The link repair is not quantified.** Its effect is inferred from the
  400,000 row above, not measured.
