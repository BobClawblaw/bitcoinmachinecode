## What changed since the last pair

The operator repaired a bad backhaul on this box's network link on 2026-09-28,
between run 29 (09-21/22) and run 30. Every earlier pair in this series — run
27 / core31 (09-18/19), run 28, run 29 / core31 (09-21/22) — was measured over
the bad link, so **run 30's wall clock cannot be compared to run 29's 18 h 29 m
or to core31's 19 h 33 m**: the link, not the code, is the first-order change.
Hence this Core rerun, on the same drive and the same link, 21 minutes after
run 30's daemon stopped.

Run 30 is also the first IBD on the 2026-09-28 tree (#329–#335: the MuHash
inverse, the ElligatorSwift multiplies, ChaCha20 in AVX2, SHA-1/SHA-512,
Base58, the comb at every private-key multiply, SHA-256 hashed in place,
the block filter builder). None of those is on the block-apply hot path
except the SHA-256 change; no speed claim is made for them here.

**Reading the rows with care.** Through 900,000 bmc is 53–59% ahead at
every row, and the margin is not narrowing: 57% at 600,000, 57% at
800,000, 56% at 850,000, 53% at 900,000. That is not what the old-link pair did. Run 29 vs core31 narrowed
from 41% at 100,000 to 10.8% at 400,000, 6.9% at 500,000 and 4.8% at
900,000, and the first draft of this file (19:15Z, Core at 581,594) expected
the same shape here. It has not appeared by 900,000.

**Where run 30's time went, from its own status lines** (2026-09-29): the
downloader's `[dlc] ==` lines print the blocks stored, the connected
(applied) tip and the lag between them every few minutes. The lag sat at
3,500–4,100 blocks from the eleventh minute to the end — the 4,096-block
download window, anchored to the applied tip — with the download waiting on
the apply the whole way (sample: 0:08 stored 309,841 applied 305,898; 1:39
639,641 / 636,321; 2:53 809,281 / 805,533; 3:42 880,641 / 876,726). So on
the repaired link run 30 was **apply-bound**, not download-bound, and the
flat margin is the apply rate: bmc connects blocks about 2.3× as fast as
Core does at every height, and the download on either side is no longer the
pace. On the old link both nodes were download-bound, their clocks converged
on the link's rate, and the apply difference was hidden — which is why that
pair narrowed to 4.8% and this one does not. The first draft's candidate (a
download-strategy difference) is withdrawn.

**The settings were not the same, in Core's favour** (found 2026-09-29 when
the two nodes' network defaults were compared line by line): run 30
downloaded from 8 peers where Core downloads from its 10 outbound peers
(the 8 full-relay and the 2 block-relay-only — the register had counted the
full-relay class alone), with a 4,096-block window where Core's is 1,024,
and with 4 idle legs held beside the 8 workers where Core's download peers
are its whole outbound set. bmc's 40-block chunk per `getdata` against
Core's rolling 16 in flight per peer remains a shape difference. From run
31 the defaults match Core's (`docs/releases/2026-09-29-core-download-shape-matched.md`).

What the rows establish: on this box, this drive and this link, bmc reaches
every height through 900,000 in 41–47% of Core's time, with both nodes on
identical index and cache settings, neither polled, and bmc on fewer
download peers and a wider window than Core. What it does not establish is
the end-of-IBD ratio: run 30's last 69,000 blocks took 43 minutes, and Core
never got to run them.

## What is and is not clean

- **Same drive, same partition, same link, same protocol, 21 minutes
  apart** — the closest pairing in this series (the earlier pairs were days
  apart).
- **Sequential, not simultaneous**, as before: the two never shared the
  NVMe or the link, and the live chain grows between them.
- **Production and the Core oracle were running on the box during both**,
  as during every pair; neither node was polled.
- **One Core run on the new link, one bmc run on it.** Run-to-run spread on
  the new link is unmeasured on both sides. The bmc side's old-link spread was
  4 m 52 s between runs 28 and 29.
- **The link repair is not quantified.** Its effect is inferred from the
  400,000 row above, not measured.
- **The Core run did not finish**, for a reason that was neither node's:
  another session's `mount` on `/mnt`. Its rows through 900,000 are
  clean; its end is missing. A rerun on the matched defaults
  (`docs/releases/2026-09-29-core-download-shape-matched.md`) is the next
  pair, and the box rule since is that nothing mounts on `/mnt` while a
  datadir lives under it.
