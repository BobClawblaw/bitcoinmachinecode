## The one thing that needs a decision

**Block 967422 on run 26 is corrupt and I caused it.** Bytes [0,292] of
`blk05762.dat` hold genesis instead of that block's start, so `getblock` on its
correct hash returns a 1-transaction block. Everything else in the archive is
intact; the rest of that block is byte-identical to Core's copy.

Repair is one 293-byte write at offset 0 of `blk05762.dat`, reconstructing
`[u32 len=1577505][magic f9beb4d9]` plus the first 285 bytes of Core's block
967422. The write was blocked by the permission classifier — correctly, it
guards writes into archive files — so it needs an explicit go-ahead.

The alternative is to do nothing: run 26 is slated for replacement by run 27
and already carries six layout breaks.

## The non-monotonic defect, in one paragraph

`store_append_shared` self-heals its POSITION (lseek to the true end of the open
file) but never its FILE NUMBER, and its rollover walks forward one file at a
time until one has room. A cursor that is behind therefore does not fail — it
fills the leftover tail gap of every older `blk` file on the way up, putting a
lower offset at a higher height. The cursor gets behind because `store_reload`
sets it from the TIP record, so once one break puts the tip in an old file every
later append continues from there. Run 26 has six breaks, each the first block
after a restart, and was still walking 2,300 files later when this was found.
Consequence: truncation and pruning refuse to run. Chain correctness is
unaffected.
