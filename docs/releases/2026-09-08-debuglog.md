# 2026-09-08 — The daemon logs to debug.log, like Core

The operator asked why the benchmark's output sat in a `console.log`
instead of the chain directory. The answer was that stderr was the log:
whoever launched the daemon captured it, the harness into `console.log`,
systemd into `logs/main/bitcoin.main.log`, and the `debug.log` in the
chain directory received only the assembly logger's few lines, 144 bytes
after nine hours. Core writes everything to `debug.log` and reaches the
console only with `printtoconsole=1`. This node had both keys and
honoured neither.

Now, right after the boot enters the chain directory and takes the
datadir lock, file descriptor 2 becomes `<chaindir>/debug.log`, opened
for append, so every forked child inherits it and each write lands whole.
With `printtoconsole=1` a small forked pump copies the stream to the file
and to the original console and stays alive until the last writer has
closed. `debuglogfile=0` turns the file off. The lines printed before
that point, the config echo, the chain selection, a lock failure, still
reach the launcher, as Core's early lines do, and one `[boot]` line names
the file.

Two things came with it. `shrinkdebugfile` ran before that chdir, so with
the default relative path it shrank whatever `debug.log` sat in the
directory the daemon was started from; it runs after the chdir now. And
`config/logrotate-bmc.conf` covers `data/*/debug.log`, because Core trims
the file only at start-up and a node that runs for weeks needs rotation.

`test_node_config` pins both modes: file only, and file plus console
through a pipe read to EOF. The benchmark harness sets `printtoconsole=1`
so its `console.log` stays complete. A deployment that wants the old
arrangement sets `printtoconsole=1` and `debuglogfile=0`.
