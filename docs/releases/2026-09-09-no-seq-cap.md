# 2026-09-09 — No sequence cap: the BIP68 ledger is sized to the transaction, like Core's

The morning's fix raised the per-transaction sequence cap from 2,048 to 24,576, a bound derived from the block weight limit. The operator's rule is stricter and right: Core has no cap, so neither do we. Consensus follows Core's behaviour wherever Core has one; where Core has none, we invent none.

- `val_read_tx` records every input's sequence into a buffer grown to the transaction's input count (Core's `tx.vin` is a vector that `CalculateSequenceLocks` walks in full). The input count is bounded by the transaction's own length, so the reservation cannot outrun the block buffer.
- The truncation flag and the BIP68 pass's refusal ("past the sequence window") are gone; there is no surplus to default.
