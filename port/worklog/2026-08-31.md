## 3. Archive genesis migration (one-height shift collapse)
main's new "wrong chain" genesis guard refused our archive: block 0 hashed to
`00000000839a8e…` (Core block 1) because the archive was one-height-shifted
(port@N = Core N+1; established earlier), i.e. the true mainnet genesis was
absent and block 0's slot held Core block 1.

Fix (verified under backup /root/archive_migrate_bak):
- Reconstructed the authoritative 285-byte mainnet genesis (verified byte-for-byte
  against Blockstream raw; header hash reverses to 000000000019d6…).
- Appended its on-disk frame `[u32 len=285][u32 magic 0xd9b4bef9][block]` to the
  FROZEN blk05695.dat (not the live tip file blk05714) at end=132779017.
- Rewrote index.dat: prepended the genesis record (fn=5695, pos=132779017,
  size=285, hash=6fe28c0a… internal order), shifted all 964809 old records +1.
- Moved utxo_applied_height.dat 964808 → 964809 (+1 for the genesis).
Result: chain is exactly Core[0..N] — H0=genesis, H1=Core[1], H2=Core[2], …,
all hash-matching + prev-linked through the tip (spot-checked 0..5,500000,964809).
Merged daemon now BOOTS (genesis guard passes), getblockcount=964812 (live tip),
8/8 peers, addrv2 active, syncing.
