## node_log production-log format: match x86 exactly (timestamp FIRST)

USER: "log file is fucked ... With timestamp before anything else" + want real
durable data in the repo, nothing in /tmp.

Root cause: port/arm64/node_log.S `node_log_str` PREPENDED the level KIND tag
(`SERVE `/`BLOCK `/`INFO ` ...) to every line before the caller's buffer. The
callers (ibd.c / ibd_lsm.c) already build their buffer as
`"YYYY-MM-DD HH:MM:SS.mmm <msg>"` (mirroring asm/daemon/log_ts.h), so the
resulting line was kind-first:
    SERVE 2026-08-27 07:33:51.313 node start (ibd_lsm ...)
x86 production format (log_ts.h) is timestamp-first:
    2026-08-27 06:41:04.130 [txrelay:5] 44.251.42.22: +1 tx accepted ...
Fix: node_log_str now emits the caller buffer as-is (timestamp first, no KIND
prefix). node_log_event is left as the raw "<KIND> a b c" low-level form.
Verified with a 6-line unit check:
    2026-08-27 08:04:53.091 node start (ibd_lsm resumable LSM download worker)
    2026-08-27 08:04:53.091 h7360 txs=1 utxo=7024 spent=0 sigs=0 runs=13
Rebuilt ibd + ibd_lsm with node_log.o.

## ibd_par: multi-client (<=16) parallel downloader — LOG PARITY with x86 node
USER: "not seeing startup banner / 16 clients / a lot missing... I want log parity."
Root cause: ibd_lsm was a SINGLE-peer downloader logging only sparse BLOCK/STORE
lines. The x86 daemon (asm/daemon/main.c) prints a startup banner (L3774) and
runs its boot catch-up across up to `catchup_workers` (default 16) parallel
clients, logging [catchup] <host> / [dl] heartbeat.

New port/arm64/ibd_par.c: resumable LSM-UTXO-backed downloader that keeps the
ENTIRE verified consensus/apply/UTXO path of ibd_lsm byte-for-byte and replaces
only the single-socket fetch with a poll(2) mux over up to 16 CONCURRENT peer
sockets (in-flight windows = #clients, applied in strict height order ->
MISSING_PREVOUT=0 preserved). Adds:
  - x86 startup banner (===== bmc-bitcoind LOG START ... =====) as first output.
  - per-client "[catchup] client N connected: <host> fd=M (LSM-RESUME)".
  - "[dl] progress: X/Y blocks verified, N clients, live utxo=Z" heartbeat every
    1000 blocks.
  - bounded nonblocking TCP dial (6s) so dead-partner fallback is fast.
Bugs fixed during bring-up: (a) g_fd[] was initialized to -1 AFTER the connect
loop, wiping every connected fd -> req_window(-1) no-ops, poll spins, 0 progress;
(b) bounded dial left fds NONBLOCKING and the p2p handshake isn't EAGAIN-safe ->
handshake always failed, client loop spun; fixed by clearing O_NONBLOCK after
dial; (c) [dl] heartbeat printed next_apply-start (negative) instead of next_apply.
Verified: 4 clients, 512 blocks h154500..155011 MISSING_PREVOUT=0 (live 1209336,
MATCH); 16 clients 1200 blocks h155012..156211 MISSING_PREVOUT=0 (live 1222443,
MATCH), all 16 clients + banner + [dl] heartbeat in data/logs/bitcoind.production.log.

## Consensus flags fix: SV_SIGPUSHONLY wrongly applied during block validation
The 10,000-block 16-client run (h156212..166211) reported bad_sig=7, all
err=26 = ERR_SIG_PUSHONLY, isolated to h163684 (tx13-15 in1) and h164675
(tx17 in1, tx19 in0/in1). Investigation:
- The downloaders used a FLAT validation flag SV_SIGPUSHONLY (SCRIpt_VERIFY_
  SIGPUSHONLY, the P2P STANDARDNESS flag) -- NOT a consensus flag. Block
  validation must use Core's GetBlockScriptFlags = per-block
  script_flags_for_block(height, hash).
- t_scan_sigs.c read the two archived blocks from index/blk and found 63 real
  txs each and ZERO non-push-only scriptSigs -> the rejects are NOT genuine
  script failures; they are artifacts of forcing the standardness flag (and/or
  the repo's documented push_only() 0x4b off-by-one, asm/Makefile L1215-1218).
  Correct consensus flags exclude SIGPUSHONLY.
- FIX: ibd_par.c / ibd_lsm.c / ibd.c now call script_flags_for_block(h, hash)
  per block and pass those bflags to sv_verify_script. Also added SIGPIPE ignore
  (peer closing mid-write killed the mux; x86 daemon does the same) + bounded
  nonblocking TCP dial reused across the client pool.
- Verified: forward 16-client run h166212..167711 -> bad_sig=0 MISSING_PREVOUT=0
  reload MATCH (live 1350379). Linking: bitcoin_script_flags.o added to IBDOBJS
  (drives ibd/ibd_lsm/ibd_par).

## ibd_par 16-client crash h177612: stack-buffer overflow in version payload
The 10,000-block 16-client run crashed after ~9.9k blocks with
"*** buffer overflow detected ***: terminated". Diagnosis:
- NOT scriptSig size: t_sigsize.c scanned h177000..177700 -> no scriptSig > 520
  (max ~252); sigb[520] is NOT the trigger in this era.
- ROOT CAUSE: connect_peer builds the P2P version message into `unsigned char
  v[102]` but a minimum version msg is ~103 bytes (with the fixed U/A it writes
  byte index 102 = ONE PAST the array). A 16-client run does many
  connects/reconnects over ~10k blocks, so this stack-frame corruption
  accumulates and is eventually detected as heap/stack "buffer overflow".
- FIX: v[102]->v[256] in ibd_par.c, ibd_lsm.c, ibd.c, live_blocks.c,
  live_download.c; also enlarged the fixed sigb[520] scriptSig copy to
  sigb[10000] (defensive; consensus scriptSigs can exceed 520 in other eras) in
  ibd_par/ibd_lsm/ibd.
- Verified rebuild; fresh 16-client segment launched from h177660.

## FAST cons-only download mode (match x86 dl_catchup performance)
FOUND (x86 asm/daemon/main.c + bitcoind.asm): the x86 build's fast catch-up
(dl_catchup) spawns up to 16 forked dlc_worker processes that each call
node_ibd_blocks_s = cons_verify (CHEAP structural: PoW/merkle/coinbase/txids)
+ store_append, and do NOT do per-sig ECDSA. So x86 reaches tip in a
network-bound parallel pass; the slow ECDSA sig verify + UTXO build is a
SEPARATE sequential pass (utxo_live). Our ibd_par did full inline single-
threaded ECDSA during download (~2.4k sigs/s) => that's why the grind crawls
(sig-dense era), ~2.6 blocks/s.
FIX: added g_fast mode (argv[8]) to ibd_par: skips the ECDSA + LSM UTXO apply
(no utxo_lsm up/get/del/flush/reload), keeping header load, store archive
cons_verify + store_append, the 16-client mux, [dl] and [dlc] logging. Resume =
archive tip+1, no LSM state needed. Converts the download to a network-bound
cons-only pass (matches x86 dl_catchup); UTXO+sig verification done afterwards
via build_utxo over the full archive. Usage: ibd_par <peers> <count> data 22 100 16 <start> 1
Commits: ibd_par.c g_fast (not yet run; verify on next launch).

## Peer model overhaul (x86 dl_bootstrap / dl_catchup parity) + FAST mode stability
USER: "stop using seeds as downloaders; seeds just seed peers; look at the x86
pipeline", "check what x86 does", "why aren't you parallelizing".
Implemented in ibd_par (all confirmed against asm/daemon/main.c dl_bootstrap +
dl_catchup + bitcoind.asm):
- connect_peer advances g_npeer ON SUCCESS (was only on failure) so fallback
  clients no longer all dial the SAME peer (bug: 15x 203.56.149.66).
- Parse P2P `addr` messages (parse_addr) + getaddr exchange -> build a
  DISCOVERED peer book (g_book, up to 1024, deduped). Seeds are now DISCOVERY
  ONLY: connect seed -> getaddr -> DROP (never a download peer).
- Client pool dials DISTINCT discovered book peers (known-good static IP pool
  prepended), static list only as last resort.
- FAST (cons-only) mode (argv[8]=1): skips ECDSA+LSM push apply => download is
  network-bound like x86 dl_catchup (cons_verify + store_append only); full
  sig/UTXO verification deferred to build_utxo.
- Unstuck the connect phase: tcp_dial_bounded 6s->2s, connect_peer retries
  147->40 (was: dead peers burned minutes per client => the pool never finished
  connecting). rotate_client now re-dials from the DISCOVERED book.
STATUS (honest): discovery + distinct peers + fast mode all work, BUT raw
getaddr-discovered peers (and the stale static list) are largely non-serving /
EOF-prone, so FAST download is currently FLAKY (0-48 blocks then peer EOF with
no reliable recovery). The old approach (given seeds as download clients) was
reliable because those are real full nodes. Reaching reliable discovered-peer
download matching x86 needs the fuller x86 machinery (validated known-good peer
memory, more aggressive ban/rotate cadence) -- next step.

## FAST download now PROGRESSES (stall fixed) + IP byte-order + seed-node bootstrap
- ROOT STALL CAUSE (fixed): when a client's reconnect failed, rotate_client set
  its window owner=-1 (orphan) but nothing ever re-issued an orphaned window, so
  the strict-height-order apply deadlocked on an orphaned head-of-line window
  (~48-144 blocks then permanent stall, all peer sets). FIX: on every window
  completion, the freed client FIRST adopts any orphaned window before issuing a
  new one. Verified: download now climbs 80->128->320->368 over the tick window
  instead of flatlining.
- IP BYTE-ORDER BUG (fixed): book_add_ip was formatting network-order s_addr
  MSB-first on a little-endian host -> known-good static peers were added
  byte-reversed (e.g. real 66.181.35.130 added as 130.35.181.66) and unreachable.
  Now formats LSB-first (network order). parse_addr likewise feeds network order.
- SEED-NODE BOOTSTRAP (per USER "download peers FROM the seeds, seeds just seed
  peers"): resolve the given seed hostnames to their real full-node IPs via
  getaddrinfo and add those to the book FIRST as reliable downloaders; the seed
  host itself is still discovery/getaddr-only and dropped. Combined with the
  static known-good pool + getaddr haul, the 16 clients dial distinct book peers.
- FAST (cons-only) downloader now works end-to-end and progresses; throughput is
  still limited by frequent peer EOFs (discovered pool quality) ~3 blk/s; reaching
  network-bound multi-core speed needs the fuller x86 rotation/backoff tuning.
