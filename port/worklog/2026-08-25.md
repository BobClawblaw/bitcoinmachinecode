# 2026-08-25 — secp256k1_point.S (core group operations) verified

## Milestone
Ported the ec-layer CORE from asm/secp256k1_point.asm to native AArch64
(port/arm64/secp256k1_point.S): point_double, point_add, point_add_mixed,
point_add_mixed_zr (with z-ratio out-param), and point_scalar_mul (w=4
windowed double-and-add over a 15-entry Jacobian table).

## Approach
- Same exported symbols/ABI so repo harnesses and the daemon link unchanged.
- The x86 original INLINES field add/sub via FE_* macros for speed; this port
  instead CALLS the already-verified fe_add/fe_sub/fe_mul/fe_sqr from
  secp256k1_fe.S. Correctness over speed; macro inlining is a PERF_SCOPE later.
- We could NOT use the repo's test_point_repr.c: it differentials against
  FROZEN x86-64 reference asm (tests/point_ref.asm, *_ref symbols) that won't
  link on ARM. So I built a fresh oracle: fuzz_point.py with an independent
  pure-Python Jacobian secp256k1 implementation (add-2007-bl, dbl-2009-l,
  mixed add, double-and-add scalar mul) driving the C driver fz_point.c.

## Verification
- repo test_point.c (point_double(G) == 2G affine): PASS native.
- fuzz_point.py: ~83,000 vectors across 7 seeds, 0 failures. Covers
  point_double/add/add_mixed/add_mixed_zr/scalar_mul, out-of-place AND
  in-place (r==p aliasing), and degenerate shapes explicitly injected
  (q==p/doubling branch, opposite->infinity, affine (0,0), Z==0), plus the
  z-ratio H out-parameter for add_mixed_zr.

## Bugs fixed (all caught by the oracle / gdb)
1. scalar_mul held loop state (R, base affine, table base, kbuf) in x19/x20/x22.
   But point_add / point_add_mixed / point_double CLOBBER x19..x22 with their
   own r/p/q/zr pointers. Result: table base destroyed -> all scalar results
   garbage (k=1 didn't even return G). root cause found with gdb dumping TAB
   intact but R scrambled. Fix: hold ALL scalar_mul loop state in x23..x28,
   which the leaf point_*/fe_* never write (they only touch x0-x18 and
   x19-x22). Registered this as a new skill pitfall.
2. top-of-file `.section .note.GNU-stack` pulled all following code into the
   note section (point_double "defined in discarded section" link error).
   Moved the directive to end of file.
3. window-loop control used plain `sub x28,x28,#1` (no S) so the flags for
   `b.mi`/`b.pl` were STALE, causing the remaining-windows loop to over-run
   even when only the top window existed -> 16x doublings scrambled R.
   Fixed to `subs x28,x28,#1`. Spot-checked every flag branch in the file is
   now preceded by cmp/subs.

  ported deps: pow_check, tx_parse, tx_txid, merkle_root. Verifies PoW, every
  tx parses in-bounds, first tx n_in==1 (coinbase), txid count == wire

  primitives -> VALID, proving data+primitives correct and isolating the bug to
  the asm orchestration.
- Debugging saga (the longest single bug of the campaign): the walk's
  loop-advance `sub x9,x9,x23; b.le .Ldone` used a plain `sub` which does NOT
  set NZCV, so `b.le` branched on STALE flags left by the earlier count-bounds
  `cmp` (81-285 = signed negative) and jumped straight to .Ldone -- the body
  (tx_parse/tx_txid/txid-copy) never ran, n=0, idx=81 != len. Fixed: `subs`.
  Same class of bug as the scalar_mul window loop; recorded in the skill.
- Frame lesson: keep small locals at LOW sp offsets and the 1 MiB tx_txid
  rebuild buffer ABOVE them; build the 0x100100 frame size in a register
  (exceeds the 12-bit stack immediate).

## bitcoin_sighash.S -- legacy_sighash ported + verified (2026-08-25, session)
Ported full asm/bitcoin_sighash.asm: copy_bytes, parse_varint, write_varint,
script_op_len, script_push_encode, script_find_and_delete, legacy_locate_nout,
legacy_sighash (9-arg, cap on stack).
- Differential fuzz fuzz_sighash.py vs independent Python Core-equivalent
  SignatureHash oracle: 30k vectors across 10 seeds (ALL/NONE/SINGLE x ACP,
  SINGLE uint256(1) quirk, codeseparator strip, malformed/truncated) = 0 fail.
Real bugs found & fixed in-module:
  1. `cmp reg,#0xffff` and `#0xffffffff` are out-of-range AArch64 compare
     immediates (write_varint, script_push_encode) -> register thresholds.
  2. `cmp reg,[mem]` is NOT valid AArch64 -> CMd macro (ldr x16,[x28,off]; cmp r,x16).
  3. legacy_locate_nout over-popped 5 reg pairs but pushed only 2 (odd ret addr
     0x400 segfault) -> push x21-x26 to match epilogue.
  4. parse_varint failure returned newptr=0 -> null tx cursor slipped bounds
     checks (segfault). Now returns -1 sentinel so every add/CMd/b.hi fails;
     cmn-x1 guard added on the n_out parse.
  5. script_find_and_delete .fad_copy_unit looped to .fad_decode (not .fad_mc),
     so OP_CODESEPARATOR units after the first were never stripped -> scF off
     by count, shifted all preimage content. Now loops back to .fad_mc.
  6. legacy_locate_nout reported n_out without validating outputs, so the SINGLE
     quirk (uint256(1)) fired on truncated txs that Core returns 0 for -> now
     fully walks outputs + locktime before reporting a valid n_out.
Verified: `make t_sighash` clean; fuzz_sighash.py 30k vectors 0 fail.

## Addendum 4 — bech32 / bech32m (BIP173 / BIP350) codec (2026-08-25)
Ported asm/bech32.asm to port/arm64/bech32.S: bech32_init, bech32_create_checksum,
bech32_verify_checksum, bech32_convert_bits, bech32_encode, bech32_decode (same

- Repo harness test_bech32: ALL PASS native (official BIP173 + BIP350 valid
  vectors, cross-spec rejection, BIP173 invalid set, real bc1q/bc1p-bech32m
  encodes, convert_bits 8->5 h160(G)) — 0 failures.
- Differential fuzz (fuzz_bech32.py + fz_bech32.c): 30k vectors across 12 seeds
  vs an independent pure-Python BIP173/BIP350 reference (polymod, convertbits,
  encode/create_checksum, verify incl. cross-spec rejection, decode round-trips
  and corrupted-string rejection): 0 failures.
- Bugs found (both caught by the higher-level fuzz harness):
  1. verify_checksum used x23 (spec) as a callee-saved holding register but
     never saved/restored it -> clobbered the caller's x23, a silent
     state-corruption that only manifested as a -O2 intermittent segfault in
     the driver (not with -O0/ASAN). Fixed by stp/ldp-shopping x23,x24.
  2. convert_bits error return used `mov w0,#-1` -> 64-bit return was
     0x00000000FFFFFFFF (4294967295, positive), tripping callers that check
     `n<0`; fixed to `mov x0,#-1` (matches the header "or -1" contract; the
     x86 original's `mov eax,-1` happened to leave 0xFFFFFFFF too).
- Pitfall added to skill: a C-callable leaf must save EVERY callee-saved reg it
  touches (x19-x28) even when the value is trivially re-loadable; a stray
  unsaved x23 is invisible under -O0 and only corrupts under -O2.
- Untracked build artifacts left local (bech32.o/test_bech32/fz_bech32);
  committed: bech32.S, fz_bech32.c, fuzz_bech32.py, Makefile, roadmap, worklog.
