## IBD — FOURTH DEEP-ERA BUG: FIXED + VALIDATED (h146.5k MISSING-PREVOUT)
ROOT CAUSE: UTXO slot table too small. ibd used slots=1<<20 (1,048,576). The real
2012-era UTXO set reaches ~1.0-1.13M outputs, driving the table to ~98% load at
h146.5k. At that real-key load (PAST the 88%-load fuzz-verified bound) a linear-
probe/Robin-Hood put/get edge silently drops an output -> later MISSING-PREVOUT.
Pinned exactly: real block 146699, tx[110] (a92c5a4a..) spends output[1] of tx[83]
(485ec24c.. = log form 9b04f2d1..), an INTRABLOCK spend; txid+parse are correct;
isolated replay (empty, and prefilled to 100% with DUMMY keys) retains the output,
but the real ~1M-key pool at ~98% load loses it.

FIX (ibd.c): slots 1<<20 -> 1<<23 (8M, ~48B*8M = ~384MB) + blob 1<<28 -> 1<<30 (1GB).
At 160k load is ~15% (1.27M/8M), deep in the verified regime. 0->160000 validation:
bad_gate=0 bad_sig=0, 3,638,533 sigs, utxo_count=1,266,361, "IBD VERIFY SIGNED OFF
NATIVELY", EXIT=0. Crossed the whole prior failure zone (146.7k mine / 154.2k cron).

Verified frontier: 0 -> 160,000 clean (was 141k).  4 deep-era bugs fixed total.

NEXT for full 0->963935: capacity for modern tip UTXO (~80M) -> will need slots
~1<<27 (134M) and multi-GB blob before attempting the segwit->tip leg (s8).

returns -2 for valid heights (idx_len@st+16 vs tip@st+24 mismatch)". That was
WRONG. A C probe (store_init+store_reload+dump struct+bare store_get_at on the
real data/ store) shows store_get_at returns 1 with correct
meta[data_pos,size,file_no] for EVERY height; store_reload sets idx_len=1440
and tip=29 consistently. The actual reason every block-reading command returned
"error: height out of range" (cmd_getblockhash maps ANY failure to err_range)
is that each command's on-stack block buffer -- 0x800=2KB (getblockhash),
0x4000=16KB (getbestblockhash), 0x180=384B (getblock/gettx/getbalance) -- is
identical to the x86 original's sizes and far too small for live_blocks'
~1.6-1.8MB segwit blocks, so cli_load_block bailed at its `cmp size,cap; b.hi
.fail`. This is an x86-shared limitation, not a porting defect.

FIX (AArch64-only, keeps the CLI useful on the real chain):
- Added CLI_BLK = 0x400000 (4MiB, >= Core MAX_BLOCK_SERIALIZED_SIZE 4,000,000).
- Enlarged every command frame so its blockbuf holds CLI_BLK bytes: getblockhash
  + getbestblockhash relocate hbuf/rev above the buffer (sp+CLI_BLK/+0x20);
  getblock relocates bin/rev/hbuf above it; gettx/getbalance grow F_TX/F_GB to
  0xe0/0xd0 + CLI_BLK. All 4MiB immediates loaded via `movz xN,#0x40,lsl#16`
  (LB macro) -- GAS `mov` cannot encode 0x400060/0x400000 in one instruction.
  Frames adjust via `LB x9; add x9,x9,#off; sub/add sp,sp,x9` (12-bit range).
- Fixed a self-inflicted epilogue bug (ldp x25,x26 -> ldp x23,x24 in
  cmd_getbestblockhash, which never saves x25/x26).
- asm/daemon/cli.c out[] 1<<20 -> 16<<20 so getblock can emit a full 4MB block
  as up to 8MB of hex.

VERIFIED natively against the real data/ store (/tmp/bcli data ...):
getblockcount=30; getblockhash 0,1,2,3,4,10,28,29 each return the CORRECT
per-height hash (block 2 == double-SHA256 of its loaded header in Python);
getbestblockhash == getblockhash 29 (both = tip); getblock by-number and
by-hash return the exact raw bytes (by-hash matches the given block's header);
getbalance = 3459106374 (sum of the 30 stored coinbase outputs); help works.
test_cli_helpers.c ALL PURE-HELPER TESTS PASSED. NOTE: heights 28,29 in this
live_blocks test store duplicate blocks 0,1 (a store-population quirk, not a
CLI bug -- CLI reports whatever bytes the store holds). No bitcoin_store.S
change was needed; store_get_at was correct all along.

## secp256k1_point_ct.S (2026-08-26) -- CONSTANT-TIME scalar mul, signing path, VERIFIED
Ported asm/secp256k1_point_ct.asm (593 lines) -> port/arm64/secp256k1_point_ct.S
(1500 lines): the constant-time secp256k1 scalar multiplication + homogeneous
point ops used ONLY on secret-scalar (signing) paths. Exports:
  pointh_add(r[12], p[12], q[12])       -- complete add, homogeneous (X:Y:Z)
  pointh_double(r[12], p[12])           -- complete doubling, homogeneous
  point_scalar_mul_ct(r[12], xy[8], k[4]) -- k*affine(xy), CONSTANT TIME -> Jacobian
Uses Renes-Costello-Batina COMPLETE formulas (a=0, b3=21) so the add/double are
exception-free by construction (identity, P==Q, P==-Q all handled, no branches).
Calls the already-verified fe_add/fe_sub/fe_mul/fe_sqr leaves (all branch-free),
so the CT property is preserved. The 256-iteration ladder does one complete
double + one complete add per bit and commits/discards the add result with CSEL
(never a branch on a secret bit); no secret-indexed memory; the infinity
canonicalisation is CSEL-driven. Constant structure mirrors the x86 source.
Driver t_pct.c + fuzz_pct.py (new): differential vs the already-ported+verified
VARIABLE-TIME point_scalar_mul (same affine point) AND vs an independent
pure-Python secp256k1 group oracle (ec_add/double/scalar-mul, random on-curve
points generated via field sqrt -- no shared code path with the port), plus
group-law checks for pointh_add/pointh_double incl. P==Q, P==-Q -> inf, identity,
and edge scalars 0,1,2,n-1,n,n+1,n-2,n//2,2^255,2^255-1.
RESULT: 14 seeds x 300 iters = 21,255 vectors, 0 mismatches (ct==vt==python,
add/double==group law); `make t_pct` + `make fuzz_pct` (8x150) = 0 fail.
Two harness bugs found+fixed during bring-up (NOT port bugs): my scalar/limb hex

### port/arm64/bitcoin_scriptverify_drv.S  (svs) — 3 port bugs
1. REAL PORT BUG (the "corrupt script pointer"): in the BIP16 redeem path the
   code loaded `cp.sp` into x9, then called the TLSLAZY macro for the svs_redeem
   arena, then did `sub x9,x9,#1; mul ...` on x9 to compute `copy_e + (cp.sp-1)*
   ELEM_SIZE`. TLSLAZY uses x9 as its TLS-slot-address scratch, so x9 no longer
   held cp.sp — the redeem top-of-stack index was garbage, producing a corrupt
   (out-of-bounds) script pointer -> segfault. FIX: reload cp.sp from the frame
   AFTER the TLSLAZY call (reordered; cp.sp check moved after it).
2+3. AAPCS CALLEE-SAVED bug: entry did `mov x19,x0 ... mov x27,x6 mov x28,x7`
   and read work/workcap into x25/x26 BEFORE the prologue `stp x19,x20 ...`,
   so the pushed save-slots held the ARG values and the epilogue restored
   those — clobbering whatever the caller kept in x19..x28. FIX: read the 2
   stack args into caller-saved x9/x10 first, push the caller's x19..x28, then
   calibrate x19..x28 from x0..x7 / x9,x10.

### port/arm64/bitcoin_witness_v0_drv.S  (wv0) — 2 port bugs
1. PROLOGUE/EPILOGUE MISMATCH: prologue saved 6 pairs (x29,30; x19..x28) but the
   epilogue `add sp,#208` then popped only 5, starting at x25,x26 — one pair
   short AND shifted, so every callee-saved register (incl. x26) was restored
   from the wrong slot and x29/x30's real slot was never read (x30 = saved x20
   -> garbage `ret`). This is the "x26 callee-saved anomaly"; it also corrupted
   the caller's frame at -O2. FIX: epilogue now pops all 6 pairs in matching
   order (x27,28 / x25,26 / x23,24 / x21,22 / x19,20 / x29,30).
2. AAPCS CALLEE-SAVED bug (same class as svs #2): entry read the 4 stack args
   into x1..x4 and moved x0..x5 into x19/x20/x21/x22/x23/x28 BEFORE pushing, so
   the epilogue restored arg values, not the caller's registers. Confirmed via
   gdb: the O2 caller held its result in w19 across the asm call and read back
   garbage after. FIX: read stack args into caller-saved x9..x12, push first,
   then calibrate / fill the ctx from x0..x7 and x9..x12.
