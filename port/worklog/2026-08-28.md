## bitcoin_bip32.S independent differential verification (BIP32 HD keys) — DONE
Prior offline commit 0fed12b had already ported bitcoin_bip32.S and verified it
against the repo test_bip32_chain + test_bip32_extkey harnesses + the official
BIP32 spec vectors, but with NO independent differential coverage. Following
the chainwork/muhash precedent, this cron run added one: an independent
pure-Python BIP32 oracle differential, port/arm64/fuzz_bip32.py.

Coverage (self-contained: gcc compiles the driver C + all needed .S sources in
a temp dir -> reproducible from a clean checkout, no stale .o dependency):
- bip32_master: random seeds of length 16..64 octets.
- bip32_ckd_priv: multi-step chains 1..12 deep over the DEP end, mixing
  hardened + normal branches and the boundary indices 0 / 0x7fffffff /
  0x80000000 / 0xffffffff. The NORMAL branch forces scalar_to_pubkey
  (k*G via the verified fixed-base comb) so a pubkey/point bug would surface
  as a wrong derived key, not just a bad ckd_priv.
- bip32_derive_path: full-path happy-path must equal the stepwise ckd chain.
- bip32_fingerprint: hash160(compress(k*G))[:4] recomputed independently.
- bip32_extkey_serialize: BOTH priv (keylen 32, 0x00 pad, version 0x0488ADE4)
  and pub (keylen 33, version 0x0488B21E), random depth 0..254 + boundary
  child indices -> exact 78-byte serialized extkey.
Oracle replicates the .S return-code semantics bug-for-bug (scalar_small_nonzero
= 0<k<=n with k==n->1; master rc = 1 iff any nonzero byte), so rc is compared
exactly, not idealized.

RESULT: 35,305 cases across 8 seeds, 0 fail (byte-exact k/c/rc, 4-byte fp,
78-byte serialized extkey). The module's mod-n reduction (each BE 8-byte limb
rev'd before the adds/adcs chain) — the documented AArch64 BE-carry pitfall —
is now verified across the value space, not just the handful of spec vectors.

Also exercised in the same link: bitcoin_hmac (hmac_sha512), bitcoin_keys
(scalar_to_pubkey/scalar_small_nonzero), bitcoin_addr (hash160) — all byte-
exact against hashlib/RSA BIP32 references.

Driver note: the initial draft's `sscanf` only captured 6 of the 7 S-op fields,
so the driver passed a zero key -> spurious S failures. The asm was CORRECT
(every header/chain-code byte matched; only the driver-fed key was zero).
Tokenizing the S line manually fixed it. Diagnostic lesson: when a fuzz driver
feeds a byte field as zeros, check the DRIVER's argument parsing before
suspecting the asm.

Two DRIVER/ORACLE lessons (not asm bugs -- the .S was correct):
- strtok cannot represent an empty passphrase token (the documented empty-token
  pitfall): `S  <mn>` with a double space collapses so the pass arg reads the
  mnemonic and the mnemonic reads NULL -> strlen(NULL) SEGV. Fixed with a '-'

  assumption is WRONG. Expected values must be recomputed by the oracle from the
  corrupted string (the asm was returning valid wordcount correctly).

## sha256 ARMv8 SHA-2 crypto-extension acceleration — DONE (7.9x on sha256_block)
x86 sha256.asm has a cpuid-gated SHA-NI block (sha256_block_shani) complementing
its scalar body; our scalar-only port was leaving ~8x on the table on this
Grace (GB10, has sha2 HWCAP). Added the AArch64 analog:

- port/arm64/sha256.S now carries BOTH the scalar block (untouched) AND a
  crypto-extension block sha256_block_shani (faithful port of the CRYPTOGAMS/
  Polyakov ARMv8 SHA2 core from OpenSSL sha256-armv4.pl .LARMv8: state held as
  {a,b,c,d}/{e,f,g,h} in v0/v1, the SHA256H/H2 pair handles the a,b,e,f
  interleave internally, 12 schedule iterations + 4 tail groups = 64 rounds,
  msg quads rotated v2..v5 with SHA256SU0/SU1).
- sha256_block lazily probes ID_AA64ISAR0_EL1.SHA2 (bits[15:12]>=1) once into a
  shani_ready flag and tail-calls the crypto block when present; scalar remains
  the portable fallback on CPUs without SHA2. Uses only caller-saved regs
  (x0-x5, v0-v7, v16-v19) so the fast path needs no prologue.
- Verification: pre-dispatch block differential sha256_block_shani vs the
  scalar sha256_block on 2,000,000 random (state,block) pairs + full edge sweep
  (zero/all-ones blocks, every single-bit of a 64B block from the IV) = ALL
  MATCH; post-dispatch repo test_sha256 KAT vectors ALL PASS and fuzz_sha256.py
  (pure-Python hashlib oracle, full + streaming over 130 varint-ed length cases
  + 300 randoms x 2 trials = 882 messages) = 0 fails; the full taproot suite
  (test_taproot_sighash 48/48, test_bip341_diff 1684/0, fuzz_taproot 4x800
  byte-exact) re-verified with the new sha256 underneath.
- Benchmark (Grace): sha256_block scalar 4.40M blk/s -> crypto 34.66M blk/s =
  7.88x; sha256_full end-to-end ~2.1 GB/s (64MiB) and ~0.10us for 64-319B
  txid/sighash-shaped hashes.
- Build plumbing: sha256.S now emits SHA256H/SU0/SU1 mnemonics, so every place
  that assembles it needs -march=armv8.2-a+sha2: added CARCH to the port
  Makefile implicit %.o rule, to build_daemon.sh's object loop, and to the
  self-contained fuzz drivers (fuzz_bip32/bip39/taproot gcc lines). shani_ready
  is reached via GOT (:got:) so sha256.S links cleanly in both -no-pie and

inline wide-compactsizeread used `ldr[h] w9/x9,[x26]` for the 0xfd/0xfe/0xff
