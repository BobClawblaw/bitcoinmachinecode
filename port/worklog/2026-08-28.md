## bitcoin_bip32.S independent differential verification (BIP32 HD keys) — DONE
Prior offline commit 0fed12b had already ported bitcoin_bip32.S and verified it
against the repo test_bip32_chain + test_bip32_extkey harnesses + the official
BIP32 spec vectors, but with NO independent differential coverage. Following
the chainwork/muhash precedent, this cron run added one: an independent
pure-Python BIP32 oracle differential, port/arm64/fuzz_bip32.py.

Coverage (self-contained: gcc compiles the driver C + all needed .S sources in
a temp dir -> reproducible from a clean checkout, no stale .o dependency):
- bip32_master: random seeds of length 16..64 octets.
- bip32_ckd_priv: multi-step chains 1..12 deep over the DEP end, mixing
  hardened + normal branches and the boundary indices 0 / 0x7fffffff /
  0x80000000 / 0xffffffff. The NORMAL branch forces scalar_to_pubkey
  (k*G via the verified fixed-base comb) so a pubkey/point bug would surface
  as a wrong derived key, not just a bad ckd_priv.
- bip32_derive_path: full-path happy-path must equal the stepwise ckd chain.
- bip32_fingerprint: hash160(compress(k*G))[:4] recomputed independently.
- bip32_extkey_serialize: BOTH priv (keylen 32, 0x00 pad, version 0x0488ADE4)
  and pub (keylen 33, version 0x0488B21E), random depth 0..254 + boundary
  child indices -> exact 78-byte serialized extkey.
Oracle replicates the .S return-code semantics bug-for-bug (scalar_small_nonzero
= 0<k<=n with k==n->1; master rc = 1 iff any nonzero byte), so rc is compared
exactly, not idealized.

RESULT: 35,305 cases across 8 seeds, 0 fail (byte-exact k/c/rc, 4-byte fp,
78-byte serialized extkey). The module's mod-n reduction (each BE 8-byte limb
rev'd before the adds/adcs chain) — the documented AArch64 BE-carry pitfall —
is now verified across the value space, not just the handful of spec vectors.

Also exercised in the same link: bitcoin_hmac (hmac_sha512), bitcoin_keys
(scalar_to_pubkey/scalar_small_nonzero), bitcoin_addr (hash160) — all byte-
exact against hashlib/RSA BIP32 references.

Driver note: the initial draft's `sscanf` only captured 6 of the 7 S-op fields,
so the driver passed a zero key -> spurious S failures. The asm was CORRECT
(every header/chain-code byte matched; only the driver-fed key was zero).
Tokenizing the S line manually fixed it. Diagnostic lesson: when a fuzz driver
feeds a byte field as zeros, check the DRIVER's argument parsing before
suspecting the asm.

## bitcoin_bip39.S independent differential verification (BIP39 mnemonic codec) — DONE
The AArch64 port of asm/bitcoin_bip39.asm had been committed offline with NO
roadmap [x] and NO ARM-native test run -- the port Makefile had no target, so
the .S was never even linked. This cron run closed that gap:

1. NATIVE HARNESS: built the repo's asm/tests/test_bip39.c against the ported
   bitcoin_bip39.S + sha256.S + bitcoin_hmac.S + sha512.S. ALL PASS, 0 failures
   (24 generated vectors: generate->validate->mnemonic_to_entropy round-trip,
   empty-passphrase seed, official "TREZOR"-passphrase seed; plus
   positive/negative corruption cases that must be rejected).
2. INDEPENDENT DIFFERENTIAL: port/arm64/fuzz_bip39.py -- a self-contained
   gcc-from-.S driver (compiles the .S deps in a temp dir, reproducible from a
   clean checkout). Oracle is pure-Python BIP39: 11-bit group codec + SHA-256
   checksum + PBKDF2-HMAC-SHA512 (hashlib, c=2048) -- a DIFFERENT implementation
   than the asm's in-loop HMAC. The wordlist is PARSED from bip39_words.S.inc
   (the same 9-byte .byte records the asm links) so oracle and port index
   identical words.
   Coverage: generate over ALL legal entropy sizes (128/160/192/224/256);
   validate + mnemonic_to_entropy on valid AND corrupted mnemonics
   (bad-checksum, unknown word, wrong word count, shuffled); mnemonic_to_seed
   for random empty + non-empty passphrases.
   RESULT: 38,400 cases across 8 seeds, 0 fail -- byte-exact mnemonic, entropy,
   rc and 64-byte seed.  (make fuzz_bip39 reproduces.)

Two DRIVER/ORACLE lessons (not asm bugs -- the .S was correct):
- strtok cannot represent an empty passphrase token (the documented empty-token
  pitfall): `S  <mn>` with a double space collapses so the pass arg reads the
  mnemonic and the mnemonic reads NULL -> strlen(NULL) SEGV. Fixed with a '-'
  sentinel for empty pass (unambiguous -- every real token is hex).
- A randomly "corrupted" mnemonic can COINCIDENTALLY pass the BIP39 checksum
  (~1/16 for a 128-bit-entropy 4-bit CS), so "corruption == -1" as an oracle
  assumption is WRONG. Expected values must be recomputed by the oracle from the
  corrupted string (the asm was returning valid wordcount correctly).

TWO REAL AArch64 BUGS found by the fuzz, both fixed and re-verified:

1. tap_leaf_hash BOUND CONSTANT WRONG: the failure bound was assembled as
   0x3FFFC6 (CAP-58) instead of TAP_PREIMG_CAP-70 = 0x003FFFBA (I mis-derived
   my first fix too: 0x400000-70 is 0x3FFFBA, and 0x400000-0x46 lands at
   0xFFBA in the low half, NOT 0xFFFA -- re-derived with the disassembler
   before it stuck). slen in (4194234, 4194246] slipped past the bound, the
   script copy overran the 4MiB TLS tap_preimg -> SIGSEGV where x86 returns
   rc=0 cleanly. Confirmed the exact crash in gdb (__cp_tw ldrb into TLS).

2. tap_branch_hash COMPARED THE WRONG OPERANDS: the .S loaded
   x0=tap_preimg+64 (the destination scratch!), x1=a, x2=b before
   `bl __tb_cmp` -- so the lexicographic sort compared the scratch buffer
   against a (never b), always concluded "a first", and emitted UNSORTED
   TapBranch(a||b) for every b<a. x86 sorts node=TapBranch(min||max), so
   every >=1-sibling script-path spend reconstructed the WRONG merkle root
   -> valid spends rejected (and crafted spends accepted against a different
   root than Core: chain-split class). tap_merkle_root's own inline compare
   was correct (proper node-vs-sibling operands); the dead __tb_cmp call
   only poisoned the standalone helper. Both failures reproduced in a
   minimal driver, fixed (mov x0,x20; mov x1,x21 before the bl), and the
   sorted output now matches the Python oracle byte-for-byte.

Why the repo's 48-check taproot harness never caught #2: its script-path
vectors are single-leaf (no control siblings) -- a reminder that the repo
harness + fresh boundary-focused differential fuzz are COMPLEMENTS, not
substitutes.

Harness-side lessons (mine, not the asm's): an empty hex token in a
whitespace-driven sscanf protocol is unparseable -- use "-" sentinels for
empty fields (third time this lesson has appeared in this project: scriptcodec,
bip39, now taproot); "0-byte present annex" is semantically distinct from
"no annex" (spend_type bit) and needed its own "z" token; and a
write-stdin-then-read-stdout sequence over pipes DEADLOCKS once output
exceeds the pipe buffer (~64KB / ~130 output lines) -- build the full input
and use subprocess.run so both pipes are pumped concurrently (the 16-minute
"hang" on seed 1 was this, not slowness).

## sha256 ARMv8 SHA-2 crypto-extension acceleration — DONE (7.9x on sha256_block)
x86 sha256.asm has a cpuid-gated SHA-NI block (sha256_block_shani) complementing
its scalar body; our scalar-only port was leaving ~8x on the table on this
Grace (GB10, has sha2 HWCAP). Added the AArch64 analog:

- port/arm64/sha256.S now carries BOTH the scalar block (untouched) AND a
  crypto-extension block sha256_block_shani (faithful port of the CRYPTOGAMS/
  Polyakov ARMv8 SHA2 core from OpenSSL sha256-armv4.pl .LARMv8: state held as
  {a,b,c,d}/{e,f,g,h} in v0/v1, the SHA256H/H2 pair handles the a,b,e,f
  interleave internally, 12 schedule iterations + 4 tail groups = 64 rounds,
  msg quads rotated v2..v5 with SHA256SU0/SU1).
- sha256_block lazily probes ID_AA64ISAR0_EL1.SHA2 (bits[15:12]>=1) once into a
  shani_ready flag and tail-calls the crypto block when present; scalar remains
  the portable fallback on CPUs without SHA2. Uses only caller-saved regs
  (x0-x5, v0-v7, v16-v19) so the fast path needs no prologue.
- Verification: pre-dispatch block differential sha256_block_shani vs the
  scalar sha256_block on 2,000,000 random (state,block) pairs + full edge sweep
  (zero/all-ones blocks, every single-bit of a 64B block from the IV) = ALL
  MATCH; post-dispatch repo test_sha256 KAT vectors ALL PASS and fuzz_sha256.py
  (pure-Python hashlib oracle, full + streaming over 130 varint-ed length cases
  + 300 randoms x 2 trials = 882 messages) = 0 fails; the full taproot suite
  (test_taproot_sighash 48/48, test_bip341_diff 1684/0, fuzz_taproot 4x800
  byte-exact) re-verified with the new sha256 underneath.
- Benchmark (Grace): sha256_block scalar 4.40M blk/s -> crypto 34.66M blk/s =
  7.88x; sha256_full end-to-end ~2.1 GB/s (64MiB) and ~0.10us for 64-319B
  txid/sighash-shaped hashes.
- Build plumbing: sha256.S now emits SHA256H/SU0/SU1 mnemonics, so every place
  that assembles it needs -march=armv8.2-a+sha2: added CARCH to the port
  Makefile implicit %.o rule, to build_daemon.sh's object loop, and to the
  self-contained fuzz drivers (fuzz_bip32/bip39/taproot gcc lines). shani_ready
  is reached via GOT (:got:) so sha256.S links cleanly in both -no-pie and
  shared-object (.so) builds.

AArch64 notes for future work: (1) `mrs ID_AA64ISAR0_EL1` from EL0 to probe SHA2;
(2) `csel with 32-bit operands uses wzr, NOT xzr` (xzr is the x-register
alias -- classic mismatch); (3) a GLOBALLY-BOUND symbol referenced from PIC
(.so) asm must use adrp :got: + ldr :got_lo12: (plain adrp+:lo12 only links in
non-PIE); local .rodata labels (KSHA256/K256) stay plain adrp+:lo12.

REAL ARM BUG found + fixed in port/arm64/bitcoin_txv_parse.S: the RDCS
inline wide-compactsizeread used `ldr[h] w9/x9,[x26]` for the 0xfd/0xfe/0xff
cases, i.e. read the DISCRIMINATOR byte as the LOW byte of the length, when
the value lives at [x26+1] (after the width byte). Advance counts were
already correct; only the loads were off-by-one. Effect: ANY tx with a
multi-byte length field (scriptSig >= 0xfd, or 0xfd-encoded lengths, big
nin/nout/script/witness) parsed the length as ~0x03fd etc. instead of the
true value, misadvanced the cursor, and rejected VALID txs as "truncated
scriptSig/sequence" -- and collapsed all downstream truncation reasons.
Probe on build_tx shapes: the big_varint shapes (4: 5-in segwit, 6: 3-in)
failed full-length accept (ARM reject vs C accept) plus 299 total
mismatches pre-fix; after `ldr <reg>,[x26,#1]` on all three wide cases, the
whole suite is 0. Same failure class as the documented parse_varint
width-dispatch pitfall (bitcoin_sighash.S) -- this port has a recurring
theme of wide-compactsize handling, worth auditing other *varint* read
routines for a missing #1 on the discriminator.

Harness side: test_txv_parse_diff wants a real block for the corpus walk
(80-byte header + txcount + txs); blockstream.info block 800000 raw was
used (1.6MB, post-taproot, heavy segwit) -- 3,721 txs, best real coverage.
