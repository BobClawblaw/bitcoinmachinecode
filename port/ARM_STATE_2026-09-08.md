# ARM port — state at the 2026-09-08 halt

**Decision (operator, 2026-09-08 ~18:30 CDT):** the AArch64 port is **PAUSED on
this host** (`xspark04`, 20-core Grace CPU / 121 GiB RAM, nvidia kernel). The
box is dedicated to serving an LLM and `bmcbitcoind` was competing with it for
CPU and memory. The next round of port work moves to a Raspberry Pi the
operator is standing up.

Nothing was deleted, reverted or rebased. The branch, the built binaries and
1.5 TB of chain data are all intact. Only the *running* node was stopped, and
the two systemd units that could restart it were disabled.

Read in this order: `port/ARM_PORT.md` (branch model, how to resume) -> this
file (state + what to work on) -> `port/PORT_ROADMAP.md` (per-module port
status) -> `worklog/2026-09-08.md` sessions 2-5 (the day's narrative) ->
`TODO.md` (the open board).

## Why it stopped, and what is off now

`bmc-arm.service` (the live stability node) and `bmc-logrotate.timer` are both
`disabled` + `inactive`; the unit symlinks are gone from
`multi-user.target.wants/` and `timers.target.wants/`, so a reboot does not
bring the node back. Unit files and the `coredump.conf` drop-in are untouched
on disk.

Killed on the way (all were ARM-build leftovers, not part of the LLM stack):

| process | owner | state found |
|---|---|---|
| `test_interp_core_vectors` | root | **100% CPU for 6 d 4 h** (~148 CPU-hours), orphaned behind a `bash -c` wrapper whose script had no newlines and hung forever |
| `t_stack /tmp/x1.txt` | root | **99.9% CPU for 14 d 6 h** (~205 CPU-hours), orphaned, and its own executable was `(deleted)` — rebuilt over on 08-25 and never reaped |
| `bmcbitcoind` (main + worker) | xian | 6.8 GB RSS, 44% CPU, worker stuck in `D`; respawning 15 s after every kill because `Restart=always` |
| `journalctl -u bmc-arm` watch loop | root | orphaned `while true; do sleep 120; ... done >> /tmp/utxo_watch.log`, up since 09-02, polling the journal of a node that was already stopped |

**Both spin-hangs are already fixed in the current tree — re-verified tonight,
not assumptions:**

- `timeout 25 ../port/arm64/parity_out/test_interp_core_vectors` -> **`ALL PASS
  (0 failures)`**, 18 verdict lines vs the stuck process's 14. The spinner was a
  pre-09-08 binary (started 09-02); the on-disk build is dated 09-08 10:15.
- `t_stack` rebuilt from source and fed the *exact* 7-op script that had spun
  (`R / P 11 / P 22 / X / d / T / 2`) -> `d=2`, `t:11`, `s2:22`, **exit 0**.
  That is the correct answer after the swap, so the IR-6 handle accessors are
  sound today.

Lesson recorded for the next session: **rebuilding a harness does not kill the
copy that is already running.** Five days of one core each went to two binaries
whose bugs had long since been fixed. Sweep/soak hygiene: after every rebuild,
`pgrep -af '[t]est_...'` / `pgrep -af '[t]_'` and kill leftovers, and check
`/proc/<pid>/exe` for `(deleted)` — that marker means the process is running
code that no longer exists in the tree. (Bracket patterns are mandatory: plain
`pgrep -f bmcbitcoind` self-matches the compound command carrying it; that
mis-killed a session's own shell on 09-08, logged in session 4.)

## Known defects, ranked — what the next session should actually do

1. **`mac_rsort_desc` (the radix flush sort) is the prime suspect for a
   production-shaped memory corruption. It is SUSPENDED, not fixed.** The
   fresh-sync boot loop crashed 5 of 6 boots 35-90 s in with radix as the
   default; the one merge-default boot ran clean. gdb caught a victim thread
   (`boot_utxo_progress`) with `si_addr = 0x0` inside `clock_nanosleep` and a
   faulting instruction (`mov x19,x0`) that cannot fault — i.e. the corrupted
   frame belongs to someone else. Line-by-line review found nothing.
   `mac_sort_mode` now defaults to **0 (merge) on ARM only**, x86 keeping radix;
   the full incident note is the comment above the symbol in
   `port/arm64/bitcoin_utxo_lsm.S` (~line 900) — read it before touching the
   sort. Cost of the divergence: flush sort 651 ms/4M instead of 153 ms.
   **Owed: an offline stress harness** — radix vs merge, randomized
   production-shaped descriptor arrays (not the synthetic ones
   `test_lsm_flush_sort_diff` passes on), odd `n`, heavy tombstones, the
   `.bss` per-depth counts reused across calls. This is the single most
   important open item: it is silent-corruption-shaped, and the reason radix
   is off is that we could not prove it innocent.
2. **`[check] block data is NOT laid out monotonically (first break at height
   353881) -- truncation and pruning will refuse to run`**, printed on every
   boot of the fresh store. The archive is complete and hash-checked, so this
   is the per-chunk committer's layout claim being violated, and it disables
   prune/truncate. Root-cause it (find the out-of-order region around
   353,881 in `blk*.dat`/`index.dat` and name the chunk that landed it there)
   or, if the check is wrong about a legal interleaving, fix the check. Either
   way do not leave the line in the log unexplained.
3. **`bitcoind.S` CC-2 is half-wired:** the hook table exists as data symbols
   (`g_peer_sendcmpct`, `g_cmpct_hook_type`) but the mux never CALLs them — no
   sendcmpct announcement after verack, no hook-selected getdata type. Compact
   block receive is inert on ARM while x86 does both.
4. **Peer-pool / upstream ask:** the merged tree carries upstream's
   `1d543d08` NODE_WITNESS dial filter, which replaced an arm-port local
   workaround, and it fires on REAL peers here (3 drops in arm-12's first 15
   min; legs 4-5/8 where the old build held 5-6). The BIP141 commitment check
   is what actually protects the archive, so the ask upstream is a soft
   preference or a config, not a ban. Unverified on a Pi — a different network
   position may change the numbers.
5. **Upstream gate defect:** `7781987c` added an `asm/Makefile` rule for
   `tests/test_par_threads` without committing `asm/tests/test_par_threads.c`
   and left the target out of the `test:` run list, so x86's own gate never
   builds it. It is ARM's 1 remaining build-fail row. Commit the source or
   delete the rule.
6. **MuHash parity vs Core is still not done.** It needs the UTXO set at a
   matched height, so it is gated on finishing the build above. Recipe:
   `validation/muhash_vs_core.sh` asks both nodes for
   `gettxoutsetinfo muhash` at the same height; oracle credentials live at
   `/etc/bmc-oracle/umbrel.cookie` (root 0600, never committed).
7. Standing policy from the operator (2026-09-08): **deploy new builds as they
   gate green**, two-step rename deploy, verify boot (reload time, 0 invalid,
   tip advance, mempool, peers), keep a rollback artifact per build. Rollbacks
   on disk: `port/arm64/daemon_out/rollback/` (12 entries; `bitcoind.pre-arm13-20260908`
   = `cfe86ed4` = arm-12 is the pre-arm-13 image).

## Moving the work to a Raspberry Pi

What a Pi can and cannot carry, stated as numbers so nobody plans around a
myth:

- The fresh mainnet store is **746 GB and incomplete**; the previous one is
  **731 GB**. A Pi with a USB-NVMe *can* hold them, but re-downloading or
  re-building either on a Pi is a multi-day exercise at best, and the UTXO
  build is RAM- and core-bound (`slots=2^23`, 16 LSM runs merging 29 s each on
  this box). **Do not plan to continue the mainnet UTXO build on a Pi.** Leave
  the store on `xspark04`, cold, and schedule a window on it if the build must
  finish.
- What a Pi does carry well, and where the port's real gate lives:
  - the **full parity sweep** — `bash port/arm64/parity_sweep.sh` (434 plan
    rows, ~400 compared; the round-44b baseline is pass 376 / fail 4 env-only);
  - every **module differential and fuzz** (`make -C port/arm64
    consensus_diffs mempool_diffs addrv2_diffs cmpct_diffs fuzz_lsm fuzz_bip32
    fuzz_bip39 fuzz_taproot txv_diffs`), the `t_*` drivers;
  - `make -C port/arm64 abi-a64-check` — the AArch64 ABI auditor gate
    (`scripts/abi_callee_saved_audit_a64.py`), 761/761 frames followed;
  - `port/arm64/build_daemon.sh` builds the node (it links to
    `.bmcbitcoind.new` and adopts it with `mv(2)`; in-place gcc was ETXTBSY);
  - short **functional** syncs: testnet4 or signet, or mainnet with
    `prune=…`, which is now blocked in our face by defect #2 above.
- A Pi 5 (Cortex-A76) is the floor for this code: the port uses `PRFM`, LSE
  atomics where the twins emit them, and the SHA path probes `ID_AA64ISAR0`;
  a Pi 4 (A72) will run everything but changes every timing baseline in the
  repo, so **do not compare a Pi number against an xspark04 or x86 number** —
  record it as its own row. Pi 4/5 both run a 64-bit OS; 32-bit OS = not this
  port at all.
- Expected new-host findings on a Pi: different `.bss`/TLS layout tolerances,
  page size (4 KiB, same as here — fine), a different peer pool (see item 4),
  and no Core oracle unless the operator moves one. First session on the Pi
  should be "does the sweep reproduce round 44b exactly" — that is the
  host-portability test, and anything that differs is the first real finding.

## If the node must run on `xspark04` again

Only in a window, and only if the LLM workload can spare it — the box was
taken off bmc because the node's RSS reached 6.8 GB with 114 of 121 GiB already
committed to the LLM and swap in use. Rules that keep the peace:

```bash
sudo systemctl enable --now bmc-arm.service      # back on, boot-persistent
sudo systemctl start bmc-arm.service             # one run, stay disabled
tail -F data/main/debug.log                      # the log; the journal is not it
sudo systemctl status bmc-arm --no-pager         # NRestarts must stay 0
```

Bound it instead of letting it have the box — a `CPUQuota=`/`MemoryMax=` drop-in
plus `systemd-analyze`, or `ionice -c3`/`nice` on a manual run. Never run an IBD
and the sweep on this box at the same time. And per this evening: the unit is
`Restart=always` with `RestartSec=15`, so `pkill` is not a stop — a killed node
comes back in 15 s; use `systemctl stop`.

Also true and worth repeating: **the node must run as `xian`, never root.** The
unit said `User=root` by design until 2026-09-08 session 3, when a parser
SEGV during boot made it a privilege question rather than a style one
(an untrusted-input parser crashing as root is a compromise, not a crash).
`data/` was chowned to match. Keep it that way on the Pi too.
